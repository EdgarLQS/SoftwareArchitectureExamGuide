# 专题四：软件工程、建模与可靠性

> 本文是当前复习版本。历史长文 [`04-软件工程与可靠性.md`](./04-软件工程与可靠性.md) 保留旧表格和例题，但其中固定维护比例、过程模型绝对化、UML/DFD 混搭和可用性公式等结论不再作为默认口径。

## 一、软件过程模型

### 1.1 瀑布模型

瀑布强调阶段、评审和文档基线，适合需求相对稳定、合规和交付边界清晰的项目。它并不意味着物理上绝对不能回退；真正的问题是变更成本随阶段推进增大，反馈周期较长。

适用判断：

- 需求和验收标准是否稳定；
- 是否需要正式阶段审查和可追溯文档；
- 技术不确定性和用户反馈需求是否较低；
- 变更审批和交付周期是否可接受。

### 1.2 增量与迭代

- 增量：每次交付可运行的新功能范围；
- 迭代：反复修正需求、设计和实现；
- 两者可以同时存在，一个 Sprint 或版本既迭代已有设计，也交付新的增量。

“增量没有风险分析、迭代没有可交付成果”都不是通用定义。

### 1.3 原型与螺旋

原型用于探索需求、交互或技术可行性。抛弃型原型不直接演进为生产代码，演化型原型则需要从一开始控制架构和质量债。

螺旋模型强调每一轮识别目标、分析风险、开发验证并规划下一轮。它适合风险高和不确定性大的项目，但需要成熟的风险管理能力。

### 1.4 V 模型

V 模型强调开发活动与相应验证/确认活动的对应关系。具体对应关系因组织和版本而异，不应机械背成唯一固定表。答题重点：

```text
需求有验收依据
→ 架构和接口有集成验证
→ 详细设计有单元/组件验证
→ 测试活动尽早规划并保持可追溯
```

### 1.5 敏捷与 Scrum

敏捷是一组价值观和原则，不等同于“没有文档、没有架构、需求随意变化”。敏捷强调早期持续交付、拥抱变化、业务与开发协作、可工作的软件、技术卓越和持续改进。

当前 Scrum Guide 定义：

- Scrum Team 包含 Product Owner、Scrum Master 和 Developers；
- 一个 Sprint 内包含 Sprint Planning、Daily Scrum、Sprint Review 和 Sprint Retrospective；
- Product Backlog、Sprint Backlog 和 Increment 分别对应 Product Goal、Sprint Goal 和 Definition of Done；
- Scrum 是轻量框架，不规定具体工程实践。

不要继续使用“团队必须 7±2 人”“Daily Scrum 必须站立”“每个 Sprint 必须两周”等旧式固定结论。团队规模、Sprint 长度和会议形式应符合 Guide 的边界和实际工作需要。

## 二、遗留系统演进

常见策略：

| 策略 | 适用条件 | 主要风险 |
|------|----------|----------|
| 继续维护 | 业务价值高且现有系统仍可控 | 技术债和人才风险 |
| 再工程 | 核心逻辑有价值，可通过重构、重构数据和现代化部署延寿 | 投入难量化、旧缺陷延续 |
| 渐进替换 | 可按业务边界逐步迁移 | 新旧并存、数据同步和切换复杂 |
| 整体替换 | 边界较小、替换风险可控 | 大爆炸切换、需求遗漏和回退困难 |
| 退役 | 价值低或已有替代方案 | 数据归档、合规和依赖清理 |

Strangler Fig 的核心是围绕旧系统逐步建立新能力、路由流量并替换旧功能，以降低大爆炸重写风险。它不是自动成功模式，仍需处理数据、双写、身份、监控、回滚和组织边界。

## 三、软件维护

### 3.1 四类维护

| 类型 | 目的 | 示例 |
|------|------|------|
| 纠错性 | 修复已发现缺陷 | 修复订单重复、空指针和计算错误 |
| 适应性 | 适应外部环境变化 | 法规、平台、数据库或协议升级 |
| 完善性 | 改善功能、性能或体验 | 新业务能力、查询优化和交互改进 |
| 预防性 | 降低未来故障和维护成本 | 重构、测试补齐、依赖升级和文档修复 |

不要把各类维护占比或“维护占生命周期 60%—80%”作为普遍且无需来源的考试硬数据。不同产品生命周期、业务增长和统计口径差异很大。

### 3.2 可维护性

评估维度包括：

- 模块边界和耦合；
- 可理解性和代码复杂度；
- 测试覆盖和变更反馈速度；
- 构建、发布和回滚能力；
- 文档、ADR 和知识传递；
- 依赖、漏洞和技术债风险；
- 变更失败率、修复时间和重复故障率。

圈复杂度、覆盖率和重复率都是信号，不应使用一个固定阈值决定所有模块质量。支付、核心算法和生成代码的风险和测试策略不同。

## 四、数据流图 DFD

### 4.1 基本元素

| 元素 | 含义 |
|------|------|
| 外部实体 | 系统边界之外的数据来源或去向 |
| 加工/处理 | 对输入数据进行转换并产生输出 |
| 数据流 | 数据在实体、加工和数据存储之间的移动 |
| 数据存储 | 系统内部持久或暂存的数据集合 |

DFD 描述数据如何流动和转换，不表示调用时序、控制条件、并发或部署拓扑。

### 4.2 分层和平衡

- 上层加工可以分解为下层子图；
- 父加工的外部输入输出应与子图边界的净输入输出一致；
- 平衡关注跨层边界的数据流，不要求内部每条流都出现在父图；
- 分解后可以细化数据名称，但应保持可追溯的数据字典；
- 上下层不平衡通常表现为新增、丢失或方向改变的外部数据流。

### 4.3 常见错误

- 黑洞：有输入无输出；
- 奇迹：无输入产生输出；
- 灰洞：输入不足以解释输出；
- 外部实体直接访问数据存储；
- 数据存储之间直接传输而没有加工；
- 数据流缺少名称或使用控制动作作为数据名；
- 把数据库表、程序模块和业务人员混成同一层级。

## 五、UML 建模

OMG UML 2.5.1 是当前正式规范版本。UML 图按结构和行为理解，不必背旧教材中不统一的“九种/十三种/十四种”数量结论。

### 5.1 常用结构图

| 图 | 主要表达 |
|----|----------|
| 类图 | 类型、属性、操作和关系 |
| 对象图 | 某一时刻对象实例与链接 |
| 组件图 | 组件、接口和依赖 |
| 包图 | 模型元素分组和依赖 |
| 部署图 | 制品、节点和部署关系 |
| 组合结构图 | 分类器内部部件、端口和连接 |

### 5.2 常用行为图

| 图 | 主要表达 |
|----|----------|
| 用例图 | 参与者、系统目标和用例关系 |
| 活动图 | 工作流、分支、并发和对象流 |
| 状态机图 | 对象状态、事件、迁移和动作 |
| 顺序图 | 交互参与者和消息时间顺序 |
| 通信图 | 交互参与者之间的结构与编号消息 |
| 时序图 | 状态或值随时间变化 |

### 5.3 用例关系

- `include`：基础用例必定复用被包含行为；
- `extend`：在扩展点和条件满足时追加可选行为；
- 泛化：子用例或子参与者继承并细化父元素语义。

不要只凭“是否经常发生”判断 include/extend，应看行为是否是基础用例完成目标所必需，以及扩展是否条件化。

### 5.4 顺序图与通信图

两者都描述交互。顺序图突出时间顺序和生命线，通信图突出对象链接和消息编号。可以转换语义，但复杂交互、并发和时序约束在表达上有差异。

## 六、需求、分析与设计模型

不建议再使用“功能模型=用例图/DFD、对象模型=类图、动态模型=状态图”作为唯一固定三模型。

更实用的组织方式：

```text
业务目标与干系人
→ 用例/用户旅程和业务规则
→ 领域模型、数据模型和上下文边界
→ 交互、状态和工作流
→ 架构、接口和部署
→ 可验证的需求与验收标准
```

DFD、UML、BPMN、E-R 和 C4 等模型各有视角，应按问题选择，不把不同建模体系强行合并成同一标准分类。

## 七、软件测试

### 7.1 测试层次

| 层次 | 关注点 |
|------|--------|
| 单元/组件测试 | 局部逻辑、边界和异常 |
| 集成测试 | 组件、数据库、消息和外部接口协作 |
| 系统测试 | 完整系统相对于需求和质量目标 |
| 验收测试 | 用户或业务是否接受交付结果 |

测试层次和组织方式因项目而异，不能把 V 模型对应表当作唯一定义。

### 7.2 黑盒、白盒和灰盒

- 黑盒：从输入输出和外部行为设计测试；
- 白盒：基于代码结构、控制流和数据流；
- 灰盒：利用部分内部知识设计接口、集成和安全测试。

黑盒与白盒是测试设计视角，不等于测试层次。

### 7.3 覆盖与测试充分性

语句、分支、条件、MC/DC 和路径覆盖是不同强度的结构覆盖指标。覆盖率高不代表断言正确、边界完整或风险被覆盖。

测试策略应结合：

- 业务风险和故障后果；
- 代码复杂度和变化频率；
- 输入组合和边界；
- 并发、时间和故障注入；
- 安全、性能和恢复要求。

### 7.4 性能与可靠性测试

- 负载测试验证目标负载下的 SLO；
- 压力测试寻找退化点和容量边界；
- 稳定性测试观察长时间资源和延迟漂移；
- 故障注入验证检测、隔离和恢复；
- 容量测试应同时覆盖数据库、缓存、消息和外部系统。

## 八、可靠性、可用性与韧性

### 8.1 概念区分

- 可靠性：指定条件和时间内正确执行功能的能力；
- 可用性：需要服务时可成功使用的程度；
- 可恢复性：故障后恢复服务和数据的能力；
- 韧性/鲁棒性：面对故障、异常和环境变化维持或恢复可接受服务的能力；
- 数据完整性：数据不被未授权或意外破坏，并能检测和恢复错误。

### 8.2 可用性度量

时间可用性常写为：

```text
Availability = 可用时间 / 总观测时间
```

在“故障与修复周期稳定、只有完全可用/不可用两个状态”等简化假设下，可近似写为：

```text
A = MTBF / (MTBF + MTTR)
```

该公式不适合直接描述部分降级、多区域、流量波动和按请求成功率衡量的服务。互联网服务通常更应使用：

```text
成功且符合 SLO 的请求 / 有效请求总数
```

同时明确哪些错误计入、观测窗口、计划维护和依赖故障处理方式。

### 8.3 SLI、SLO 和错误预算

- SLI：实际测量指标，如成功率、P99 延迟和数据新鲜度；
- SLO：对 SLI 的目标；
- SLA：与用户或客户约定的责任和后果；
- 错误预算：`1 - SLO` 允许的失败空间，用于平衡可靠性和发布速度。

“99.99%”必须说明时间窗口和计算方式，不能只写数字。

## 九、可用性与可靠性战术

### 9.1 故障预防

- 限制资源、负载和变化风险；
- 隔离故障域；
- 冗余和多样性；
- 配置、制品和依赖治理；
- 容量规划和渐进发布。

### 9.2 故障检测

- 心跳、Ping/Echo 和健康检查；
- 超时、租约和看门狗；
- 日志、指标、链路和审计；
- 数据校验、对账和不变量检查。

检测机制会出现误报和漏报。心跳周期、超时和故障判定需要结合网络延迟、负载和恢复成本。

### 9.3 故障恢复

- 主备或多副本切换；
- 重试、回滚、补偿和状态重建；
- 断路、限流和降级；
- 检查点、日志回放和备份恢复；
- 人工应急和演练。

重试必须有幂等、截止时间、退避和上限。降级不能返回虚假成功或破坏核心业务不变量。

### 9.4 恢复目标

- RTO：允许的恢复时间目标；
- RPO：允许的数据丢失窗口目标；
- 两者是业务目标，不是备份产品自动保证的属性；
- 必须通过恢复演练验证备份、权限、密钥、依赖和人员流程。

## 十、可靠性工程流程

```text
识别关键业务与故障后果
→ 定义质量属性场景和 SLO
→ 分析依赖、故障域和容量
→ 选择检测、隔离和恢复战术
→ 建立可观测性与运行手册
→ 进行负载、故障和恢复测试
→ 复盘事故并调整架构
```

不要只依赖理论 MTBF 预测。对复杂软件系统，更可靠的证据来自架构分析、测试、生产 SLI、事故数据和恢复演练。

## 十一、案例答题框架

### 11.1 DFD/UML 图题

```text
识别图类型和语义
→ 找已知实体/对象和边界
→ 根据数据或消息方向补空
→ 检查平衡、职责和依赖
→ 使用题干术语作答
```

### 11.2 可靠性设计题

```text
定义故障场景
→ 指定刺激、环境和受影响制品
→ 选择检测机制
→ 隔离故障和保护资源
→ 恢复服务与数据
→ 给出 SLI、RTO、RPO 和演练方式
```

### 11.3 遗留改造题

```text
评估业务价值和技术质量
→ 选择维护、再工程、渐进替换或退役
→ 建立边界和流量路由
→ 处理数据同步、兼容和回滚
→ 逐步迁移并停止旧功能
```

## 十二、考场检查

- [ ] 是否避免把瀑布写成物理上绝对不可回退
- [ ] 是否按当前 Scrum Guide 描述角色、事件和承诺
- [ ] 是否避免固定维护比例和成本比例
- [ ] DFD 分层是否检查父子边界净输入输出
- [ ] 是否区分 DFD、UML、E-R 和 BPMN 的用途
- [ ] 用例 include/extend 是否按必要性和条件判断
- [ ] 是否区分可靠性、可用性、可恢复性和数据完整性
- [ ] 可用性公式是否说明观测窗口和假设
- [ ] 是否使用 SLI/SLO、RTO/RPO 和故障演练验证设计
- [ ] 重试、故障转移和降级是否说明幂等与副作用

## 十三、核验依据

- OMG Unified Modeling Language 2.5.1；
- Agile Manifesto 与十二条原则；
- The Scrum Guide 2020；
- Software Engineering Institute 可用性战术和可靠性资料；
- Google Site Reliability Engineering 的 SLI/SLO、可用性和可靠性工程资料；
- Martin Fowler 的 Strangler Fig Application 渐进替换方法；
- 当前仓库历年案例核验说明和测试、维护论文专题技术校准结果。
