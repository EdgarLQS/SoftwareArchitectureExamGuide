## 第一大题：电动车充电管理系统（质量属性分析）

**案例背景：**

某市计划建设一套**电动车充电管理系统**，为城市中的集中式充电站、路侧分布式充电桩以及用户手机 APP 提供统一的接入与管理服务。

系统需满足如下质量需求场景（a～n）：

| 编号 | 场景描述 |
|------|----------|
| a | 当用户通过手机 APP 或现场终端发起"开始充电"操作后，系统必须在 **3 秒内**给出响应结果（成功/失败及原因），否则视为超时。 |
| b | 在充电站方圆 200 米范围内，即使同时有超过 **300 个设备**在充电或等待充电口分配，系统 **CPU 使用率仍需控制在 40% 以下**，保证系统性能稳定。 |
| c | 当运营方提出集成新的第三方支付或计费 API 时，自提出需求之日起，须在 **10 个工作日内**完成设计、开发、联调和上线，不影响原有业务功能。 |

| j | 针对普通新用户，从首次接触系统到能独立完成一次充电操作的时间，**不应超过 60 秒**，体现系统的易学性和操作简单。 |
| k | 系统前端界面需在不同分辨率与不同类型终端设备（手机、平板、PC、大屏）上**自适应显示**，保证布局清晰、控件可用。 |

### 问题3

用户个人信息、位置信息可能长度较长，而 **AES-256 为定长 128bit（16 字节）块加密算法**。对于超长数据，系统应如何处理才能正确进行加密？请从处理流程上进行说明。

**我的答案**

超长数据使用  **AES-256 定长 128bit（16 字节）块加密算法** 加密如下

- 将待加密数据按一定长度和方法进行分序号进行拆分 ，拆分后再将数据进行分别加密传输
- 收到数据后 再分别对数据进行解密，然后按照序号在进还原文本

---

**评分：约 2/5 分**

**评判：**
- ✓ 方向正确：数据拆分→分别加密→传输→解密→按序号还原
- ✗ 缺少关键技术术语：未提到**分组密码工作模式**（如 CBC、CTR、GCM 等），这是本题的核心考点
- ✗ 未提到**初始化向量（IV）**的作用（防止相同明文块产生相同密文）
- ✗ 未提到**填充方案**（如 PKCS#7）处理最后一块不足 16 字节的情况
- ✗ 未提到**认证加密**（如 GCM 模式）保证数据完整性

---

**补充答案（标准参考）：**

AES-256 是 128bit（16字节）块加密算法，本身只加密固定 16 字节的单个数据块，不处理超长数据。超长数据需通过加密组件库（如 Java Cipher、Python cryptography）在外层自动封装分块、填充和工作模式逻辑。具体处理流程如下：

1. **数据分块**：将超长用户信息按 16 字节（128bit）划分为固定长度的明文块
2. **填充处理**：若最后一块不足 16 字节，使用 **PKCS#7 填充**补齐（缺 N 字节则补 N 个 0x0N）；若恰好整除，额外补 1 个完整块确保可去填充
3. **分组加密**：选用安全模式（如 CBC、CTR、GCM），首块与随机 IV 异或后加密，后续块与前一块密文异或再加密，保证相同明文块生成不同密文
4. **密文拼接**：将所有分块加密后的密文按顺序拼接，形成最终完整密文（用于存储/传输）

**解密流程**：先拆分密文为 16 字节块 → 逐块解密 → 去除填充 → 还原原始数据

> **补充说明**：AES 算法本身只做"加密固定 16 字节单个块"一件事；分块、填充、工作模式（CBC/GCM）由加密组件库自动封装实现。

## 第二大题：云–端一体点菜系统

**案例背景：**

某连锁餐饮集团建设了"云–端一体的点菜系统"。

**终端侧（端）：**部署在门店的收银机、服务员手持 PAD、自助点餐机等，负责：
1. 桌台管理与点菜下单；
2. 本地订单暂存与支付；
3. 与云端同步菜品、价格等基础数据。

**云端系统（云）：**部署在集团数据中心或公有云，负责：
1. 菜品基础信息管理（菜品、原料、定价、上下架等）；
2. 订单管理（汇总各门店订单、对账、结算）；
3. 餐厅菜品与菜单配置（不同门店的可售菜品组合）；
4. 员工与权限管理；
5. 报表分析与运营决策。

企业计划采用 **领域驱动设计（DDD）** 方法，对复杂的业务域进行建模和拆分，同时需要考虑云端与终端之间的网络质量不稳定（弱网、间歇断网）的情况，保证点单业务"**尽量可用 + 数据最终一致**"。

**DDD 基本思想：**
领域驱动设计是一种以业务领域为核心的软件设计方法论，强调通过"通用语言"（Ubiquitous Language）让技术人员与业务专家使用同一套术语沟通，将业务逻辑直接映射到代码模型中。核心概念包括实体、值对象、聚合根、领域服务和限界上下文。

**限界上下文（Bounded Context）定义：**
限界上下文是 DDD 中用于划分复杂业务域的边界，每个限界上下文拥有独立的领域模型、通用语言和数据库。在边界内，术语和规则具有一致的含义；跨越边界时，需要通过上下文映射（Context Mapping）进行转换。

**在点菜系统中的作用：**
1. **业务域拆分**：将复杂的点菜系统拆分为订单管理、菜品管理、桌台管理、支付管理等独立上下文
2. **降低复杂度**：每个团队专注一个上下文，模型互不干扰
3. **独立演进**：各上下文可独立开发、部署和扩展
4. **云-端协同**：云端负责全局上下文（菜品库、对账），端侧负责本地上下文（桌台、暂存订单），通过上下文映射实现数据同步

## 第三大题：电商平台 MySQL + Redis 缓存架构（缓存击穿问题）

**案例背景：**

某互联网电商平台采用 MySQL + Redis 的缓存架构。核心接口为"查询商品详情"，日常峰值 QPS 达到几万。

系统目前使用 Cache-Aside 模式：先查 Redis 缓存，命中则直接返回；未命中时访问数据库，并把结果写回 Redis，设置过期时间（TTL）。

近期运维发现：某些热点商品在缓存失效瞬间，会出现大量请求同时击穿缓存、直接访问数据库，导致数据库连接数飙升、接口响应超时，影响系统整体可用性。

架构组组织评审，提出了两种优化思路：

- 方案一（王工）：基于互斥锁的物理过期方案。 仍然依赖 Redis TTL，缓存正常按过期时间删除。当缓存未命中时，只有拿到互斥锁的线程才允许去数据库重建缓存，其它线程等待或重试。

- 方案二（李工）：逻辑过期方案。 不依赖互斥锁做强同步，可返回过期数据。Redis 中存储"业务数据 + 逻辑过期时间字段"，可以不设置或设置很长 TTL。访问时若发现逻辑过期，可以先返回旧数据，同时由获取到非互斥锁的线程或后台异步线程去数据库重建缓存。
