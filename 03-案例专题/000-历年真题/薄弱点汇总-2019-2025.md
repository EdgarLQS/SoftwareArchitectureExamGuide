### 完整复习资料

#### 1. Cache-Aside Pattern（旁路缓存模式）标准流程

**读数据流程（5步）：**
```
客户端请求
  → ① 查询缓存
    → 缓存命中 → ② 直接返回数据给客户端
    → 缓存未命中 → ③ 查询数据库
                   → ④ 将数据库查询结果写入缓存
                   → ⑤ 返回数据给客户端
```

**写数据流程（2步）：**
```
客户端写请求
  → ① 先更新数据库
  → ② 删除缓存（注意：是删除，不是更新！）
  → 返回成功
```

#### 2. 为什么写操作是"删除缓存"而非"更新缓存"？

在并发场景下，如果"先更新缓存再写数据库"：
```
时刻1：线程A更新缓存为新值X
时刻2：线程B读缓存，拿到X（但数据库还是旧值！）
时刻3：线程A写数据库失败
结果：缓存是新值X，数据库是旧值，数据不一致
```

正确的"先写数据库再删除缓存"：
```
时刻1：线程A写数据库成功为新值X
时刻2：线程A删除缓存
时刻3：线程B读缓存未命中 → 查数据库拿到X → 回写缓存
结果：缓存和数据库都是X，最终一致
```

#### 3. 多线程缓存数据不一致的解决方案（至少掌握4种）

| 方案 | 原理 | 适用场景 |
|------|------|---------|
| **Cache-Aside标准模式** | 先写数据库，再删除缓存 | 一般场景 |
| **延迟双删** | ①先删缓存 → ②写数据库 → ③延时500ms → ④再删缓存 | 消除读写并发窗口 |
| **分布式锁** | 读写使用同一把分布式锁（Redis SETNX），保证串行化 | 强一致性要求高 |
| **订阅 binlog 异步淘汰** | 通过 Canal 等工具监听数据库 binlog，变更时异步淘汰缓存 | 解耦、高性能 |
| **设置合理的 TTL** | 即使缓存未及时淘汰，过期后自动失效重建 | 兜底方案 |

#### 4. 缓存击穿防护两种方案对比

| 对比维度 | 王工：互斥锁+物理过期 | 李工：逻辑过期 |
|---------|---------------------|---------------|
| **实现复杂度** | 简单，加分布式锁即可 | 复杂，需维护逻辑过期字段+异步刷新 |
| **响应延迟** | 较高，未获锁线程需等待 | 低，始终立即返回旧数据 |
| **数据一致性** | 强，重建后返回最新数据 | 弱，可能短暂返回过期数据 |
| **可用性** | 较差，锁超时或DB故障时可能不可用 | 高，即使DB故障也能返回旧数据 |
| **适用场景** | 库存、价格等强一致性场景 | 商品详情等可容忍短暂不一致场景 |

**互斥锁方案流程（王工）：**
```
查缓存 → 未命中 → 尝试获取互斥锁
  → 获取成功 → 查数据库 → 写缓存 → 释放锁 → 返回数据
  → 获取失败 → 等待/自旋重试 → 重新查缓存 → 返回数据
```

**逻辑过期方案流程（李工）：**
```
查缓存 → 发现逻辑过期 → 尝试获取刷新锁
  → 获取成功 → 先返回旧数据 → 开异步线程查DB → 更新缓存 → 释放锁
  → 获取失败 → 直接返回旧数据
```

### 完整复习资料

#### 1. RDB vs AOF 全面对比（必须背熟）

| 对比维度 | RDB（快照） | AOF（追加日志） |
|---------|-----------|---------------|
| **原理** | 定期将内存数据生成二进制快照文件(.rdb)保存到磁盘 | 将每个写操作以Redis协议格式追加到AOF日志文件 |
| **磁盘更新频率** | 低，按时间间隔快照 | 高，实时记录每次写操作 |
| **数据安全** | **较低**，快照间隔内数据可能丢失 | **较高**，追加日志保证数据安全 |
| **数据一致性** | **较低**，快照时刻数据，可能丢失间隔数据 | **较高**，记录每次写操作，数据完整 |
| **重启性能** | **快**，直接加载快照文件 | **慢**，需重新执行日志中的写操作 |
| **数据文件大小** | **小**，压缩快照 | **大**，记录每次写操作 |
| **适用场景** | 大规模数据恢复、备份、对性能要求高 | 对数据完整性要求高、可容忍恢复慢 |

**AOF 三种 fsync 策略：**
- `always`：每次写入都刷盘 → 最安全但最慢
- `everysec`：每秒刷盘（默认） → 最多丢1秒数据，性能与安全平衡
- `no`：由OS决定何时刷盘 → 最快但最不安全

**混合使用推荐**：RDB 定期全量备份 + AOF everysec 保证数据完整性。

#### 2. Redis 6种内存淘汰机制（必须背熟）

```
┌─────────────────────────────────────────────────────────┐
│                    Redis 内存淘汰机制                      │
├──────────────────────┬──────────────────────────────────┤
│  针对已设置过期时间的   │  针对全部键                        │
│  (volatile-xxx)      │  (allkeys-xxx)                   │
├──────────────────────┼──────────────────────────────────┤
│ volatile-lru          │ allkeys-lru                       │
│ 淘汰最近最少使用的数据   │ 淘汰最近最少使用的数据              │
├──────────────────────┼──────────────────────────────────┤
│ volatile-ttl          │ allkeys-random                    │
│ 淘汰即将过期的数据      │ 任意选择数据淘汰                    │
├──────────────────────┼──────────────────────────────────┤
│ volatile-random       │ noeviction                        │
│ 任意选择过期数据淘汰    │ 不淘汰，内存满时写操作返回错误        │
└──────────────────────┴──────────────────────────────────┘
```

#### 3. Redis 5种数据类型

| 数据类型 | 特点 | 典型场景 |
|---------|------|---------|
| **String** | 最基本类型，key-value，value 可以是字符串/数字 | 评论计数器、会话存储、缓存单个对象 |
| **List** | 双向链表，支持从两端插入/弹出 | 粉丝列表、消息队列、发布/订阅 |
| **Set** | 无序不重复集合 | 标签管理（去重）、共同好友（交集） |
| **Hash** | key-field-value 结构，类似小型关系表 | 用户信息结构化存储、对象属性存储 |
| **ZSet** | 有序集合，每个元素关联score，自动排序 | 排行榜、热搜榜、延迟队列 |

#### 4. Redis 主从同步流程（必考）

**全量同步（5步）：**
```
① 从库向主库发送 PSYNC -1 或 SYNC 请求（发起首次同步）
② 主库执行 BGSAVE 命令，在后台生成 RDB 快照文件
   （BGSAVE 期间主库仍可正常处理客户端读写，通过 fork + COW 实现）
③ 主库将 BGSAVE 期间的写操作追加到 replication backlog（复制缓冲区）
④ 主库通过 socket 将 RDB 文件传输给从库
⑤ 从库加载 RDB 后，主库将 backlog 中的增量写命令发送给从库
```

**BGSAVE 核心机制：**
- `fork()` 创建子进程，子进程获得父进程内存空间副本
- **COW（Copy-On-Write）**：fork 后父子进程共享物理内存；父进程写数据时，OS自动复制被修改页给子进程
- 子进程看到 fork 时刻的旧数据（保证快照一致性），父进程继续处理新数据（不影响业务）
- **BGSAVE vs SAVE**：BGSAVE 异步不阻塞，SAVE 同步阻塞（生产环境用 BGSAVE）

**增量同步（3步）：**
```
① 主库将新写操作追加到复制缓冲区（replication buffer）
② 主库将增量命令（带偏移量 offset）持续发送给从库
③ 从库接收并执行增量命令，更新自身数据，保持与主库一致
```

#### 5. Redis 分布式锁

**基本命令：**
```
SET lock_key unique_value NX EX 10
```
- `NX`：Only set if Not eXists（只有key不存在时才设置）
- `EX 10`：过期时间10秒

**死锁场景：**
1. **客户端获取锁后崩溃，未设TTL** → 锁永久存在，其他客户端永远无法获取
2. **业务执行超时，锁自动释放** → A和B同时持有"锁"执行临界区，数据不一致
3. **可重入锁未正确释放** → 嵌套调用中异常退出，重入计数未完整释放

**解决方案：**
- 使用 `SET key value NX EX seconds` 原子命令（不要用分开的 SETNX + EXPIRE）
- 使用 Redisson 客户端（内置 Watch Dog 自动续期）
- 使用 Redlock 算法（多Redis实例，提高可靠性）

#### 6. Redis-MySQL 数据同步方案

| 方案 | 原理 | 优缺点 |
|------|------|--------|
| **Cache-Aside** | 先更新数据库，再删除缓存 | 简单，标准做法 |
| **数据库 binlog 订阅** | Canal 等工具监听 binlog，异步淘汰缓存 | 解耦、高性能 |
| **触发器同步** | 数据库触发器通知缓存更新 | 侵入性强，不推荐生产使用 |

#### 1. 质量属性场景 6 要素（必须背诵）

| 要素 | 说明 | 示例 |
|------|------|------|
| **刺激源（Source）** | 产生刺激的事物 | 用户、外部系统、硬件故障、管理员 |
| **刺激（Stimulus）** | 影响系统的事件 | 崩溃、超时、流量激增、集成新API、修改配置 |
| **环境（Environment）** | 刺激发生时系统所处的状态 | 正常运行、系统过载、降级模式、维护模式 |
| **工件（Artifact）** | 被刺激影响的系统部分 | 处理器、数据库、通信信道、持久存储器、进程 |
| **响应（Response）** | 系统对刺激的反应活动 | 记录日志、通知管理员、切换备用系统、禁止故障源 |
| **响应度量（Response Measure）** | 衡量响应是否合格的标准 | 5分钟内恢复、30秒内切换、99.99%可用时间 |

**记忆口诀：源 → 刺 → 环 → 工 → 响 → 度量**

#### 2. 可用性 vs 可靠性 vs 性能 区分

| 质量属性 | 关注点 | 关键词 | 典型场景 |
|---------|--------|--------|---------|
| **可用性** | **故障恢复速度** | MTTR、MTBF、切换、恢复、备用、热备份 | 断电后5秒切换到备用站点、宕机后10秒感知并启动热备份 |
| **可靠性** | **故障不发生/不扩散** | 容错、健壮性、故障隔离、不影响、继续运行 | 部分模块出错不影响整体、错误时不影响正常运行 |

---

### 完整复习资料

#### 1. DFD 四要素

| 要素 | 图形 | 命名规则 | 示例 |
|------|------|---------|------|
| **外部实体** | 矩形框 | 名词（人或组织） | 注册客户、供应商、经理 |
| **加工/处理** | 圆角矩形/圆形 | **动宾结构**（做什么） | 在线订餐、厨房备餐、生成报表 |
| **数据流** | 带箭头线段 | **名词**（是什么） | 订单信息、已付款订单、统计报表 |
| **数据存储** | 开口矩形/双线 | 名词 | 订单表、食材库存 |

#### 2. DFD 基本规则

1. **每个加工必须有输入和输出**（没有输入=奇迹/无中生有；没有输出=黑洞/数据消失）
2. 数据流不能直接在两个外部实体之间流动
3. 数据流不能直接在外部实体和数据存储之间流动（必须经过加工）
4. 数据流不能直接在两个数据存储之间流动（必须经过加工）

#### 3. DFD 三类错误

| 错误类型 | 特征 | 举例 |
|---------|------|------|
| **黑洞（Black Hole）** | 有输入无输出，数据进入后消失 | "需求评估与课程推荐"加工只有输入无输出 |
| **灰洞/输入不足（Gray Hole）** | 有输入输出但输入不足以产生输出 | "培训课程安排"加工缺少必要的输入数据流 |
| **外部实体与存储直连** | 外部实体直接与数据存储相连，未经过加工 | 员工→员工数据库直连 |

#### 4. 数据平衡原则

- **父图与子图平衡**：子图所有加工的输入输出数据流之和 = 父图中对应加工的输入输出数据流
- **子图内平衡**：子图内每个加工必须有输入和输出数据流

#### 5. DFD vs 系统流程图

| 区别方面 | 数据流图（DFD） | 系统流程图 |
|---------|----------------|-----------|
| **展现内容** | 数据的流动、加工、存储和来源去向 | 处理的执行顺序和控制转移 |
| **并行性** | 加工可以**并行**执行 | 某个时间点只能处于**一个**处理过程（串行） |
| **计时标准** | 各加工之间遵循**不同的计时标准** | 各处理过程遵循**一致的计时标准** |

#### 6. 数据字典

**定义**：对数据流图中**所有数据元素**进行精确定义，消除歧义，确保开发人员和用户对数据有共同理解。

**定义对象**：数据项、数据结构、数据流、数据存储、加工

**作用**：
- 需求分析阶段：精确定义所有数据元素，消除歧义
- 设计阶段：为数据库设计（数据结构、数据项定义）提供基础

### 完整复习资料

#### 1. NoSQL 基本特点

- **Not Only SQL**（不仅仅是SQL），不是替代关系数据库，而是补充
- Schema-free（无固定表结构），灵活的数据模型
- 易水平扩展（Scale-out），原生支持分布式集群
- 遵循 BASE 理论（基本可用、软状态、最终一致性），不保证 ACID
- 针对特定场景优化，高性能

#### 2. 为什么 SNS 系统不适合用传统关系数据库

1. **可扩展性差**：关系数据库主要支持垂直扩展，SNS 需要水平扩展
2. **固定 Schema**：SNS 功能快速迭代，频繁修改表结构成本高
3. **高并发性能瓶颈**：百万级并发读写，锁和事务隔离成瓶颈
4. **复杂关系查询**：社交关系是图结构，"好友的好友"需大量 JOIN
5. **非结构化数据处理弱**：帖子、图片、评论不适合关系表

#### 3. NoSQL 四种类型

| 类型 | 数据模型 | 典型产品 | 适用场景 | 特点 |
|------|---------|---------|---------|------|
| **Key-Value** | 键值对 | Redis | 缓存、会话、计数器 | O(1)查找，读写性能最高 |
| **列式存储** | 列族 | HBase、Cassandra | 数据仓库、大数据分析、OLAP | 适合大规模数据分析 |
| **文档型** | BSON/JSON文档 | MongoDB | Blog、Wiki、内容管理 | Schema-free，结构灵活 |
| **图数据库** | 节点+边+属性 | Neo4j | 社交网络、推荐系统 | 高效查询复杂关系 |

#### 4. 混合数据库组织方式

按数据类型和访问模式组织：
- 关系型数据库（RDBMS）：结构化基本信息（用户、部门、订单）
- 图数据库：社交关系、推荐系统
- 文档型数据库：Blog、Wiki 等半结构化内容
- Key-Value 存储：缓存、会话、高速读写场景
- 各数据库通过**应用层统一调度**，按访问模式路由到对应存储引擎

### 完整复习资料

#### RESTful 核心特点

1. **资源导向**：所有数据抽象为资源，通过 URI 唯一标识（如 `/api/products/123`）
2. **HTTP 方法语义化**：
   - GET → 查询资源
   - POST → 创建资源
   - PUT → 更新资源
   - DELETE → 删除资源
3. **无状态**：每次请求包含完整上下文，服务端不保存会话状态
4. **标准 HTTP 状态码**：200成功、201创建、404未找到、500服务器错误等
5. **JSON 数据交换格式**

#### 前后端分离实现 RESTful

- 前端通过 HTTP方法 + 资源URI + JSON 数据体调用后端 API
- 后端提供统一的 RESTful 接口，接收 JSON 请求，返回 JSON 响应 + HTTP 状态码
- 前后端通过 API 约定接口规范，各自独立开发和部署
- 通过 CORS 解决跨域问题

---

### 完整复习资料

#### 1. 基于数据库主键索引实现分布式锁的缺点

1. **性能差**：每次获取锁需 INSERT/DELETE，数据库 IO 成本高；高并发时连接池资源耗尽
2. **数据库单点故障**：锁服务强依赖数据库，宕机则所有依赖该锁的业务不可用
3. **无法水平扩展**：数据库写入性能有上限
4. **不支持锁超时自动释放**：客户端崩溃后无法自动释放锁，需额外实现 TTL
5. **不支持可重入锁**：同一线程重复获取同一把锁会因主键冲突失败
6. **非公平锁**：无法保证 FIFO 顺序，可能导致饥饿
7. **竞态条件（TOCTOU）**：查询锁状态和插入记录不是原子操作

#### 2. Redis 分布式锁死锁场景

| 场景 | 过程 | 避免方法 |
|------|------|---------|
| 客户端崩溃未设TTL | A获取锁 → 崩溃 → 锁永久存在 → 其他人永远无法获取 | `SET key value NX EX seconds` |
| 业务执行超时 | A获取锁设10秒 → 业务耗时15秒 → 锁过期B获取 → A和B同时执行 | Watch Dog 自动续期（Redisson） |
| 可重入锁未正确释放 | 嵌套调用中异常退出 → 重入计数未完整释放 | 使用 Redisson 客户端 |
