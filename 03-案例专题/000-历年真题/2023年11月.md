**补充答案（标准参考）：**

- 当日概览模块需要**秒级刷新**实时信息，Lambda 的速度层（Speed Layer）可满足实时性需求
- 赛事回顾模块需要处理**海量历史数据**的统计分析，Lambda 的批处理层（Batch Layer）对全量历史数据吞吐量高、处理能力强
- Kappa 架构虽然也满足实时性，但历史数据处理能力较弱（流式全量处理吞吐量低），不适合该场景的海量历史数据分析需求

【说明】
说明:某软件公司为企业开发一套员工在线教育系统，支持员工利用业余时间开展专业技术培训，提升员工技能。在项目开展初期，采用结构化分析进行开发，并对系统中培训部员工和培训教师的相关功能进行分析，具体需求如下:、

**评分：约 2/8 分**

**评判：**

-  缺少 DFD 的四个核心要素：**外部实体**（数据源/终点）、**加工/处理**（数据变换）、**数据流**（数据 movement）、**数据存储**（数据仓库）

**补充答案（标准参考）：**

**数据流图（Data Flow Diagram, DFD）** 是一种图形化建模工具，用于描述系统中数据的**流动**和**变换过程**。DFD 由四个核心元素组成：
1. **外部实体**（External Entity）：位于系统边界之外，是数据的来源或去向（人或组织）
2. **加工/处理**（Process）：对输入数据进行变换，产生输出数据
3. **数据流**（Data Flow）：数据在元素之间的流动方向，用带标签的箭头表示
4. **数据存储**（Data Store）：数据暂存或持久化的位置

DFD 采用**分层分解**方法，从顶层图（Context Diagram）到 0 层图，再到各级子图，逐层细化描述系统的数据处理过程。DFD 关注"数据如何流动和变换"，不涉及控制逻辑和时间顺序。

**补充答案（标准参考）：**

1. **黑洞（Black Hole）**：
   - **位置**："需求评估与课程推荐"加工

   - **位置**："培训课程安排"加工

## 第4大题：Web应用架构

阅读下列说明，回答问题1至问题3，将解答填入答题纸的对应栏内。
【说明】
某国际大型企业拟向企业开发一个在线社交网络服务(SNS)系统，让企业内部的员工能够通过类似社交网络的方式进行工作和自我管理以实现企业内部员工高效、透明、便捷的沟通与协作。其基本的工序包括:
1、企业内部部门、员工等基本信息的维护和管理
2、提供常见的SNS服务，如Blog，WiKi,数钱，RSS，即时通信和邮件等
3、提供社交网络，推荐系统等基本功能提高业务协作
除了上述功能性的需求外，还需要满足系统的可拓展、灵活部署以及高性能和高可用性需求企业设计系统小组.

### 问题1
李工建议采用SNS中常见的NOSQL数据库技术，原因是传统的关系数据库不能满足实际需求，请用200 字内说明该系统不能采用**传统关系数据库的原因**，并给出**NOSQL数据的基本特点.**

**我的答案**

NOSQL数据特点如下

- 不仅仅是满足数据SQL 查询，还满足其他查询
- 不同传统的关系数据库的key-vALUE模式， NOSQL 的 value可进行自定义数据结构和扩展

不能采用**传统关系数据库的原因**如下

- SNS 需要满足 可拓展、灵活部署以及高性能和高可用性 在这几点上，选择  NOSQL 更加合适，因为 传统数据库拓展不是很方便
- SNS服务，如Blog，WiKi,数钱，RSS，即时通信和邮件等  ，可以看到需要做到这些服务，那么对数据结构的设计要求就很高，需要分别为每一种服务都去设计数据存储结构，但是如果是   NOSQL，那么就可以统一采取key-value的方式存储，key进行统一管理，然后 value针对不同业务进行设计即可

---

**评分：约 3/8 分**

**评判：**
-  NoSQL 特点理解有误：NoSQL 是 "**Not Only SQL**"（不仅仅是 SQL），不是"不仅仅是满足 SQL 查询"。NoSQL 的核心特点是灵活的数据模型（无固定 Schema）、易水平扩展、无复杂事务（遵循 BASE 理论）
-  "NoSQL 的 value 可进行自定义数据结构和扩展"表述不够准确。NoSQL 有四种主要类型：Key-Value、列式存储、文档型、图数据库，各有不同数据模型
-  不用传统关系数据库的原因方向正确（可扩展性、灵活部署），但缺少关键点：**高并发访问**、**海量非结构化数据**、**复杂关系查询**（社交网络的"好友的好友"需要大量 JOIN 操作）
-  "统一采取 key-value 方式存储"过于简化，SNS 系统需要多种 NoSQL 数据库类型配合

---

**补充答案（标准参考）：**

**不能采用传统关系数据库的原因：**
1. **可扩展性差**：关系数据库主要支持垂直扩展（Scale-up），SNS 系统数据量爆炸式增长，需要水平扩展（Scale-out）
2. **固定 Schema**：关系数据库需要预定义表结构，SNS 功能快速迭代，频繁修改表结构成本高
3. **高并发性能瓶颈**：SNS 系统面临百万级并发读写，关系数据库在锁和事务隔离上易成为瓶颈
4. **复杂关系查询**：社交关系形成图结构，"好友的好友"等查询需大量多表 JOIN，性能低下
5. **非结构化数据处理弱**：SNS 产生大量帖子、图片、评论等非结构化数据，不适合关系表结构

**NoSQL 数据库的基本特点：**
1. **灵活的数据模型**（Schema-free）：无需预定义表结构，支持动态数据结构
2. **易水平扩展**（Scalability）：原生支持分布式集群，可横向扩展
3. **无复杂事务**：遵循 BASE 理论（基本可用、软状态、最终一致性），不保证 ACID
4. **高性能**：针对特定场景优化（如 Key-Value 高速读写、图数据库关系查询）
5. **高可用**：内置副本和故障转移机制

**补充答案（标准参考）：**

混合数据库按数据类型和访问模式组织：
1. **关系型数据库（RDBMS）**：存储企业内部部门、员工等结构化基本信息，利用其强一致性和复杂事务支持
2. **图数据库（Neo4j 等）**：存储社交网络关系、推荐系统数据，利用图算法高效查询"好友的好友"等关系
3. **文档型数据库（MongoDB 等）**：存储 Blog、Wiki 等半结构化内容，灵活支持不同文档结构
4. **Key-Value 存储（Redis 等）**：用于缓存、会话管理、即时消息等高速读写场景

各数据库通过**应用层统一调度**，根据数据访问模式路由到对应的存储引擎，实现优势互补。
