# 专题三：Web、微服务与云原生

> 本文是当前复习版本。历史长文 [`03-Web架构与云原生.md`](./03-Web架构与云原生.md) 保留旧表格和例题，但其中架构演进、OAuth/JWT、Ingress、Secret、探针、HPA 和 Service Mesh 等结论不再作为默认口径。

## 一、架构演进不是单向必经路线

不能机械背诵：

```text
单体 → 垂直拆分 → SOA → 微服务 → 云原生
```

更准确的选择逻辑：

- 小型团队和清晰边界系统可以长期采用模块化单体；
- SOA 适合企业服务协同和异构集成，但不等于必须使用 ESB；
- 微服务适合需要独立演进、独立部署和团队自治的业务能力；
- 云原生是一组交付和运行能力，可服务于单体、微服务、批处理和事件系统；
- 架构选择应由业务复杂度、质量属性、团队能力和运维成本驱动。

## 二、微服务架构

### 2.1 核心目标

```text
围绕业务能力形成边界
→ 明确数据所有权
→ 支持独立演进和发布
→ 控制故障和变更影响面
```

常见特征：

- 服务围绕业务能力组织；
- 契约明确并可版本化；
- 每个服务对自己的数据和规则负责；
- 自动化构建、测试和发布；
- 面向失败设计并建立可观测性；
- 技术自治受组织标准、安全和运维能力约束。

“每个服务必须使用不同技术栈”是错误理解。过度异构会增加供应链、招聘、监控和运维成本。

### 2.2 服务拆分

拆分依据：

- 限界上下文和业务能力；
- 数据所有权与事务边界；
- 独立变化和发布频率；
- 负载和扩展差异；
- 团队职责和认知负担。

避免：

- 按数据库表一表一服务；
- 按技术层拆成用户 DAO、用户 Service 等远程服务；
- 按代码行数或事件数量机械拆分；
- 所有服务共享数据库并相互修改表；
- 形成同步调用链很长的“分布式单体”。

### 2.3 服务通信

| 方式 | 适用场景 | 主要风险 |
|------|----------|----------|
| HTTP/REST | 资源操作、外部 API、简单同步调用 | 时间耦合、超时和重试 |
| gRPC | 内部强类型、高效 RPC 和流式通信 | 契约演进、浏览器接入和调试 |
| 消息/事件 | 异步解耦、削峰和多消费者 | 重复、顺序、积压和最终一致 |
| 批量文件 | 外部机构和离线交换 | 时效、格式和补传治理 |

同步调用必须设置超时、重试条件、并发上限和取消传播。重试只适合幂等或可安全重复的操作，并应使用退避和抖动，避免重试风暴。

## 三、DDD 与服务边界

### 3.1 核心概念

| 概念 | 含义 |
|------|------|
| 限界上下文 | 模型和通用语言生效的明确边界 |
| 实体 | 由身份和生命周期区分的对象 |
| 值对象 | 由属性值定义、通常不可变的对象 |
| 聚合 | 事务一致性边界内的一组对象 |
| 聚合根 | 聚合对外访问和维护不变量的入口 |
| 领域事件 | 已发生且对领域有意义的事实 |
| 防腐层 | 在上下文边界转换外部模型，防止污染内部模型 |

限界上下文与微服务通常相关，但不是强制一一对应。一个上下文可以先由模块化单体实现，也可能因规模和部署需求拆为多个服务。

### 3.2 上下文映射

合作、客户—供应商、遵奉者、防腐层、开放主机服务和发布语言等关系用于描述上下文之间的依赖和模型转换。答题时应结合谁控制契约、谁承担适配成本和如何演进。

## 四、API 与 HTTP 语义

### 4.1 REST 设计

- 资源使用名词和稳定标识；
- 使用 HTTP 方法表达操作语义；
- 状态码区分成功、客户端错误、冲突、限流和服务故障；
- 分页、过滤、排序和字段选择有明确约定；
- 错误响应包含稳定错误码、消息和追踪标识；
- 契约和版本演进保持向后兼容或提供迁移期。

### 4.2 幂等

HTTP 规范把 PUT、DELETE 和安全方法定义为幂等方法，但幂等只约束用户请求的预期效果；服务器仍可能为每次请求写日志或记录审计。

POST 等非幂等业务可通过：

```text
Idempotency-Key
+ 请求摘要
+ 唯一约束
+ 状态记录
+ 重复响应复用
```

实现安全重试。

### 4.3 API 网关

网关常承担：

- 路由、协议转换和聚合；
- 认证入口与粗粒度策略；
- 限流、配额和防护；
- 版本、灰度和可观测性。

网关不应承担全部业务逻辑，也不能替代服务内部的资源级授权。网关是关键组件，需要多副本、容量规划、配置治理和故障降级。

## 五、服务治理与韧性

| 机制 | 目的 | 常见误区 |
|------|------|----------|
| 超时 | 限制等待时间和资源占用 | 所有调用使用同一固定值 |
| 重试 | 处理短暂故障 | 对非幂等请求盲目重试 |
| 熔断 | 在持续故障时快速失败并试探恢复 | 把熔断当作故障修复 |
| 隔离 | 限制单一依赖消耗全部资源 | 只做线程池不做容量预算 |
| 限流 | 保护系统和下游容量 | 只按单机 QPS，不考虑全局与租户 |
| 降级 | 保留核心能力 | 返回虚假成功或破坏业务语义 |
| 负载均衡 | 分配请求 | 忽略实例能力、区域和连接状态 |

重试、超时、熔断和限流需要协同，且必须受整体请求预算约束。

## 六、OAuth、OIDC 与 JWT

### 6.1 三者定位

- OAuth 2.0：授权框架，使客户端获得访问受保护资源的有限权限；
- OpenID Connect：建立在 OAuth 2.0 之上的身份层，提供用户认证和 ID Token；
- JWT：一种 Token 表示格式，可以用于 ID Token、Access Token 或其他声明，但使用 JWT 不自动获得安全性或“完全无状态”。

### 6.2 Token 校验

资源服务器校验至少包括：

- 签名算法和签名；
- `iss`、`aud`、`exp`、`nbf` 等声明；
- Key ID 与密钥轮换；
- Scope、角色和资源级权限；
- Token 撤销、短生命周期和风险控制；
- 重放保护和日志脱敏。

Access Token 不应被前端当作普通用户资料，ID Token 也不应直接代替 API 授权判断。

### 6.3 认证与授权

```text
认证：确认主体是谁
→ 授权：确认主体能对哪个资源做什么
→ 审计：记录谁在何时执行了什么
```

资源级授权必须在拥有资源语义的服务中执行，不能只依赖网关中的角色字段。

## 七、Web 安全

### 7.1 CORS

CORS 是浏览器实施的跨源访问控制机制，通过响应头决定脚本能否读取跨源响应。它不是服务器身份认证或通用防火墙。服务端仍需认证、授权、CSRF 和输入验证。

### 7.2 CSRF

当浏览器自动携带 Cookie 等凭证时，需要：

- SameSite Cookie；
- CSRF Token 或双提交策略；
- 校验 Origin/Referer；
- 对敏感操作进行重新认证；
- 避免使用 GET 修改状态。

Bearer Token 放在 Authorization Header 中通常不会被浏览器自动跨站携带，但仍需防范 XSS 和 Token 泄露。

### 7.3 XSS 与注入

- SQL 注入：参数化查询和最小权限，不能靠字符串过滤；
- XSS：按输出上下文编码，配合 CSP 和安全模板；
- 命令/模板/路径注入：使用安全 API、白名单和隔离；
- 输入验证与输出编码承担不同职责。

## 八、Kubernetes 核心对象

| 对象 | 主要作用 | 关键边界 |
|------|----------|----------|
| Pod | 一组共享网络和卷的容器，是调度单位 | 不是永久实例，不直接承担高可用 |
| Deployment | 管理无状态工作负载、副本和滚动更新 | 状态服务需额外设计 |
| StatefulSet | 为有状态工作负载提供稳定身份和有序管理 | 不自动保证数据复制与恢复 |
| Service | 为一组 Pod 提供稳定访问和服务发现 | 类型和实现因环境不同 |
| Ingress | 描述 HTTP(S) 外部路由规则 | 必须由 Ingress Controller 实现，不等于 Nginx |
| Gateway API | 更通用和角色化的流量管理 API | 需要对应控制器 |
| ConfigMap | 非敏感配置 | 不适合密码和密钥 |
| Secret | 小量敏感数据对象 | 默认存入 etcd 时并非自动加密 |
| Namespace | 名称与策略边界 | 不是硬安全隔离或环境唯一方案 |

Kubernetes 项目已冻结 Ingress API 的功能演进并推荐新需求考虑 Gateway API，但 Ingress 仍是稳定 API，不表示立即废弃。

### 8.1 Secret 安全

至少需要：

- etcd 静态加密；
- 最小权限 RBAC；
- 限制哪些 Pod 可读取；
- 审计和轮换；
- 必要时接入外部密钥系统；
- 避免在日志、环境转储和镜像中泄露。

## 九、探针与工作负载健康

| 探针 | 目的 | 失败后的主要结果 |
|------|------|------------------|
| Startup Probe | 判断应用是否完成启动 | 失败达到阈值后重启容器；成功前屏蔽其他探针 |
| Readiness Probe | 判断是否可以接收流量 | 从 Service 后端移除，但不重启容器 |
| Liveness Probe | 判断进程是否陷入不可恢复状态 | 失败达到阈值后重启容器 |

不要让 Liveness 依赖容易波动的下游，否则数据库或外部 API 故障可能触发所有 Pod 重启并形成级联故障。

Readiness 可以反映临时过载或必要依赖不可用；Startup 适合慢启动和预热应用。

## 十、弹性与容量

HPA 可以使用 CPU、内存、Pod 指标、对象指标和外部指标，并支持多指标。它调整的是副本数，不会自动扩展数据库、缓存、消息队列或第三方接口。

推荐流程：

```text
选择反映负载的指标
→ 设置资源 Request
→ 配置目标值和最小/最大副本
→ 配置扩缩容速率和稳定窗口
→ 校验数据库连接与下游容量
→ 压测启动、扩容、缩容和故障场景
```

连接预算示例：

```text
最大 Pod 数 × 每 Pod 最大连接数
≤ 数据库可用于该应用的连接预算
```

Cluster/Node Autoscaler 解决节点资源不足，但云资源申请、镜像拉取、调度、应用启动和预热都需要时间，不能承诺固定“分钟级”或“秒级”。

## 十一、发布与交付

```text
代码提交
→ 构建与单元测试
→ 依赖和镜像扫描
→ 生成 SBOM 与签名
→ 契约/集成/性能验证
→ 制品晋级
→ 金丝雀或蓝绿发布
→ SLO 观察
→ 自动或人工回滚
```

不可变镜像应与配置、密钥分离。配置热更新需要验证兼容性和失败回滚，不能保证所有应用无需重启。

## 十二、Service Mesh

Service Mesh 把部分服务间通信能力下沉到代理或节点基础设施，例如：

- mTLS；
- 流量路由；
- 遥测；
- 重试、超时和熔断策略。

“无侵入”只表示减少业务代码改造，不表示没有代价。Sidecar 模式会增加资源、网络跳数、证书和升级复杂度；Ambient 等模式改变数据面部署方式，也仍需策略、性能和故障治理。

Service Mesh 不解决业务幂等、事务语义、数据一致性和领域边界。

## 十三、弱网与离线同步

移动端或边缘场景需要：

- 本地持久队列和同步状态；
- 唯一请求 ID 与幂等；
- 版本向量、时间戳或业务版本；
- 冲突检测和合并策略；
- 增量同步、断点续传和退避；
- 敏感数据加密、过期和远程擦除；
- 失败操作可观察并允许人工处理。

“最后写入获胜”简单但可能丢失有效修改。订单、库存和审批等业务应通过状态机、服务端仲裁或领域补偿解决冲突。

## 十四、Serverless

Serverless/FaaS 适合事件触发、间歇负载和短时无状态处理。主要权衡：

- 冷启动和执行时限；
- 状态外置与连接管理；
- 平台限制和可移植性；
- 观测、调试和成本曲线；
- 并发扩展对数据库和外部接口的冲击。

Serverless 不等于“零运维”，运维职责从服务器转向函数、权限、事件、依赖、成本和 SLO。

## 十五、可观测性

- Metrics：速率、错误、延迟、饱和度和业务 SLI；
- Logs：结构化事件、错误上下文和审计；
- Traces：跨服务调用、关键路径和依赖延迟；
- Profiles：CPU、内存和锁竞争等持续性能证据。

Trace ID 应贯穿网关、服务、消息和异步任务。采样、隐私、成本和保留周期需要治理。

## 十六、案例答题框架

### 16.1 微服务迁移

```text
识别业务边界和现有单体问题
→ 选择先拆模块还是拆服务
→ 明确数据所有权和事务边界
→ 通过 Strangler 等方式渐进迁移
→ 建立网关、发现、配置和可观测性
→ 处理跨服务一致性、幂等和补偿
→ 灰度发布并验证业务 SLO
```

### 16.2 云原生改造

```text
容器化与不可变制品
→ 声明式部署和资源治理
→ 三类探针和优雅终止
→ 弹性指标与下游容量预算
→ 灰度、回滚和供应链安全
→ 指标、日志、链路和恢复演练
```

### 16.3 API 设计

```text
资源与操作语义
→ HTTP 方法和状态码
→ 认证、授权和幂等
→ 分页、错误和版本
→ 限流、超时和可观测性
```

## 十七、考场检查

- [ ] 是否避免把架构演进写成单向必经路线
- [ ] 是否从业务边界、数据和事务拆分微服务
- [ ] OAuth 是否作为授权框架，认证是否使用 OIDC 等身份协议
- [ ] JWT 是否校验签名、Issuer、Audience、过期和权限
- [ ] Ingress 是否区分资源与 Controller
- [ ] Secret 是否说明静态加密和 RBAC
- [ ] 是否区分 Startup、Readiness 和 Liveness
- [ ] HPA 是否考虑自定义指标和下游容量
- [ ] Service Mesh 是否说明资源和运维代价
- [ ] REST 是否正确说明幂等和状态码
- [ ] 弱网是否包含冲突、幂等、补偿和人工兜底

## 十八、核验依据

- Kubernetes 官方 Ingress、Ingress Controller、Secret、Probe 和 HPA 文档；
- IETF RFC 6749 OAuth 2.0 Authorization Framework；
- OpenID Connect Core 1.0；
- IETF RFC 9110 HTTP Semantics；
- Istio 官方 Sidecar 与 Ambient 数据面资料；
- 当前仓库微服务、云原生和安全论文专题技术校准结果。
