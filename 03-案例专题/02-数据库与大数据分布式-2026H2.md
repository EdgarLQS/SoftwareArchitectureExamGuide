# 专题二：数据库、分布式数据与大数据架构

> 本文是当前复习版本。历史长文 [`02-数据库与大数据分布式.md`](./02-数据库与大数据分布式.md) 保留旧例题和素材，但其中固定阈值、锁机制、CAP、Redis 和流批架构结论不再作为默认口径。

## 一、数据库设计基础

### 1.1 E-R 模型

| 元素 | 含义 | 常用表示 |
|------|------|----------|
| 实体 | 可独立识别的对象或概念 | 矩形 |
| 属性 | 实体或联系的特征 | 椭圆 |
| 联系 | 实体之间的业务关系 | 菱形 |

联系基数常见为 1:1、1:N 和 M:N。把 E-R 模型转换为关系模型时，需要明确主键、外键、可空性、唯一约束和联系表。

### 1.2 函数依赖与范式

| 范式 | 核心要求 | 主要避免的问题 |
|------|----------|----------------|
| 1NF | 关系属性在当前数据模型中保持原子性 | 重复组和嵌套集合 |
| 2NF | 满足 1NF，非主属性完全依赖每个候选码 | 对复合码的部分依赖 |
| 3NF | 满足 2NF，非主属性不通过其他非主属性传递依赖候选码 | 传递依赖 |
| BCNF | 对每个非平凡函数依赖 `X → Y`，决定因素 X 都是超码 | 3NF 仍可能保留的异常依赖 |

BCNF 不能简化为“消除主属性对码的部分和传递依赖”。判断时应从函数依赖和候选码出发。

### 1.3 反规范化

反规范化是为了特定查询和服务目标有意识地引入冗余、派生列、宽表或预聚合。使用前应回答：

- 哪个查询或链路需要优化；
- 冗余数据由谁维护；
- 更新失败如何补偿；
- 如何对账和重建；
- 是否可用物化视图、索引或缓存替代。

不能把“分布式 Join”一律替换成宽表。跨节点关联是否可接受取决于数据量、分布、选择性、执行引擎和查询频率。

## 二、OLTP、OLAP 与 HTAP

| 类型 | 主要负载 | 典型目标 | 常见设计 |
|------|----------|----------|----------|
| OLTP | 高频短事务、点查和更新 | 正确性、低延迟、并发与恢复 | 行存、索引、事务和约束 |
| OLAP | 大扫描、聚合和多维分析 | 扫描吞吐、压缩和并行 | 列存、分区、预聚合和向量化 |
| HTAP | 同时服务事务与近实时分析 | 减少数据复制延迟并隔离负载 | 行列副本、日志复制或混合引擎 |

HTAP 不是“一套系统自动解决全部问题”。仍需评估事务与分析资源隔离、数据新鲜度、成本和故障域。

ETL/ELT、CDC 和流式同步都是数据从事务系统进入分析系统的方式。选择依据包括时效、重算、源库压力、Schema 变化和数据治理，不能把某一产品写成唯一趋势。

## 三、查询与索引优化

推荐证据链：

```text
业务 SLO 和负载模型
→ 慢查询与调用链证据
→ EXPLAIN/执行计划
→ 扫描行数、选择性和锁等待
→ 索引或 SQL 修改
→ 同负载复测
```

### 3.1 索引

- 联合索引列顺序应结合等值、范围、排序和选择性；
- 覆盖索引减少回表，但会增加写放大和存储；
- 过多索引影响写入、页分裂和维护；
- 函数、隐式转换和不匹配的数据类型可能影响索引使用；
- “减少 Join”不是通用优化规则，正确索引和合理 Join 往往优于应用层多次查询。

### 3.2 分区与分片

数据库分区通常在一个逻辑表或数据库内按范围、列表、哈希等方式组织数据；分片把数据分布到多个独立节点或库。

分片设计必须讨论：

- 分片键和查询路由；
- 热点与数据倾斜；
- 跨分片查询和聚合；
- 全局唯一标识；
- 扩容、迁移和回滚；
- 事务、一致性和对账；
- 运维与成本。

全局 ID 可以使用数据库序列、分段号段、时间有序 ID、UUID 或雪花类算法。选型要考虑趋势递增、时钟回拨、碰撞、信息泄露和多机房。

## 四、事务、隔离与锁

### 4.1 ACID

- 原子性：事务中的操作整体成功或回滚；
- 一致性：事务把数据库从满足约束的状态带到另一个满足约束的状态；
- 隔离性：并发事务的中间状态按隔离级别受控；
- 持久性：已提交结果在系统承诺的故障模型下可恢复。

一致性不是数据库引擎单独完成的，业务约束、唯一键、检查约束、应用状态机和外部系统也参与保证。

### 4.2 隔离级别与并发现象

| 隔离级别 | 主要目标 | 仍需关注 |
|----------|----------|----------|
| Read Uncommitted | 最低隔离 | 脏读及更多异常 |
| Read Committed | 每次语句读取已提交版本 | 不可重复读、写偏差等 |
| Repeatable Read | 事务内重复读取保持稳定视图 | 实现差异、幻读和写冲突 |
| Serializable | 效果等价于某个串行顺序 | 冲突、阻塞或事务重试 |

不同数据库通过锁、MVCC、SSI 等机制实现隔离，不能只背名称而忽略产品语义。

### 4.3 悲观并发控制

`SELECT ... FOR UPDATE` 等语句对匹配记录加锁。是否锁行、间隙或更大范围取决于数据库产品、索引、执行计划和隔离级别。

必须修正：InnoDB 不存在“WHERE 未使用索引就自动升级为表锁”的通用规则。无合适索引可能扫描并锁住大量记录或间隙，表现得像大范围阻塞，但不能直接等同于表级锁升级。

悲观方案适合冲突高、临界区短且失败重试代价大的操作，但仍需固定加锁顺序、缩短事务和处理死锁重试。

### 4.4 乐观并发控制

常用模式：

```sql
UPDATE item
SET value = :new_value, version = version + 1
WHERE id = :id AND version = :old_version;
```

影响行数为 0 表示版本冲突，由业务决定重读、合并或失败。乐观控制不等于数据库完全不加锁；SQL 更新执行期间仍可能获取锁，也不能承诺永不死锁。

选型不能简化为“读多写少一定乐观、写多读少一定悲观”，应根据冲突概率、临界区长度、重试成本、吞吐和用户体验决定。

### 4.5 数据库协调与分布式锁

数据库唯一约束、条件更新、行锁、租约表和 Advisory Lock 在许多场景下可以作为协调机制。不能统一写成“生产环境不推荐数据库锁，必须使用 Redis 或 ZooKeeper”。

选择依据：

- 锁保护的资源是否就在数据库；
- 是否需要跨数据库和跨服务；
- 租约、会话和故障恢复语义；
- 是否需要 fencing token；
- 一致性要求和吞吐；
- 运维复杂度。

Redis 锁的当前安全边界见[Redis 当前指南](../01-知识点/03-Redis%20专题-2026H2.md)。

## 五、跨服务事务与一致性

### 5.1 优先缩小事务边界

```text
业务边界和数据所有权
→ 单服务本地事务
→ 必要时可靠事件
→ 幂等、补偿和对账
```

分布式事务不是所有跨服务流程的默认方案。应先检查服务是否拆分过细、数据是否由多个服务共同写入、能否通过状态机和业务流程拆解。

### 5.2 常见方案

| 方案 | 适用场景 | 主要代价 |
|------|----------|----------|
| XA/2PC | 参与者支持协议、强原子提交需求 | 阻塞、协调者、可用性和运维复杂度 |
| TCC | 可明确 Try/Confirm/Cancel 的业务资源 | 侵入业务、悬挂、空回滚和幂等 |
| Saga | 长事务、可定义补偿的业务流程 | 中间状态可见、补偿不一定完全逆转 |
| Transactional Outbox | 本地事务后可靠发布事件 | 消息转发、重复、清理和监控 |
| 幂等 + 对账 | 可接受最终收敛的业务 | 需要状态机、重复检测和人工兜底 |

Outbox 的业务数据和事件记录必须在同一个本地事务和同一事务资源中提交；把消息表物理分到另一个数据库会失去该原子性。

## 六、CAP、BASE、PACELC 与共识

### 6.1 CAP

CAP 不能背成平时任意“三选二”。更准确的答题方式：

- 在异步网络模型中发生分区时，系统不能同时保证线性一致性和每个请求都得到非错误响应；
- 对真实分布式系统，网络分区是必须考虑的故障，关键是在分区期间选择拒绝/等待部分操作，还是允许不同副本继续响应并接受不一致；
- 分区恢复后还需要冲突检测、合并、回放和对账。

“CP 场景就选 Raft、AP 场景就选最终一致”过于简化。Raft 是复制状态机的共识算法，适合实现特定一致性和故障模型，但业务系统仍需处理客户端重试、重复命令、成员变更、快照和不可用窗口。

### 6.2 BASE

BASE 描述基本可用、软状态和最终一致的设计思想，但不表示所有社交或电商系统都应牺牲强一致。订单金额、库存、余额和用户展示数据可以采用不同一致性等级。

### 6.3 PACELC

PACELC 提醒：即使没有网络分区，系统也常在延迟和一致性之间权衡。答题时可用于跨地域复制、同步写确认和就近读取，但不要把它当作具体协议。

### 6.4 共识

多数派确认只是共识实现的一部分。完整讨论还包括：

- 领导者选举和任期；
- 日志复制和提交规则；
- 节点崩溃和网络分区；
- 成员变更和快照；
- 客户端重试与幂等；
- 状态机命令的确定性。

## 七、NoSQL 选型

| 类型 | 典型能力 | 合适场景 | 主要限制 |
|------|----------|----------|----------|
| Key-Value | 按 Key 快速访问、原子命令 | 缓存、会话、计数和实时状态 | 查询模型受限、二级索引能力因产品而异 |
| 文档 | 嵌套文档和灵活 Schema | 内容、商品属性和聚合对象 | 跨文档事务、Schema 演进和索引成本 |
| 宽列/列族 | 分区键、稀疏宽表和高写吞吐 | 时序、轨迹和大规模分区数据 | 查询需围绕分区键建模 |
| 图数据库 | 顶点、边和路径遍历 | 关系网络、风控和知识图谱 | 超级节点、分布式遍历和写入治理 |
| 搜索引擎 | 倒排索引、全文和聚合 | 检索、日志和分析 | 不是所有业务的主事务数据库 |

不能宣称图数据库多跳查询是常数时间，也不能说关系数据库 Join 必然指数下降。性能取决于数据模型、索引、选择性、分布和查询计划。

“Schema-less”更准确地理解为 Schema 灵活或由应用/数据治理控制，不表示没有 Schema、验证和版本管理。

## 八、缓存与 Redis

数据库专题不再重复维护一套 Redis 全文。当前统一使用：

- [Redis 与缓存架构当前复习指南](../01-知识点/03-Redis%20专题-2026H2.md)
- [Redis 历史长文核验说明](../01-知识点/03-Redis%20专题-核验说明.md)

关键口径：

- Cache-Aside 写入数据库提交后删除缓存；
- Binlog 驱动失效是异步最终一致；
- Redis Cluster 使用 16384 个 Hash Slot，不等同一致性哈希环；
- 分布式锁需要 token、租约、安全释放和业务兜底；
- 缓存不替代数据库事务、约束和对账。

## 九、Lambda、Kappa 与流批统一

### 9.1 Lambda

Lambda 通常同时维护批处理路径和低延迟流处理路径，并在服务层合并结果。优势是可用批处理重算和校正，代价是两套链路、代码和口径容易分叉。

### 9.2 Kappa

Kappa 使用日志作为事实来源，主要通过流式处理链路消费实时或重放历史事件。它并非“不适合批处理”：历史数据可以通过日志重放或有界输入处理；真正限制是日志保留、重放成本、外部数据补入、算法是否适合增量化以及状态规模。

### 9.3 流批统一

现代处理引擎可以对有界和无界数据提供统一 API 或执行模型。Flink 明确支持有界和无界数据，批执行与流执行在调度、状态和恢复机制上仍有差异。不能把“统一 API”写成所有运行语义完全相同。

### 9.4 湖仓

湖仓表格式提供快照、事务、Schema 演进和多引擎访问能力，但不会自动解决：

- 上游语义冲突；
- 实时和批处理口径不一致；
- 数据质量与血缘；
- 小文件、分区和成本；
- 权限和隐私。

## 十、流处理关键问题

### 10.1 事件时间与 Watermark

Watermark 表示系统对事件时间进度的估计，用于决定窗口何时可以计算。它在延迟和结果完整性之间权衡。迟到数据需要允许延迟、侧输出、更新结果或批量校正策略。

### 10.2 Exactly-Once

Checkpoint 只能为计算状态恢复提供基础，不能单独证明端到端 Exactly-Once。完整链路要求：

- 可重放或事务型 Source；
- 一致的状态快照；
- 支持事务或幂等提交的 Sink；
- 外部副作用和客户端重试可控。

### 10.3 背压

背压表示下游消费能力低于上游生产能力。治理顺序：

```text
定位慢算子或外部 Sink
→ 检查数据倾斜和序列化
→ 调整并行度和分区
→ 优化 I/O、批量和连接池
→ 再评估 Checkpoint 和缓冲参数
```

不能只靠增加 Kafka 缓冲、关闭对齐或限流掩盖根因。

### 10.4 数据倾斜

- 检查 Key 分布和热点实体；
- 使用局部聚合、加盐和两阶段聚合；
- 拆分超级节点或热点 Key；
- 评估重分区成本和最终聚合正确性。

## 十一、数据迁移

零停机迁移不是固定四步，而是一个需要验证和回滚的流程：

```text
盘点数据和依赖
→ 建立目标 Schema 与校验规则
→ 全量复制
→ 增量同步
→ 影子读或双读校验
→ 小流量切换
→ 观察与回滚
→ 停止旧写入并收尾对账
```

双写可能部分成功，应优先使用数据库日志、Outbox 或可恢复同步链路，并设置校验、补偿和回滚。

## 十二、案例答题框架

```text
1. 明确数据模型、事务和查询负载
2. 识别一致性、延迟、吞吐和恢复目标
3. 找到瓶颈证据或故障路径
4. 比较候选数据库、分片和同步方案
5. 说明事务、幂等、补偿和对账
6. 说明扩容、迁移、安全和成本
7. 给出可验证指标和回滚方案
```

## 十三、考场检查

- [ ] BCNF 是否从决定因素和超码定义
- [ ] 是否避免“无索引自动升级表锁”的错误
- [ ] 是否避免“乐观锁绝不死锁”
- [ ] 是否按业务冲突和重试成本选择并发控制
- [ ] CAP 是否说明分区期间 C/A 权衡
- [ ] Outbox 是否保持同一事务资源
- [ ] NoSQL 是否按查询模型选择而不是只背产品名
- [ ] 是否避免图数据库恒定时间等绝对结论
- [ ] Kappa 是否说明日志重放和有界数据
- [ ] Exactly-Once 是否覆盖 Source、状态和 Sink
- [ ] 数据迁移是否包含校验、回滚和对账
