# 04 图数据库、爬虫与异步 I/O

## 1. 为什么常用图数据库

医药、社交、风控等场景通常具有实体类型多、关系复杂、需要多跳遍历的特点。图数据库使用节点、关系和属性直接表达关系网络，适合围绕关系进行查询。

## 2. 图数据库与关系数据库

| 维度 | 关系数据库 | 图数据库 |
|------|------------|----------|
| 模型 | 表、行、列 | 节点、关系、属性 |
| 关系表达 | 外键和 JOIN | 原生边和路径 |
| 多跳查询 | 需要组合 JOIN | 直接遍历关系 |
| Schema | 通常较严格 | 取决于实现，可较灵活 |
| 强项 | 事务、聚合、成熟 SQL 生态 | 关系网络、路径、邻域分析 |
| 风险 | 多跳模型复杂时查询维护成本高 | 超大规模、强事务、批量聚合不一定占优 |

不要写“图数据库多跳查询性能恒定”。正确答案是：图遍历避免了把每一跳都显式展开为大量 JOIN，但实际性能仍受数据规模、度数、索引、查询模式、分片和实现影响。

## 3. 医药知识图谱选型答题模板

```text
应优先考虑图数据库或 RDF 三元组库，具体取决于系统的查询和语义要求。

医药数据包含药品、疾病、症状、科室和医生等多种实体，实体之间存在治疗、禁忌、属于、位于等复杂关系。图模型能够直接表示节点和边，便于进行多跳关系查询、路径分析和关联推荐。若系统强调 W3C 语义标准和 OWL 本体推理，可选择 RDF 三元组库；若强调应用开发、图遍历和属性查询，可选择属性图数据库。
```

## 4. 爬虫架构

```text
URL 调度器 → 网页下载器 → 内容解析器 → 数据存储器
      ↑              │             │
      └── URL 去重 ──┘             └── 候选实体/关系
```

| 组件 | 责任 |
|------|------|
| URL 调度器 | 管理待抓取 URL、优先级和抓取策略 |
| URL 去重 | 判断 URL 是否已经处理，减少重复抓取 |
| 网页下载器 | 发出 HTTP 请求，获取页面或接口响应 |
| 内容解析器 | 从 HTML、JSON 或 XML 中提取结构化内容 |
| 数据存储器 | 保存原文、元数据和待抽取内容 |

工程上还需要考虑 robots 规则、访问频率、重试、超时、代理、编码、动态页面、失败队列和数据来源审计。

## 5. 异步 I/O

异步 I/O 的核心不是“自动多线程”，而是：发起 I/O 请求后不阻塞等待，任务可以先让出执行权，待 I/O 完成后再处理结果。

```text
同步：请求 A → 等待 A → 处理 A → 请求 B → 等待 B
异步：请求 A → 请求 B → 请求 C → 谁先完成谁先处理
```

适合网页下载、网络请求和数据库访问等 I/O 密集型场景。主要收益是减少等待造成的空闲、提高并发请求能力和网络吞吐；代价是代码控制流、超时、异常和资源限制更复杂。
