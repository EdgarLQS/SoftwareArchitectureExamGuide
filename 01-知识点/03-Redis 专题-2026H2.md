# Redis 与缓存架构当前复习指南

> 本文是 `2026-H2` 当前复习版本。历史长文 [`03-Redis 专题.md`](./03-Redis%20专题.md) 继续保留命令和例题素材，但技术结论以本文及[核验说明](./03-Redis%20专题-核验说明.md)为准。

## 一、Redis 的定位

Redis 是内存型数据结构服务器，可用于缓存、会话、计数、排行榜、消息流、限流和部分实时数据场景。是否把 Redis 作为主数据存储，需要根据持久化、复制、故障恢复和一致性要求单独评估。

不能背诵固定吞吐量。Redis 性能取决于命令复杂度、Value 大小、Pipeline、网络、CPU、持久化、拓扑和客户端模型，应通过目标负载下的压测得到容量结论。

## 二、执行模型

- 核心命令处理主要通过事件循环串行执行，使单条命令具备原子执行语义；
- 网络 I/O、持久化、异步释放、复制和模块可能使用线程或子进程；
- “单线程”不代表不会阻塞，慢命令、大 Key、Lua、Fork、磁盘和网络都可能造成延迟；
- 设计时应关注 P99、事件循环延迟、慢查询、命令复杂度和客户端排队。

## 三、数据类型与常用场景

传统考试高频类型：

| 类型 | 核心语义 | 典型场景 |
|------|----------|----------|
| String | 字节序列、计数和原子修改 | 缓存、计数、令牌、状态 |
| Hash | 字段集合 | 对象属性、购物车 |
| List | 有序序列、两端操作 | 简单队列、时间线 |
| Set | 无序去重集合 | 标签、关系、集合运算 |
| Sorted Set | 按 Score 排序的唯一成员 | 排行榜、延迟任务索引 |
| Stream | 可持久消费的消息流 | 事件、消费组、任务流 |

当前官方文档还包含 Bitmap、Bitfield、Geospatial、HyperLogLog、JSON、Time series、Vector sets 和其他概率型结构。考试答题必须结合题目与教材版本，不能固定写成“Redis 永远只有五种数据类型”。

### 3.1 复杂度意识

- `GET`、`SET` 等通常是常数级操作，但网络和 Value 大小仍影响延迟；
- `KEYS`、大范围集合操作、超大 `HGETALL` 和长 Lua 可能阻塞事件循环；
- 集合交并差、排序和范围查询要结合元素数量分析；
- 生产环境优先使用渐进扫描、分页和容量限制。

## 四、持久化

| 方案 | 机制 | 优点 | 主要风险 |
|------|------|------|----------|
| RDB | 周期性快照 | 文件紧凑、恢复较快 | 快照间隔内数据可能丢失，Fork/COW 有资源影响 |
| AOF | 记录写命令并重放 | 数据恢复窗口通常更小 | 文件增长、重写和 fsync 带来开销 |
| RDB + AOF | 同时启用 | 兼顾恢复速度和数据完整度 | 运维、磁盘和恢复流程更复杂 |
| 无持久化 | 仅使用内存 | 简单、适合可重建缓存 | 节点重启后数据消失 |

选择依据：

```text
数据能否重建
→ 可接受的数据丢失窗口 RPO
→ 可接受恢复时间 RTO
→ Fork、磁盘和内存预算
→ 是否有副本、备份与恢复演练
```

`appendfsync everysec` 只能描述典型同步策略，不能承诺任意故障下严格只丢一秒；`always` 也不能替代存储可靠性、备份和恢复演练。

## 五、复制、Sentinel 与 Cluster

### 5.1 主从复制

- 主节点把写命令异步传播到副本；
- 初次同步或无法部分同步时需要全量同步；
- 短时断线可根据 replication ID、偏移量和复制积压缓冲区尝试部分同步；
- 副本读取可能陈旧，故障转移可能丢失尚未传播的写入；
- 读己之写可以路由主节点、等待复制确认或采用会话策略，但会增加延迟或降低可用性。

### 5.2 Sentinel

Sentinel 提供监控、主观/客观下线判断、领导者选举、故障转移和客户端发现新主节点。它不是无条件强一致方案，仍需考虑：

- Sentinel 数量和 quorum；
- 主从跨故障域部署；
- 客户端重连和拓扑刷新；
- 异步复制的数据丢失窗口；
- 脑裂期间旧主节点的写入限制；
- 定期故障演练。

### 5.3 Redis Cluster

Redis Cluster 使用 **16384 个 Hash Slot**：

```text
slot = CRC16(key) mod 16384
```

每个主节点负责一部分槽，扩缩容通过迁移槽完成。Redis Cluster **不使用一致性哈希环**，两者不能混写。

Cluster 答题要点：

- Cluster-aware 客户端维护槽到节点映射；
- `MOVED` 表示稳定重定向，迁移期间可能出现 `ASK`；
- 多 Key 命令通常要求 Key 在同一槽；
- Hash Tag 可让相关 Key 映射到同一槽；
- 少数节点故障时可自动切换，但多数主节点不可用时集群可能停止服务；
- 跨槽事务、一致性、热点槽和大 Key 仍需治理。

## 六、缓存模式

### 6.1 Cache-Aside

当前默认答题流程：

```text
读：查缓存
→ 命中则返回
→ 未命中查数据库
→ 回填缓存并设置合理 TTL

写：更新数据库并提交
→ 删除缓存
```

删除失败需要重试或通过消息/Binlog 补偿。高一致性场景还要考虑并发读把旧值回填、写后读、副本延迟和缓存重建顺序。

### 6.2 Read/Write Through

应用只访问缓存抽象，由缓存层负责数据加载和写入数据源。Redis 本身不是完整的数据库透明代理，通常需要框架或自研封装。

### 6.3 Write-Behind

先写缓存或队列，再异步批量写入数据库。写吞吐较高，但需要可靠日志、重试、幂等、顺序、积压监控和数据恢复，不应只写“性能高但可能丢失”。

## 七、穿透、击穿与雪崩

| 问题 | 本质 | 主要方案 |
|------|------|----------|
| 穿透 | 查询不存在数据，缓存无法保护后端 | 鉴权、限流、布隆过滤器、空值缓存 |
| 击穿 | 热点 Key 失效后大量请求并发重建 | 单飞、带租约互斥锁、逻辑过期、提前刷新 |
| 雪崩 | 大量 Key 同时失效或缓存整体不可用 | 随机 TTL、多级缓存、限流降级、后端保护和高可用 |

### 7.1 布隆过滤器

- `BF.*` 命令通常依赖 Redis 概率型数据能力或相应组件，使用前确认部署版本；
- 标准 Bloom Filter 有假阳性，在正确使用且不删除元素时没有假阴性；
- 容量和误判率必须按预计元素数量设计；
- 判断“可能存在”后仍要查询缓存或数据源；
- 新增、删除、重建和故障恢复必须纳入数据同步流程。

### 7.2 热点重建锁

单实例锁的基本模式：

```text
SET lock-key unique-token NX PX lease-time
→ 获得锁的请求加载数据并回填缓存
→ 解锁时比较 token 后删除
```

不能使用无过期时间的 `SETNX`，也不能直接 `DEL`，否则可能死锁或误删其他持有者的锁。等待方应设置超时、退避和最大重试次数。

## 八、缓存一致性

缓存通常是主数据的派生副本，一致性目标应先按业务分类：

| 场景 | 允许的陈旧窗口 | 常见方案 |
|------|----------------|----------|
| 商品详情、字典 | 秒级或分钟级 | Cache-Aside + TTL + 删除重试 |
| 用户刚修改后立即查看 | 读己之写 | 删除缓存后主库读或会话粘滞 |
| 库存、余额、订单状态 | 极低容忍 | 数据库约束/事务为准，缓存只加速读取 |
| 热点展示数据 | 可返回旧值 | 逻辑过期和异步刷新 |

必须纠正：

- Binlog 驱动删除缓存通常是异步最终一致，不是强一致；
- 应用同时写数据库和缓存可能部分成功，不是天然“最强一致”；
- 逻辑过期明确允许返回陈旧值；
- 互斥重建只能控制并发加载，不能自动解决所有数据库与缓存一致性问题。

## 九、分布式锁

锁的完整答题结构：

```text
唯一 token
+ NX 获取
+ 有限租约
+ 比较 token 后释放
+ 必要时续租
+ 超时和随机退避
+ 业务幂等
+ fencing token 或数据库约束兜底
```

Redis 主从复制是异步的，基于故障转移的锁可能在主节点写入尚未复制时发生互斥失效。正确性要求非常高的场景，应评估共识型协调服务、数据库锁/约束或带 fencing token 的资源控制。

## 十、热点 Key、大 Key 与内存治理

### 10.1 热点 Key

- 识别请求频率和带宽热点；
- 使用本地缓存、读副本、Key 拆分或请求合并；
- 防止单槽和单节点成为瓶颈；
- 热点复制后仍需解决失效广播和一致性。

### 10.2 大 Key

风险包括网络阻塞、删除延迟、复制放大、迁移困难和内存抖动。治理方式：

- 设定 Value、集合元素数和单次返回上限；
- 拆分大集合；
- 使用渐进删除或异步释放；
- 禁止无边界 `HGETALL`、`SMEMBERS` 和大范围查询；
- 监控慢命令、带宽和内存碎片。

### 10.3 淘汰策略

选择淘汰策略前先确认 Redis 是纯缓存还是混合数据存储。业务不能依赖淘汰策略保护必须持久保存的数据；关键数据应放在具备明确持久性和恢复机制的数据源中。

## 十一、库存防超卖

Redis 预扣只负责高并发入口控制，最终正确性还需要业务链路：

```text
Lua 原子校验并预扣
→ 唯一请求标识
→ 可靠消息创建订单
→ 数据库唯一约束和条件更新
→ 超时取消与库存补偿
→ 对账修复
```

不要使用固定 QPS 决定方案。选择依据包括热点程度、库存规模、订单持久性、失败补偿、支付超时和业务一致性要求。

## 十二、监控与容量

关键指标：

- 命令吞吐、P50/P95/P99 延迟；
- 事件循环延迟和慢日志；
- 内存使用、碎片率、淘汰和过期；
- Keyspace 命中率，但不能脱离业务判断；
- 客户端连接、阻塞客户端和网络带宽；
- 主从延迟、积压缓冲区和全量同步次数；
- Cluster 槽分布、热点槽、故障转移和重定向；
- RDB/AOF 状态、Fork 时间和恢复演练结果。

容量评估必须基于数据量、Value 分布、读写比例、峰值模型、持久化和故障降级场景。

## 十三、案例答题骨架

```text
1. 定义问题：穿透/击穿/雪崩/一致性/扩容/高可用
2. 说明原因：并发时序、失效机制、拓扑或容量瓶颈
3. 给出主方案：流程和关键命令
4. 补充异常路径：超时、失败、重试、幂等和补偿
5. 说明权衡：一致性、可用性、性能和成本
6. 给出可验证指标：延迟、命中率、数据库压力、复制延迟和错误率
```

- [ ] 是否避免固定“只有五种数据类型”
