# 缓存模式与一致性

> 目标：看到缓存题时，先判断数据来源、读写路径、一致性要求和故障边界。

## 一、Cache-Aside 旁路缓存

### 读流程

```text
请求 → Redis
       ├─ 命中 → 返回缓存
       └─ 未命中 → 查询数据库 → 写入 Redis（TTL）→ 返回
```

### 写流程

```text
请求更新 → 更新数据库成功 → 删除缓存 → 返回
```

通常优先“更新数据库，再删除缓存”，因为缓存是派生数据；直接更新缓存会增加并发覆盖和双写失败的复杂度。若题目要求更强的准实时一致性，可补充 Binlog/消息异步失效、延迟双删或版本号校验，但必须写清它们仍有延迟和失败重试边界。

## 二、三大缓存问题

| 问题 | 现象 | 主要原因 | 方案 | 代价 |
|---|---|---|---|---|
| 穿透 | 查询不存在的数据反复打到数据库 | 缓存和数据库都没有该 Key | Bloom Filter + 空值缓存 + 参数校验 | 假阳性、空值 TTL 管理 |
| 击穿 | 一个热点 Key 失效，瞬时大量回源 | 热点 Key 同时失效 | 互斥锁、逻辑过期、提前刷新 | 锁等待或短暂返回旧数据 |
| 雪崩 | 大量请求同时回源或 Redis 故障 | TTL 同时到期、节点不可用 | TTL 随机化、分批预热、限流降级、Sentinel/Cluster | 复杂度、可能牺牲实时性 |

判断口诀：穿透是“查不存在”，击穿是“热点过期”，雪崩是“大量同时失效或缓存整体不可用”。

## 三、缓存一致性取舍

| 方案 | 写入路径 | 一致性 | 适用场景 | 主要风险 |
|---|---|---|---|---|
| Cache-Aside | 写 DB，删缓存 | 最终一致 | 通用读多写少 | 删除失败、并发读旧值 |
| 同步双写 | DB 和缓存都写 | 理论上更强 | 数据量小、强约束场景 | 双写失败、事务复杂 |
| 延迟双删 | 先删，写 DB，延迟再删 | 减少并发窗口 | 旧值覆盖风险较高 | 延迟任务丢失、时间难设 |
| Binlog 异步 | DB 提交后消费变更 | 最终一致 | 读多写少、可容忍延迟 | 消息积压、重复消费 |
| 逻辑过期 | 永不过期，值内带过期时间 | 允许读旧 | 热点读、不能阻塞 | 内存长期占用、数据短暂陈旧 |

答题时不要直接说“保证强一致”。应说明 Redis、数据库和消息链路中的哪个窗口仍可能出现旧值，以及用重试、版本号、幂等和监控如何收敛问题。

## 四、缓存 Key 设计

- 使用业务前缀和版本：`product:v1:{id}`，避免不同业务互相覆盖。
- 控制 Value 大小，避免把不需要的字段全部塞进缓存。
- TTL 采用业务可接受的有效期，并加入随机偏移分散失效时间。
- 对空值设置较短 TTL，避免恶意或错误请求长期占用空间。
- Cluster 场景需要多 Key 原子操作时，使用合理的 hash tag，并评估热点集中风险。

## 五、案例作答模板

```text
先读 Redis，命中直接返回；未命中查询数据库并回写带随机 TTL 的缓存。
更新时先提交数据库，再删除缓存；删除失败进入重试或消息补偿。
不存在数据用参数校验、布隆过滤器和短 TTL 空值缓存防穿透。
热点 Key 用互斥锁单飞或逻辑过期异步刷新防击穿。
大量 Key 失效或 Redis 故障时通过随机 TTL、限流、降级和高可用集群防雪崩。
同时监控命中率、回源 QPS、延迟、错误率、热 Key 和补偿积压。
```

## 六、练习

1. 商品详情读多写少，但价格修改后必须尽快生效：选择什么缓存策略？为什么？
2. 热门商品缓存过期时不能让用户等待数据库：选择物理过期互斥锁还是逻辑过期？说明取舍。
3. 黑客随机查询不存在的商品 ID：至少给出三层防护，并说明 Bloom Filter 的假阳性。
4. Redis 整体不可用：从限流、降级、数据库保护、恢复预热四个角度写处理流程。
