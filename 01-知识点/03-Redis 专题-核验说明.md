## 二、必须修正的基础表述

### 2.1 性能数字

“10 万 QPS”“5000 QPS”“数据库低于 100 QPS”等数字不能作为通用结论。吞吐量取决于：

- 命令复杂度、Value 大小和 Pipeline；
- 网络、CPU、内存带宽和持久化配置；
- 单机、主从或 Cluster 拓扑；
- 客户端连接方式和测试模型；
- 是否存在 Lua、模块、慢查询或大 Key。

答题时应写“内存访问和事件驱动使 Redis 具备较高吞吐”，项目效果必须来自同一负载模型下的压测。

### 2.2 执行模型

Redis 不能笼统背成“所有工作都是单线程”。更准确的表述是：

- 核心命令执行长期以单线程事件循环为主要模型，便于保证单命令原子性；
- Redis 6 以后可以使用 I/O 线程处理部分网络读写；
- 持久化、释放内存、复制和模块可能涉及后台线程或子进程；
- 单线程命令执行不代表不会被慢命令、大 Key、Fork 或系统资源阻塞。

### 2.3 数据结构分类

String、List、Hash、Set、Sorted Set 是常见核心类型，但不应固定称为“Redis 永远只有五种类型”。Stream 等类型应按版本和题目范围处理；Bitmap、Geo 和 HyperLogLog 更多是基于底层类型或专用编码提供的能力，不必全部称为独立核心类型。

## 三、分布式锁

原文中仅使用 `SETNX` 再 `DEL` 的示例不安全，可能出现死锁和误删其他客户端锁。

推荐答题骨架：

```text
SET lock-key unique-token NX PX lease-time
→ 业务执行
→ Lua 比较 token 后删除
→ 长任务按需要续租
→ 关键资源使用 fencing token 防止过期持有者继续写入
```

必须说明：

- 锁需要唯一所有者标识和过期时间；
- 解锁必须比较 token；
- 业务执行时间可能超过租约；
- 网络分区、进程暂停和主从切换会影响锁语义；
- 强正确性场景优先依赖数据库约束、共识系统或业务幂等，而不是只写“Redis 锁保证绝对安全”。

## 四、布隆过滤器

- `BF.ADD`、`BF.EXISTS` 通常来自 RedisBloom 模块，不是所有 Redis 安装默认具备的核心命令；
- 标准 Bloom Filter 在正确初始化且不删除元素时没有假阴性，但存在可配置的假阳性率；
- 容量估算必须考虑预计元素数和错误率，不能固定说“亿级数据只需几 MB”；
- 用于缓存穿透时，过滤器判断“可能存在”后仍需查询缓存或数据源；
- 数据新增、删除和重建需要同步治理。

## 五、持久化与复制

### 5.1 RDB 与 AOF

- `BGSAVE` 仍会产生 Fork、Copy-on-Write、内存和磁盘 I/O 影响，不能写成“完全不影响主进程”；
- `appendfsync everysec` 通常将故障窗口控制在约一秒，但不等于所有故障下严格只丢一秒；
- `appendfsync always` 增强持久性但不等于绝对不丢数据，仍受存储、文件系统和部署故障影响；
- 选型应结合 RPO、RTO、数据是否可重建和恢复演练，不使用固定“高安全必选 always”。

### 5.2 主从复制

部分同步需结合 replication ID、复制偏移量和复制积压缓冲区说明。复制是异步链路，读从库可能读到旧数据；故障转移时也可能丢失尚未传播的写入。需要强读己之写时可路由主库、使用会话策略或等待复制确认，但都需说明可用性和延迟代价。

### 5.3 Sentinel 与 Cluster

- Sentinel 提供监控和自动故障转移，但仍需多数派、客户端重连、脑裂防护和故障演练；
- Redis Cluster 使用 **16384 个 Hash Slot**，Key 通过 CRC16 映射到槽；
- Redis Cluster 的槽机制不能与客户端一致性哈希环混为同一个分片算法；
- 多 Key 操作、事务和 Lua 脚本通常要求相关 Key 位于同一槽，可使用 Hash Tag 控制。

## 六、缓存问题与一致性

### 6.1 Cache-Aside

当前默认训练口径：

```text
读：查缓存 → 未命中查数据库 → 回填缓存
写：更新数据库并提交 → 删除缓存
```

删除失败需要重试、消息或 Binlog 补偿；高一致性场景还要处理并发读回填旧值、写后读和缓存重建顺序。

### 6.2 三类问题

- 穿透：不存在的数据持续访问后端；可用布隆过滤器、空值缓存、鉴权和限流。
- 击穿：热点 Key 失效后大量请求并发重建；可用单飞、互斥重建、逻辑过期或提前刷新。
- 雪崩：大量 Key 同时失效或缓存服务整体不可用；需要随机 TTL、多级缓存、限流降级和后端保护。

原文互斥锁示例必须补充租约、所有者 token、异常释放和重试上限，不能递归无限等待。

### 6.3 一致性强度

原文将“订阅 Binlog”标为强一致、将“双写同步”标为最强一致，均不准确：

- Binlog/消息失效通常属于异步最终一致，需要重试、幂等、死信和监控；
- 应用同时写数据库和缓存可能出现部分成功，不能天然获得强一致；
- 缓存通常是派生数据，主数据一致性应由数据库事务、唯一约束、状态机和幂等控制；
- 逻辑过期明确允许返回旧值，适合可接受陈旧读取的场景；
- 互斥重建也不能简单标为“强一致”，仍可能受并发写、复制延迟和回填顺序影响。

## 七、多级缓存和数据库描述

- MySQL 查询缓存已在 MySQL 8.0 移除，不能把“数据库查询缓存”作为当前通用层级；
- 数据库 Buffer Pool 是页缓存，不等同于应用结果缓存；
- 本地缓存会引入多实例失效和容量问题，需要版本、消息失效或短 TTL；
- CDN、浏览器和 API 缓存必须结合 HTTP 缓存语义、隐私和失效策略。

## 八、防超卖

Redis 原子递减只解决单个命令的原子性，不自动保证订单最终不超卖。推荐结构：

```text
Lua 原子校验并预扣
→ 生成唯一请求或订单标识
→ 可靠消息创建订单
→ 数据库唯一约束与条件更新兜底
→ 超时取消和库存补偿
→ 对账修复
```

不能使用固定 QPS 判断方案适用范围；应根据库存规模、热点程度、失败率、持久性和业务一致性要求选择。
