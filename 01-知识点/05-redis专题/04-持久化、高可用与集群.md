# 持久化、高可用与集群

> 目标：区分“数据不丢”“服务可用”“容量可扩展”三个问题，不把 RDB、复制、Sentinel、Cluster 混为一谈。

## 一、三类能力

| 能力 | 解决的问题 | 典型机制 | 不能自动解决 |
|---|---|---|---|
| 持久化 | Redis 重启后如何恢复数据 | RDB、AOF | 不能自动保证服务无中断 |
| 复制 | 多个节点保留数据副本 | 主从/主副本复制 | 异步复制存在延迟和丢失窗口 |
| 故障转移 | 主节点故障后谁接管 | Sentinel 或 Cluster | 不能消除业务一致性问题 |
| 分片 | 单节点容量和吞吐不足 | Cluster 槽位分片 | 跨槽多 Key 操作受限制 |

## 二、RDB、AOF 和混合持久化

| 方案 | 记录方式 | 优点 | 缺点 | 典型选择 |
|---|---|---|---|---|
| RDB | 某一时刻的数据快照 | 文件紧凑、恢复快 | 两次快照间可能丢写入 | 缓存或可接受分钟级丢失 |
| AOF | 追加记录写命令 | 数据恢复点更细 | 文件较大，需要重写 | 数据安全要求更高 |
| 混合 | RDB 打底 + AOF 增量 | 兼顾恢复速度和数据完整性 | 配置与理解更复杂 | 通用业务的折中方案 |

考试比较必须带业务约束：数据是否可丢、恢复时间目标 RTO、数据恢复点目标 RPO、磁盘和 CPU 成本。

## 三、主从复制

基本流程：

1. 从节点使用 `PSYNC` 请求同步。
2. 首次或无法部分重同步时，主节点生成并发送 RDB。
3. 主节点继续把期间的写命令放入复制积压缓冲区。
4. 从节点加载快照，再执行积压的增量命令。
5. 短暂断线且偏移量仍在缓冲区时，优先部分重同步。

复制通常是异步的，因此“写主后立刻读从”可能读到旧数据。需要强一致读时，可读主、等待复制确认或采用业务侧版本/路由策略，但每种方案都有性能代价。

## 四、Sentinel 与 Cluster

| 方案 | 重点 | 适用场景 | 主要限制 |
|---|---|---|---|
| 主从 | 复制和读扩展 | 小规模、可人工切换 | 主节点仍是写瓶颈 |
| Sentinel | 监控、选主、故障转移 | 不需要分片的高可用 | 主要解决可用性，不是容量分片 |
| Cluster | 槽位分片、节点级故障转移 | 数据量和吞吐都需水平扩展 | 跨槽事务和多 Key 操作复杂 |

### Sentinel 故障转移答题链

```text
哨兵发现主节点异常
→ 主观下线与客观下线确认
→ 选举负责执行转移的哨兵
→ 从节点中选择候选者晋升
→ 重配置其他从节点
→ 通知客户端新的主节点
```

### Cluster 选型检查

- Key 通过槽位映射到分片，不是简单把所有请求广播到所有节点。
- 多 Key 原子操作需要落在同一槽位，必要时使用 hash tag，但要防止热点集中。
- 扩容不仅是增加节点，还要迁移槽位、预热数据、观察延迟和失败重试。
- Cluster 的高可用、复制和持久化仍是不同层次，必须分开描述。

## 五、故障演练题

| 故障 | 先保护什么 | 恢复动作 | 复盘指标 |
|---|---|---|---|
| Redis 进程重启 | 限制回源 QPS | 按 RDB/AOF 恢复并逐步预热 | RTO、RPO、回源峰值 |
| 主节点宕机 | 写流量和连接重试 | Sentinel/Cluster 选主 | 故障转移时间、丢写窗口 |
| 网络分区 | 防止双写和错误重试风暴 | 依据拓扑和 quorum 恢复 | 错误率、复制延迟、脑裂风险 |
| 单节点内存满 | 拒绝非关键写入或淘汰 | 调整 TTL、拆分大 Key、扩容 | used_memory、evicted_keys |
