# 分布式锁、高并发与性能

> 目标：不仅会写 `SET NX EX`，还要能说明锁的所有权、过期、释放、续期和业务一致性边界。

## 一、正确的 Redis 锁最小模型

```bash
SET lock:order:{order_id} {random_token} NX EX 10
```

获取锁必须同时完成“仅当不存在时设置”和“设置过期时间”。释放锁不能直接 `DEL`，应使用 Lua 原子校验 token 后删除：

```lua
if redis.call('GET', KEYS[1]) == ARGV[1] then
  return redis.call('DEL', KEYS[1])
end
return 0
```

| 风险 | 原因 | 防护 |
|---|---|---|
| 死锁 | 客户端崩溃后锁不释放 | 强制 TTL |
| 误删他人锁 | 锁过期后旧持有者仍执行 DEL | 唯一 token + Lua 校验 |
| 锁提前失效 | 业务执行时间超过 TTL | 合理续期、看门狗或缩短临界区 |
| 重试风暴 | 获取失败后立即自旋 | 退避、超时、限流和熔断 |
| 锁住但数据未提交 | 锁与数据库事务边界不一致 | 幂等、版本号、补偿和唯一约束兜底 |

RedLock 只作为考试中的方案比较点，不直接写成“绝对强一致”；必须根据故障模型、时钟、网络和业务风险判断是否需要 ZooKeeper、数据库约束或其他协调机制。

## 二、秒杀与防超卖

```text
客户端防重复
→ 网关限流
→ Redis 预热库存
→ Lua 原子检查库存、检查用户资格、扣减库存
→ MQ 异步创建订单
→ 数据库唯一约束和幂等消费兜底
```

单独使用 `DECR` 只能保证单条命令原子，不能同时完成“检查用户是否购买、检查库存、扣减、记录购买者”。这些动作需要放进同一个 Lua 脚本，或者采用其他明确的事务/串行化设计。

## 三、内存和热点问题

| 问题 | 识别信号 | 处理方式 |
|---|---|---|
| 大 Key | 单 Key 占用过大、单次命令延迟高 | 拆分 Hash/List、分片、分页、限制 Value |
| 热 Key | 某 Key QPS 极高、单分片负载不均 | 本地缓存、Key 拆分、复制读、请求合并 |
| 内存不足 | `used_memory` 接近上限、写失败或淘汰增多 | TTL、淘汰策略、拆分和扩容 |
| 慢命令 | `SLOWLOG` 出现长耗时命令 | 避免大范围读取、分页、异步化和数据结构调整 |
| 缓存污染 | 无效或过期不合理的数据持续占空间 | Key 规范、TTL、删除策略和容量监控 |

选择淘汰策略时先问：所有 Key 都能淘汰吗？只有带 TTL 的 Key 能淘汰吗？业务是否允许写失败？`noeviction`、`allkeys-lru`、`volatile-lru`、LFU 等策略不能脱离这些约束单独背诵。

## 四、性能分析顺序

```text
客户端超时
→ 网络连接与连接池
→ Redis 命令耗时和慢日志
→ Key 大小与命令返回量
→ 内存、淘汰、碎片和 CPU
→ 主从延迟、热点分片和回源流量
→ 数据库、MQ、应用线程池是否成为下游瓶颈
```

不要把“Redis 很快”当作结论。架构答案应给出可观测指标：命中率、P50/P95/P99 延迟、QPS、回源 QPS、连接数、内存使用、淘汰数、复制延迟、慢命令数和错误率。

## 五、练习

1. 业务执行时间不稳定，固定 10 秒锁可能过期：你如何设计续期、超时和幂等？
2. 一个 Hash 包含 500 万个字段，读取单字段仍偶发超时：从数据结构、拆分和访问方式分析。
3. Cluster 中某个商品 Key 形成热点：如何在不破坏业务查询的情况下分散请求？
4. Redis 正常但数据库被回源打满：从缓存、限流、降级和恢复预热四层设计保护方案。
