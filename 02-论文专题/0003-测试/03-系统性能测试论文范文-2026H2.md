# 系统性能测试在电商交易平台中的应用

> 本文项目背景、负载模型和量化指标均为论文训练用模拟数据。

## 摘要

本文以某电商交易平台的大促性能保障为背景，论述系统性能测试在项目中的应用。该平台日常峰值约三千 TPS，大促前业务预计峰值将超过三万 TPS。原有测试只验证单接口平均响应时间，未覆盖真实业务比例、缓存冷热、数据库数据量和依赖故障，导致系统在接近生产流量时出现 P99 超过五秒、数据库连接等待和内存持续增长等问题。作为系统架构师，我负责将业务目标转换为 SLO，组织负载模型、测试环境、数据准备、分层观测和瓶颈治理，并协调研发、测试、数据库和运维团队完成复测。项目根据历史日志构建下单、查询、支付和取消等用户旅程，依次开展基线、负载、压力、峰值、耐久和故障测试，通过指标、日志和追踪定位慢查询、缓存穿透和内存泄漏。改造后，在统一模拟条件下，系统峰值吞吐由三千 TPS 提升到三万五千 TPS，P99 降至一百五十毫秒以内，错误率降至 0.02% 以下，连续七十二小时运行未再出现持续内存增长。本文重点说明性能目标、负载模型、瓶颈证据和复测闭环。

## 一、项目背景与性能目标

平台包含商品查询、购物车、订单、支付和库存等核心业务。过去的压测脚本主要循环调用商品查询接口，数据量较小且缓存已经预热，无法代表真实交易。大促演练时，订单创建比例上升、热门商品集中、第三方支付延迟波动，系统很快出现数据库连接耗尽和超时重试放大。

我组织业务人员从用户旅程和风险定义性能目标。核心下单成功率应达到 99.9%，峰值吞吐目标为三万五千 TPS，核心接口 P99 小于两百毫秒，错误率小于 0.02%；当第三方支付延迟升高时，系统应限制重试并保留订单处理中状态；连续七十二小时运行不应出现持续内存增长。资源利用率不采用统一的 70% 阈值，而是关注吞吐停止增长、尾延迟快速上升、错误率增加和队列持续积压等饱和拐点。

## 二、负载模型与测试设计

测试团队根据生产日志和业务预测识别商品浏览、库存查询、创建订单、支付、取消和售后等关键旅程，统计请求比例、到达率、思考时间和账户分布。为了模拟大促特征，我们加入热门商品集中访问、新老用户混合、缓存冷启动和支付延迟波动，并准备接近生产规模的订单和库存数据。测试数据经过脱敏，账号与库存相互隔离，保证多轮执行能够重复。

测试分为多个层次。基线测试用于建立当前版本的可比较结果；负载测试验证预期流量下是否满足 SLO；压力测试逐步加压以发现饱和点和失败方式；峰值测试模拟流量快速上升和回落；耐久测试观察内存、连接和队列是否持续劣化；故障测试注入支付延迟、缓存节点异常和数据库只读副本故障，验证降级和恢复。不同测试名称可能存在重叠，关键是每次测试的目标、负载和停止条件明确。

测试环境在组件拓扑、限额和数据量上尽量接近生产。无法完全等价的部分，如机器规格和外部支付能力，都记录差异并通过小规模生产演练校准，而不是用简单的 1:4 比例直接推算生产容量。

## 三、分层观测与执行过程

每轮测试先完成环境和数据校验，再进行缓存与 JIT 预热，从小流量冒烟开始，随后阶梯加压并在每一级保持稳态。观测覆盖业务成功率、P50/P95/P99、吞吐、错误和超时；应用层关注 CPU、内存、GC、线程池和队列；依赖层关注数据库执行计划、锁等待、连接池、缓存命中率、消息积压和外部 API 延迟。压测机本身的 CPU、网络和连接数也纳入监控，避免把客户端瓶颈误认为服务端容量。

测试中每次只验证一个主要假设。修改索引后使用相同数据和流量复测，调整连接池时保持数据库和应用实例数不变，缓存策略变化后同时验证命中率、数据正确性和回源压力。这样能够建立技术措施与指标变化的因果关系。

## 四、关键问题与解决过程

第一个问题是慢查询。吞吐超过八千 TPS 后，订单查询 P99 快速上升，数据库 CPU 和锁等待同步增加。通过慢查询日志和执行计划发现，按用户和状态查询订单时缺少合适联合索引，部分事务还持锁过久。我们调整索引顺序、缩短事务范围并拆分不必要的大查询。连接池没有直接扩大到更大值，而是根据数据库并发能力、查询时长、应用实例数和超时预算重新计算。复测后，数据库等待明显下降。

第二个问题是缓存穿透。压测脚本和异常流量中存在大量不存在的商品编号，缓存未命中后持续访问数据库。我们增加参数和租户校验，使用布隆过滤器拦截明显无效 Key，并为确实不存在的数据设置短 TTL 空值缓存；热点 Key 使用互斥重建，普通 TTL 增加随机偏移。缓存命中率由 60% 提升到 95%，数据库负载恢复稳定。Cache-Aside 的写路径仍保持更新数据库并提交后删除缓存，避免把缓存当作权威数据源。

第三个问题是重试风暴。支付依赖延迟升高时，上游多个服务同时重试，线程和连接迅速耗尽。我们建立端到端超时预算，只对幂等且可能短暂恢复的请求进行有限重试，并使用随机退避；超过阈值后熔断，订单保持处理中状态，通过异步查询和补偿完成。故障测试表明，支付异常期间核心下单仍能受控运行，系统没有因重试放大而整体雪崩。

第四个问题是长时间内存增长。八小时耐久测试后，Full GC 频率持续增加。通过堆转储和对象增长趋势发现，一个本地缓存没有容量上限和淘汰策略。我们修复生命周期管理，设置容量和监控，并将耐久测试加入发布前基线。连续七十二小时复测未再出现持续内存增长。

## 五、结果、局限与持续性能工程

在统一模拟条件下，平台峰值吞吐由三千 TPS 提升到三万五千 TPS，P99 由五秒以上降到一百五十毫秒，错误率由 0.15% 降到 0.02% 以下，缓存命中率由 60% 提升到 95%，连续七十二小时运行没有持续内存劣化。这些结果来自负载模型、观测、数据库、缓存和故障治理的组合，而不是单一工具或一次参数调整。

性能测试仍有局限。实验环境不能完全复制生产流量和第三方依赖，业务增长也会使原有模型失效；性能提升可能增加缓存、机器或数据复制成本；过度追求吞吐可能牺牲一致性和可维护性。因此我们将关键接口基线、契约和小规模性能回归纳入流水线，发布前进行容量和耐久测试，生产中通过 SLI/SLO 和真实用户监控继续验证，并定期更新流量模型。

综上，系统性能测试不是简单增加并发并观察平均响应时间，而是从业务目标出发，建立可解释负载模型和分层观测，通过证据定位瓶颈，并在相同条件下复测。只有同时验证性能、正确性、韧性和成本，测试结果才能真正支持架构决策。
