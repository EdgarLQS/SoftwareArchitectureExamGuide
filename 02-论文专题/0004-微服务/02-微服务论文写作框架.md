# 微服务架构论文写作框架

> 本框架按题目要求组织，不再强制五段、固定字数、固定过渡句或固定“我/我们”次数。

## 一、适用题型

- 论微服务架构及其应用；
- 说明服务拆分、服务治理和数据一致性；
- 比较单体、SOA 和微服务；
- 说明微服务迁移、故障隔离和持续交付；
- 结合项目说明设计依据、实施难点和效果。

## 二、审题映射

| 题目要求 | 必须回答 |
|----------|----------|
| 核心特征 | 业务能力、独立部署、自治、数据归属和面向故障设计 |
| 服务拆分 | 领域、限界上下文、数据所有权、事务和团队能力 |
| 服务治理 | 注册、配置、网关、超时、熔断、隔离、观测和发布 |
| 数据一致性 | 强一致边界、Outbox、Saga/TCC、幂等、补偿和状态查询 |
| 项目实践 | 单体痛点、渐进迁移、具体故障、指标和不足 |

## 三、推荐结构

```text
摘要
→ 项目背景、单体痛点和本人职责
→ 微服务原则与边界设计
→ 治理、一致性和迁移策略
→ 项目实践：三组问题—决策—实施—验证
→ 效果、不足和演进
```

## 四、理论准备

### 4.1 核心特征

| 特征 | 价值 | 新增复杂度 |
|------|------|------------|
| 围绕业务能力组织 | 边界贴合领域，团队端到端负责 | 需要领域建模和协作 |
| 独立部署 | 小范围发布和回滚 | 需要自动化与兼容治理 |
| 服务自治 | 技术与数据可独立演进 | 技术栈碎片和重复建设 |
| 数据按服务归属 | 减少共享数据库耦合 | 分布式一致性与查询聚合 |
| 面向故障设计 | 隔离和降级提高韧性 | 需要监控、演练和容量治理 |
| 基础设施自动化 | 支撑大量服务持续交付 | 平台建设和运维成本 |

### 4.2 服务拆分

```text
业务目标与价值流
→ 事件风暴识别事件和命令
→ 划分子域与限界上下文
→ 明确数据所有权和事务边界
→ 分析调用、变更和故障耦合
→ 以独立部署、扩展和团队能力校验粒度
```

不要从事件数量机械推导服务数量。“两披萨团队”只能作为组织启发，不是硬规则。

### 4.3 微服务与 SOA

二者都强调服务化和松耦合。常见差异是关注重点：SOA 更常用于企业集成和服务复用，微服务更强调独立交付、团队自治和轻量通信。ESB 不必然单点，微服务也不天然高可用。

## 五、治理体系

| 能力 | 需要说明 |
|------|----------|
| API 入口 | 路由、认证、限流和版本，网关不承载复杂业务 |
| 服务发现 | 实例上下线、健康和负载策略 |
| 配置管理 | 环境隔离、权限、审计、灰度和回滚 |
| 容错 | 超时、重试预算、熔断、隔离和降级 |
| 可观测性 | Metrics、Logs、Traces、业务指标和统一关联 ID |
| 发布 | CI/CD、灰度、金丝雀、契约兼容和快速回滚 |
| 容量 | 热点服务独立扩展，同时保护数据库和外部依赖 |

只列 Nacos、Sentinel、SkyWalking 等产品名不够，应先说明架构能力和质量属性。

## 六、数据一致性

每个跨服务流程回答：

- 哪个服务拥有权威数据；
- 哪些步骤要求强一致；
- 哪些步骤允许最终一致；
- 消息如何可靠发布；
- 消费者如何幂等；
- 失败如何补偿；
- 用户如何查询处理中状态；
- 人工兜底和对账如何进行。

| 方案 | 适用场景 | 主要代价 |
|------|----------|----------|
| 本地事务 | 单服务内部 | 不能覆盖跨服务 |
| Outbox/事务消息 | 可靠发布领域事件 | 延迟、清理和重复消费 |
| Saga | 长流程、可补偿业务 | 补偿设计和中间状态 |
| TCC | 强业务控制、短链路 | 侵入性和资源预留 |
| 幂等+对账 | 可接受最终一致 | 修复延迟和运营成本 |

## 七、渐进迁移

```text
建立单体基线和依赖图
→ 选择边界清晰、变更频繁的能力
→ 使用绞杀者模式抽取
→ 建立契约测试和观测
→ 小流量灰度
→ 对比指标并扩大或回滚
→ 逐步拆分数据和组织责任
```

避免一次性重写。数据库也可以渐进分离，不要求第一天就每个服务物理独库。

## 八、项目实践框架

### 8.1 配置故障

```text
问题：多服务多环境漏配导致故障
→ 根因：配置随包发布、无版本和审计
→ 方案：集中配置、环境隔离、权限、灰度和回滚
→ 验证：变更时间、配置故障和恢复时间
```

### 8.2 循环依赖

```text
问题：订单和用户服务循环调用
→ 根因：按技术模块拆分，数据责任不清
→ 方案：重划限界上下文、明确画像能力、事件解耦
→ 验证：调用链长度、故障影响和发布耦合
```

### 8.3 跨服务一致性

```text
问题：订单成功但积分或通知失败
→ 决策：核心订单本地事务，弱感知步骤事件化
→ 实施：Outbox、幂等、重试、死信和补偿
→ 验证：一致率、积压、恢复和人工处理量
```

## 九、模拟指标口径

| 指标 | 改造前 | 改造后 |
|------|--------|--------|
| 发布频率 | 每周 1—2 次 | 每天 20+ 次 |
| 部署时间 | 30 分钟 | 少于 2 分钟 |
| 故障影响 | 可能影响全站 | 单功能隔离并降级 |
| 代码冲突 | 频繁 | 减少 90% |
| 热点服务扩容 | 随整体扩容 | 独立扩容 5 倍 |

均为训练模拟数据，应与记忆卡和范文保持一致。

## 十、摘要与总结

### 摘要

```text
项目与单体痛点
→ 微服务边界和治理方案
→ 一致性与迁移重点
→ 主要效果
→ 本文回应的题目要求
```

### 总结

```text
回扣独立交付和故障隔离目标
→ 给出验证指标
→ 说明一致性、运维和组织复杂度
→ 给出契约、平台和演进改进
```

## 十一、检查单

- [ ] 服务边界由业务能力和数据所有权驱动
- [ ] 服务粒度没有由数量公式决定
- [ ] SOA、ESB 与微服务关系没有绝对化
- [ ] 治理说明原理而不是只列产品
- [ ] 跨服务一致性包含可靠发布、幂等和补偿
- [ ] 包含渐进迁移、灰度和回滚
- [ ] 下游容量和故障传播已考虑
- [ ] 模拟指标与记忆卡和范文一致
- [ ] 能在规定时间内用纯文字完成
