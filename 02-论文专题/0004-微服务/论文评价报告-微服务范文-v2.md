# 微服务范文训练评价 v2

> 评估对象：`03-微服务论文范文-改写版.md`
>
> 评价性质：仓库内部训练复盘，不是官方阅卷结果，不再使用 `71/75` 等确定分数。

## 一、总体判断

当前等级：**usable（可用）**。

优点：

- 单体痛点、系统架构师职责和改造目标清楚；
- 能覆盖服务拆分、治理、故障隔离和持续交付；
- 实践中包含配置、循环依赖和服务治理问题；
- 具备可改写为不同微服务题目的基本素材。

主要风险：

- 以“识别 30 个事件、拆成 12 个服务”暗示粒度由数量决定；
- “每服务独立数据库”写得过于绝对，未说明迁移与查询代价；
- SOA、ESB 与微服务的关系容易被写成简单替代；
- Nacos、Sentinel、SkyWalking 等产品名较多，架构决策依据偏弱；
- 分布式一致性、幂等、事件契约和渐进迁移展开不足；
- 项目和效果指标属于模拟数据，但原文未充分标注。

## 二、技术审查

| 主题 | 状态 | 修订建议 |
|------|------|----------|
| 服务拆分 | 待加强 | 以业务能力、限界上下文、数据所有权、变更频率和团队能力校验边界 |
| 服务粒度 | 待加强 | 删除“事件数量→服务数量”的机械推导，说明过细和过粗的代价 |
| 数据自治 | 可用 | 不写成所有服务必须物理独库，允许渐进分离和受控共享 |
| 服务治理 | 可用 | 产品名后补充注册、配置、超时、熔断、隔离和观测的原理 |
| 一致性 | 待加强 | 根据业务选择 Outbox、Saga、TCC 或同步事务边界，补充幂等和补偿 |
| SOA 对比 | 待修订 | 改为侧重点不同且可组合，不写“ESB 必然单点” |
| 迁移策略 | 待加强 | 增加绞杀者模式、灰度、契约测试和回滚 |
| 模拟指标 | 待统一 | 与记忆卡和写作框架使用同一组基线 |

## 三、重点修订

### 3.1 服务边界

推荐表达：

```text
事件风暴识别业务事件和命令
→ 划分子域与限界上下文
→ 明确数据所有权和事务边界
→ 分析调用与变更耦合
→ 以独立部署、扩展和团队维护能力校验粒度
```

“两披萨团队”和事件数量只能作为启发，不是固定服务规模公式。

### 3.2 数据一致性

每个跨服务流程必须回答：

- 哪个服务拥有权威数据；
- 哪些步骤需要强一致；
- 哪些步骤允许最终一致；
- 消息如何可靠发布；
- 消费者如何幂等；
- 失败如何补偿和人工处理；
- 用户如何查询处理中状态。

### 3.3 容错

超时、重试、熔断、隔离和降级需要组合设计。重试可能放大故障，熔断不会自动保证业务正确，降级必须定义可接受的业务结果。

## 四、模拟指标建议

| 指标 | 改造前 | 改造后 |
|------|--------|--------|
| 发布频率 | 每周 1—2 次 | 每天 20+ 次 |
| 部署时间 | 30 分钟 | 少于 2 分钟 |
| 故障影响 | 单模块故障可能影响全站 | 单功能隔离并降级 |
| 代码冲突 | 频繁 | 减少 90% |
| 热点服务扩容 | 随整体扩容 | 独立扩容 5 倍 |

这些数据只能作为训练口径，不能作为真实生产结果或官方得分依据。

## 五、优先修订清单

- [ ] 在范文开头标记模拟项目和模拟指标
- [ ] 重写服务拆分依据，减少数量化结论
- [ ] 补充数据所有权、幂等、补偿和查询状态
- [ ] 修正 SOA/ESB 与微服务的绝对化比较
- [ ] 增加渐进迁移、灰度和回滚
- [ ] 将产品名转换为架构能力和质量属性说明
- [ ] 核对记忆卡、框架和范文指标一致性
- [ ] 用新题完成一次 120 分钟迁移写作

## 六、提升为 stable 的条件

```text
题目要求逐项回应
服务边界和数据所有权清楚
跨服务一致性方案完整
治理机制说明原理而非只列产品
指标前后一致
连续两次限时训练无重大遗漏
```
