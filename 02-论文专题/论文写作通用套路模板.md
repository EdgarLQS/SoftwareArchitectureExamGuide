# 系统架构设计师论文通用训练模板

> 本模板用于限时训练和检查论文完整性，不是官方评分标准。题量、字数、作答方式和考试规则以当次官方通知及原始题面为准。

## 一、使用原则

1. **先审题，后套结构**：结构必须服务题目要求，不能用固定五段覆盖所有题型。
2. **逐项回应设问**：题目要求说明几个问题，正文就必须明确回应几个问题。
3. **理论与实践相互对应**：理论不是百科罗列，实践也不是技术栈清单。
4. **架构决策必须有权衡**：说明为什么选、为什么不选、适用边界和副作用。
5. **项目数据必须可信**：真实、脱敏或模拟要明确，全文指标保持一致。
6. **纯文字可表达**：复习资料可以有图表和代码，考场文章必须能用连续文字完成。
7. **内部检查不等于考试分数**：通过本模板只能说明训练项覆盖，不代表确定得分。

## 二、第一步：拆解题目

在写作前建立“题目要求映射表”：

| 题目要求 | 必须回答的内容 | 正文位置 | 项目证据 |
|----------|----------------|----------|----------|
| 说明概念/方法 | 定义、组成、机制、适用场景和限制 | 理论部分 | 项目为何需要该方法 |
| 比较或选型 | 候选方案、质量属性、成本和风险 | 选型部分 | 项目约束与决策依据 |
| 结合项目实践 | 问题、根因、方案、实施和效果 | 实践部分 | 模块、数据流和指标 |
| 说明难点 | 失败模式、边界、副作用和治理 | 实践部分 | 实际遇到的具体问题 |
| 评价效果 | 基线、结果、验证方式和不足 | 总结部分 | SLI/SLO、故障或业务指标 |

审题完成后检查：

- 题目中的每个动词是否识别；
- 是否有数量要求，例如“三种方法”“两个问题”；
- 是否限定行业、系统类型、质量属性或技术；
- 是否要求“结合你参与的项目”；
- 是否要求优缺点、比较、实施难点或效果。

## 三、推荐文章结构

以下是默认结构，可以根据题目合并或拆分：

```text
摘要
→ 一、项目背景与本人职责
→ 二、题目要求的核心理论或方法
→ 三、架构选型、设计与权衡
→ 四、项目实施：问题—原因—方案—效果
→ 五、总结、不足与改进
```

### 结构调整原则

- 题目理论要求多：增加理论与比较篇幅；
- 题目重点是实践：缩短通用定义，增加项目决策和问题处理；
- 题目要求多个子问题：按子问题设置小标题；
- 题目要求评价某技术：增加优点、局限和适用条件；
- 题目要求方法流程：按阶段组织，但不要把某一教材阶段数写成唯一标准。

## 四、摘要

摘要需要让读者快速知道：

```text
什么项目
→ 为什么需要该技术或方法
→ 我承担什么架构职责
→ 采用了哪些核心决策
→ 取得什么结果
```

推荐骨架：

```text
本文以……项目为背景，论述……在该项目中的应用。
该系统面向……业务，原有架构存在……问题。
我在项目中担任系统架构师，负责……。
针对上述问题，我们从……、……和……方面进行设计与实施。
改造后，……指标由……改善到……，同时也暴露出……不足。
```

检查：

- 是否直接点题；
- 是否包含项目、角色、方案和效果；
- 是否没有塞入过多配置和产品细节；
- 指标是否与正文一致；
- 模拟项目是否避免冒充真实项目。

字数只作为训练参考，不以精确落在某个区间作为满分依据。

## 五、项目背景与角色

### 5.1 项目背景

至少说明：

- 行业和系统目标；
- 核心用户和业务流程；
- 系统规模和主要约束；
- 原有架构或现状；
- 触发改造的业务与技术问题。

不需要堆砌完整技术栈。只保留与题目相关的组件和约束。

### 5.2 架构师职责

职责应体现：

- 识别架构驱动因素；
- 制定架构方案和关键技术决策；
- 组织候选方案比较和验证；
- 定义架构约束、接口和质量指标；
- 协调研发、测试、安全和运维落地；
- 处理架构风险和演进。

“我担任系统架构师”可以自然出现，但不是必须逐字照抄的官方得分句式。重点是角色与职责真实、清楚并与论文主题相关。

## 六、理论与方法

理论部分采用以下最小结构：

```text
准确定义
→ 核心组成或流程
→ 工作机制
→ 优势
→ 局限
→ 适用场景
```

### 6.1 分类题

每一类说明：

- 分类依据；
- 核心机制；
- 与其他类型的区别；
- 优势与限制；
- 适用场景；
- 项目中是否采用。

不要为了凑数量发明分类，也不要把某一资料中的分类当作唯一标准。

### 6.2 流程题

每个阶段说明：

- 输入；
- 主要活动；
- 输出；
- 责任人或参与者；
- 质量门槛；
- 与前后阶段的反馈关系。

阶段通常不是单向瀑布，应说明迭代、回退和演进。

### 6.3 原则或特征题

每项原则说明：

```text
含义
→ 为什么重要
→ 如何落地
→ 可能的副作用
→ 如何验证
```

### 6.4 比较题

使用统一维度比较：

- 业务适配；
- 一致性和事务；
- 性能与扩展；
- 可用性与恢复；
- 可修改性；
- 安全；
- 成本和团队能力；
- 运维与演进。

## 七、架构选型与权衡

推荐结构：

```text
质量属性和约束
→ 候选方案
→ 风险、敏感点和权衡点
→ 决策
→ 配套治理措施
```

### 7.1 不只写“优点多”

选型理由应与项目约束绑定：

- 业务量和增长；
- 延迟和吞吐目标；
- 一致性要求；
- 故障影响；
- 数据和安全约束；
- 现有系统迁移成本；
- 团队能力；
- 时间和预算。

### 7.2 必须写限制

例如：

- 微服务提高独立交付能力，但引入分布式一致性和治理成本；
- 缓存降低读取延迟，但引入一致性和失效问题；
- 异步消息解耦时间，但引入幂等、顺序和补偿；
- 自动扩容提高弹性，但可能放大数据库和外部依赖压力；
- 加密保护数据，但增加密钥管理和性能成本。

## 八、项目实践

每个主要实践使用统一因果链：

```text
问题现象
→ 监控或数据证据
→ 根因
→ 候选方案和权衡
→ 最终方案
→ 实施过程
→ 风险与副作用
→ 验证结果
```

### 示例骨架

```text
项目上线压测时，我们发现……，表现为……。
通过……指标、日志和链路追踪，确认根因是……，而不是最初怀疑的……。
我们比较了方案 A、B 和 C：A 的优点是……但……；B……；最终选择 C，原因是……。
实施中，我们先……，再……，并通过……控制风险。
改造后，在相同测试条件下，指标从……改善到……；同时……仍是限制，因此后续……。
```

### 常见无效写法

- 只列产品名称；
- 只写“使用后性能显著提升”；
- 没有基线和测试条件；
- 忽略失败、补偿和回滚；
- 一个方案解决所有问题；
- 指标前后不一致；
- 技术措施与效果没有因果关系。

## 九、指标与模拟数据

### 9.1 指标分类

| 类别 | 示例 |
|------|------|
| 性能 | P50/P95/P99、TPS、队列长度 |
| 可用性 | SLO、错误率、MTTR、恢复演练 |
| 质量 | 缺陷率、一致率、数据质量规则通过率 |
| 交付 | Lead Time、部署频率、变更失败率 |
| 安全 | 高危事件、发现时间、处置时间、审计覆盖 |
| 成本 | 资源使用、账单、单位业务成本 |
| 业务 | 成功率、转化率、处理周期、投诉量 |

### 9.2 数据一致性检查

- 摘要、正文和总结使用同一基线；
- 中间阶段指标按合理顺序改善；
- 可用性、故障次数和 MTTR 不互相矛盾；
- 成本结论有容量或账单依据；
- 没有把工具语义写成业务绝对正确；
- 模拟数据明确标注 `scenario_data: simulated`。

## 十、总结

总结包含：

- 回答题目要求；
- 概括关键架构决策；
- 给出最重要的验证结果；
- 说明仍存在的限制；
- 给出与限制直接相关的下一步改进。

不要使用空泛的“AIOps、AI、Service Mesh”作为所有论文统一展望。展望必须解决正文中真实存在的不足。

## 十一、限时训练

### 11.1 提纲训练

```text
审题并拆分设问
→ 建立题目要求映射表
→ 选择项目背景
→ 列出三组问题—方案—效果
→ 检查技术边界和模拟指标
```

### 11.2 全文训练

时间分配可根据个人速度调整，核心要求是：

- 留出足够时间审题和列提纲；
- 先确保全部题目要求有位置；
- 不在单一理论点上耗费过多时间；
- 完成后检查题目遗漏、指标冲突和明显技术错误；
- 每次训练记录实际用时和未完成原因。

## 十二、交卷前检查

### 题目回应

- [ ] 题目全部设问均已回应
- [ ] 没有偏离题目限定的技术或场景
- [ ] 理论与项目实践一一对应

### 技术正确性

- [ ] 术语定义准确
- [ ] 方案说明了限制和副作用
- [ ] 一致性、故障、安全和恢复有处理
- [ ] 没有使用“天然、绝对、零侵入、一定”等无条件结论

### 项目与数据

- [ ] 项目规模与方案匹配
- [ ] 指标前后一致
- [ ] 模拟数据没有冒充真实结果
- [ ] 效果有验证条件和依据

### 表达与完成度

- [ ] 结构清楚
- [ ] 段落中心明确
- [ ] 没有大段重复
- [ ] 关键图表内容已转换为文字
- [ ] 有不足和针对性改进

## 十三、评价方式

训练评价使用：

- `stable`：能够迁移，技术和数据经过复核；
- `usable`：可以使用，但仍有风险；
- `revise`：存在明显问题；
- `avoid`：不建议继续使用。

详细见[论文训练评价规范](../00-项目管理/论文训练评价规范.md)。不要把内部检查表换算成确定的 `75/75` 或“70+ 分”。
