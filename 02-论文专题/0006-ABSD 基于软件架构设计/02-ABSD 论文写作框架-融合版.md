# ABSD 基于架构的软件设计论文写作框架

> 文件名保留“融合版”仅为兼容历史链接。当前内容不再强制五段、固定字数、固定句式、固定“我/我们”次数，也不把某一种 ABSD 阶段划分写成唯一官方标准。

## 一、适用题型

- 论基于架构的软件设计及其应用；
- 说明架构需求、设计、文档、评估、实现和演进；
- 说明质量属性场景和架构驱动因素；
- 说明 ATAM 或其他架构评估方法；
- 结合项目说明架构设计、关键风险和演进过程。

## 二、审题映射

| 题目要求 | 必须回答 |
|----------|----------|
| 说明 ABSD | 核心思想、输入、活动、产出和反馈闭环 |
| 说明质量属性 | 场景六要素、优先级和响应度量 |
| 说明架构设计 | 风格、部件、连接器、约束和候选方案 |
| 说明评估 | 风险、非风险、敏感点、权衡点和改进决策 |
| 结合项目 | 问题、架构决策、实施一致性、演进和指标 |

## 三、推荐结构

```text
摘要
→ 项目背景、质量属性和本人职责
→ ABSD 核心思想和本文采用的活动组织
→ 架构设计、文档与评估
→ 项目实践：风险—决策—实施—验证
→ 架构演进、效果和不足
```

题目若采用特定教材阶段划分，应按该题目或来源组织；不要脱离来源宣称只有唯一“六阶段”。

## 四、ABSD 核心闭环

```text
业务目标和约束
→ 架构驱动因素与质量属性场景
→ 候选架构风格、部件、连接器和约束
→ 多视图文档化
→ 架构评估与风险处理
→ 实现一致性和自动化约束
→ 运行反馈与受控演进
```

### 4.1 各活动需要说明的内容

| 活动 | 输入 | 核心工作 | 输出 |
|------|------|----------|------|
| 架构需求 | 业务目标、功能、约束和干系人诉求 | 识别架构驱动因素和质量属性优先级 | 场景、约束和验收指标 |
| 架构设计 | 驱动因素、现状和候选技术 | 选择风格、分解部件、定义连接器和约束 | 架构方案与关键决策 |
| 文档化 | 架构方案和干系人关注点 | 使用不同视图描述结构、运行和部署 | 可沟通、可实现的架构文档 |
| 架构评估 | 场景、架构方法和约束 | 分析风险、敏感点和权衡点 | 风险清单和改进建议 |
| 实现与治理 | 架构约束和开发计划 | 契约、依赖、流水线和一致性检查 | 与架构一致的实现 |
| 演进 | 运行指标、故障、变更和成本 | 重新评估并受控修改架构 | 新决策、迁移计划和更新文档 |

这些活动通常迭代进行，不是严格单向瀑布。

## 五、质量属性场景

| 要素 | 需要回答的问题 |
|------|----------------|
| 刺激源 | 谁或什么产生事件 |
| 刺激 | 发生了什么 |
| 环境 | 正常、高峰、故障还是维护状态 |
| 制品 | 哪个系统部分受到影响 |
| 响应 | 系统采取什么动作 |
| 响应度量 | 如何判断满足要求 |

示例：

> 在大促高峰环境下，外部用户向订单服务发起每秒一万次请求，系统通过限流、水平扩容和异步削峰保持核心下单能力，P99 小于 500ms，错误率小于 0.1%。

场景要使用项目真实或模拟的主体、组件和指标，不只列六个名词。

## 六、架构设计与文档

### 6.1 设计对象

- **部件**：服务、模块、数据库、消息系统和外部系统；
- **连接器**：调用、事件、消息、共享数据和协议；
- **约束**：依赖方向、数据所有权、通信、部署、安全和合规规则；
- **架构方法**：为满足质量属性而采用的风格、模式和战术。

### 6.2 候选方案比较

使用统一维度：

- 性能和容量；
- 可用性和恢复；
- 可修改性和独立交付；
- 一致性和事务；
- 安全与隐私；
- 迁移、成本和团队能力。

### 6.3 文档视图

可以根据干系人需要使用逻辑、开发、进程、部署和场景等视图。重点是：

- 每个视图回答谁的问题；
- 视图之间保持一致；
- 关键接口和架构约束可执行；
- 架构变化后同步更新。

不要求所有论文都机械列出完整 4+1 视图。

## 七、架构评估

### 7.1 ATAM 训练口径

```text
确认业务驱动因素
→ 说明架构方案
→ 构建质量属性效用树
→ 分析架构方法
→ 识别风险、非风险、敏感点和权衡点
→ 汇总改进建议
```

| 概念 | 含义 | 示例 |
|------|------|------|
| 风险 | 可能无法满足场景的架构决策 | 长同步调用链造成级联故障 |
| 非风险 | 当前场景下有充分依据认为可接受 | 报表使用短暂最终一致副本 |
| 敏感点 | 参数变化显著影响质量属性 | 超时阈值影响恢复和误判 |
| 权衡点 | 同一决策影响多个质量属性 | 加密提高安全性但增加延迟 |

评估不是给架构“打一个总分”，而是发现风险并改变决策。

## 八、项目实践框架

### 8.1 实践一：同步故障传播

```text
问题：仓储、运输和结算同步强依赖
→ 证据：依赖故障导致整条业务链超时
→ 架构风险：可用性和恢复能力不足
→ 候选：增加重试、服务隔离、事件驱动
→ 决策：核心事务保持本地，跨域使用事件和补偿
→ 实施：Outbox、幂等消费、状态查询和人工兜底
→ 验证：故障影响范围、恢复时间和一致率
```

### 8.2 Outbox 正确边界

```text
业务数据与 Outbox 记录同库同事务提交
→ CDC 或可靠扫描投递消息
→ 消费者幂等处理
→ 已发送记录分区、归档和清理
```

若把消息表与业务表物理拆库，就不再天然拥有本地事务原子性，必须补充新的可靠协议。不能只写“拆库解决 I/O”。

### 8.3 实践二：加密与查询

```text
问题：敏感字段需要加密，但查询性能下降
→ 分析：哪些字段需可检索，哪些只需解密读取
→ 候选：明文索引、确定性加密、盲索引和专用检索服务
→ 决策：按威胁、查询类型和合规选择
→ 风险：频率泄露、碰撞、密钥轮换和模糊查询限制
→ 验证：查询延迟、泄露面和轮换演练
```

不要把盲索引描述为支持任意安全模糊查询。

### 8.4 实践三：架构漂移

```text
问题：实现逐渐违反依赖和契约约束
→ 根因：架构规则只存在文档中
→ 方案：ADR、依赖测试、契约测试和流水线检查
→ 验证：违规依赖、破坏性变更和回滚次数
```

## 九、架构演进

- 使用 ADR 记录背景、候选方案、决策和后果；
- 使用绞杀者模式渐进迁移；
- 灰度发布并保存回滚路径；
- 根据 SLI/SLO、故障和成本重新评估；
- 架构文档与实现同步更新；
- 演进不是追逐新技术，而是处理新的架构驱动因素。

## 十、模拟指标口径

| 指标 | 改造前 | 改造后 |
|------|--------|--------|
| 峰值吞吐 | 2000 TPS | 12000 TPS |
| 平均响应 | 1500ms | 150ms |
| 可用性 | 99.5% | 99.99% |
| 故障影响 | 全链传播 | 局部隔离和异步补偿 |
| 数据异常率 | 0.5% | 少于 0.01% |

均为训练模拟数据，应与记忆卡和范文保持一致。不要使用“数据安全零事故”证明方案绝对正确。

## 十一、摘要与总结

### 摘要

```text
项目和架构驱动因素
→ 采用 ABSD 的原因
→ 质量属性、设计、评估和实施重点
→ 主要效果
→ 本文回应的题目要求
```

### 总结

```text
回扣质量属性和关键架构决策
→ 给出验证指标
→ 说明文档、演进或治理不足
→ 给出针对性的下一步改进
```

不要把 AI/AIOps 作为所有项目的默认展望，除非它直接解决正文中的具体不足。

## 十二、检查单

- [ ] 题目要求的 ABSD 活动全部回应
- [ ] 阶段划分有来源，未写成唯一官方标准
- [ ] 质量属性场景包含六要素和响应度量
- [ ] 部件、连接器和约束描述清楚
- [ ] 候选方案使用统一维度比较
- [ ] ATAM 风险、敏感点和权衡点使用准确
- [ ] Outbox 保持正确事务边界
- [ ] 实现一致性和架构演进形成闭环
- [ ] 模拟指标与记忆卡和范文一致
- [ ] 能在规定时间内用纯文字完成
