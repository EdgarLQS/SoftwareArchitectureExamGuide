# 论文审查与改进工作流

> 用于审查已有论文、框架和记忆卡。该流程不产生官方考试分数，只输出内部等级、技术风险和可验收的修订任务。

## 一、工作流概览

```text
确定题目与版本
→ 审题映射
→ 技术事实审查
→ 架构决策审查
→ 项目与指标一致性审查
→ 结构与表达审查
→ 形成 P0/P1/P2 修订清单
→ 限时重写
→ 再评价与归档
```

## 二、确定评估对象

开始前记录：

- 原始论文题目和全部设问；
- 当前范文、写作框架和记忆卡文件；
- 文档版本和最近更新时间；
- 项目数据类型：真实、脱敏、模拟或混合；
- 使用的主要来源及其可信度；
- 本轮评估目标：技术纠错、结构改写、限时训练或批次迁移。

没有原始题面时，只能评价文章本身，不能断言“完全切题”或推导考试分数。

## 三、建立题目要求映射

| 题目要求 | 范文回应位置 | 覆盖状态 | 主要问题 |
|----------|--------------|----------|----------|
| 要求 1 | 摘要 / 第 X 节 | 完整 / 部分 / 缺失 | |
| 要求 2 | 第 X 节 | 完整 / 部分 / 缺失 | |
| 项目实践 | 第 X 节 | 完整 / 部分 / 缺失 | |
| 难点或权衡 | 第 X 节 | 完整 / 部分 / 缺失 | |
| 效果与评价 | 总结 | 完整 / 部分 / 缺失 | |

以下属于 P0：

- 遗漏题目明确要求；
- 回答对象或场景与题目不符；
- 只写通用知识，没有结合项目；
- 项目实践无法支持所选技术；
- 结论与设问相反或答非所问。

## 四、技术事实审查

逐项检查：

1. 定义是否准确；
2. 分类、阶段和原则是否有来源；
3. 是否把某一资料的分类写成唯一标准；
4. 是否混淆相近概念；
5. 是否存在“天然高可用、完全零侵入、绝对一致”等无条件结论；
6. 是否说明技术限制、副作用和前提；
7. 产品名称是否被误当成架构原理；
8. 是否包含故障、回滚、补偿和恢复；
9. 是否与当前专题记忆卡采用同一技术口径。

推荐表格：

| 技术点 | 当前表述 | 状态 | 风险 | 修订建议 | 来源 |
|--------|----------|------|------|----------|------|

状态统一使用：

- `correct`：当前表述准确；
- `needs-context`：基本正确，但缺少前提或边界；
- `incorrect`：存在实质性技术错误；
- `unverified`：暂时没有足够来源核验。

## 五、架构决策审查

每个关键方案至少回答：

```text
要解决什么问题
→ 有什么监控、日志或业务证据
→ 候选方案有哪些
→ 使用哪些质量属性和约束比较
→ 为什么选择当前方案
→ 有什么代价和风险
→ 如何验证、灰度和回滚
```

### 常见缺陷

- 直接从问题跳到产品名称；
- 没有候选方案和权衡；
- 一个技术被描述为解决所有问题；
- 没有一致性、安全、容量和故障边界；
- 只写成功结果，不写副作用和治理；
- 方案规模远大于或远小于项目实际需要；
- 把团队熟悉某产品写成唯一选型依据。

## 六、项目与指标一致性审查

建立统一指标表：

| 指标 | 基线 | 中间阶段 | 最终结果 | 出现位置 | 是否一致 |
|------|------|----------|----------|----------|----------|

检查：

- 摘要、记忆卡、框架、范文和总结是否一致；
- 中间阶段是否合理改善；
- 提升幅度是否与措施和资源匹配；
- 可用性、故障次数、MTTR 和统计窗口是否一致；
- TPS、QPS、并发用户和业务交易是否混用；
- 成本结论是否有容量或账单依据；
- 正确性指标是否与处理语义混为一谈；
- 模拟数据是否明确标注。

以下属于 P0：

- 百分比和分数计算错误；
- 优化后指标反而变差但没有解释；
- 同一指标在不同文档使用多套基线；
- 模拟数据冒充真实项目结果；
- 由单次压测直接推导长期成本或可用性；
- 用“零事故”证明架构绝对正确。

## 七、结构与表达审查

### 7.1 结构

- 摘要是否点题；
- 项目背景是否只保留相关信息；
- 理论是否服务题目；
- 选型是否有权衡；
- 实践是否包含问题、证据、方案和效果；
- 总结是否回应题目并说明不足；
- 小标题是否与题目设问对应。

文章可以是五段、六段或按题目子问题组织。段落数量本身不构成得分或失分依据。

### 7.2 表达

- 是否存在长句、重复和空泛口号；
- 是否自然说明个人职责和团队协作；
- 是否能用纯文字表达关键架构；
- 是否过度依赖固定过渡句；
- 是否为了术语数量牺牲逻辑；
- 是否能在限时条件下完成；
- 是否把内部训练规则写成官方要求。

不检查固定“我/我们”出现次数，不要求统一五条过渡句，也不把精确字数区间换算为分数。

## 八、形成优先级清单

### P0：必须修复

- 核心概念错误；
- 题目要求遗漏；
- 架构方案违反关键技术前提；
- 指标冲突或数学错误；
- 来源伪造或把参考内容称为官方；
- 把模拟数据写成真实项目；
- 把内部量表写成官方分数；
- 方案无法保证基本正确性、安全性或可恢复性。

### P1：影响稳定性

- 选型缺少权衡；
- 项目和理论联系不强；
- 缺少故障、补偿、回滚或演进；
- 指标缺少验证条件；
- 文章无法迁移到新题；
- 技术栈堆叠多，架构决策少。

### P2：表达优化

- 重复内容；
- 段落顺序；
- 术语统一；
- 句子过长；
- 过渡不自然；
- 次要数据不易记忆；
- 示例和结论距离过远。

## 九、重写策略

### 9.1 最小修订

适用：主体正确，仅有局部错误。

- 修正事实和术语；
- 统一指标；
- 增加限制和验证；
- 删除绝对化结论；
- 补充遗漏设问；
- 在开头增加来源和模拟数据标记。

### 9.2 结构重组

适用：素材可用，但题目映射和顺序混乱。

- 保留项目与有效实践；
- 按题目要求重新排列；
- 合并重复理论；
- 将产品清单改为架构决策；
- 重新写摘要和总结；
- 删除只为满足固定模板而存在的段落。

### 9.3 全文重写

适用：核心技术错误、项目不匹配或无法限时完成。

```text
重新审题
→ 选择稳定项目
→ 建立质量属性和候选方案
→ 选择 2—4 组最强实践因果链
→ 统一指标
→ 限时完成新版本
→ 用新题再次迁移验证
```

## 十、内部评价

使用以下等级，不换算考试分数：

| 等级 | 含义 |
|------|------|
| `stable` | 能迁移到新题，技术和数据经过复核 |
| `usable` | 可用于训练，仍有若干风险 |
| `revise` | 存在明显问题，需修订后再使用 |
| `avoid` | 不建议继续使用 |

输出评价应包含：

- 总体判断；
- 题目回应情况；
- 技术审查；
- 项目与指标；
- P0/P1/P2 修订清单；
- 提升到下一等级的验收条件。

详细规范见[论文训练评价规范](../00-项目管理/论文训练评价规范.md)。

## 十一、限时验证

修订后至少进行：

1. 一次 10—15 分钟脱稿提纲；
2. 一次新题迁移；
3. 一次 120 分钟全文训练；
4. 一次技术和指标复核；
5. 将遗忘点和新风险回写记忆卡。

通过标准：

```text
题目要求无遗漏
无重大技术错误
指标前后一致
能够在规定时间内完成
能解释方案限制和替代方案
新题中不再机械复制原文结构
```

## 十二、历史文档迁移

遇到以下旧表述时：

| 旧表述 | 新处理方式 |
|--------|------------|
| `71/75`、`75/75`、`70+ 分标准` | 改为内部等级和技术风险 |
| “正文必须五段” | 改为按题目要求组织 |
| “理论必须 1100 字” | 改为理论足够回答题目且不挤压实践 |
| “我必须出现两次” | 改为职责表达自然、真实 |
| “五条过渡句必须出现” | 改为逻辑衔接清楚 |
| “每篇必须三组问题” | 根据题目数量和篇幅选择 |
| “字数满足即得满分” | 改为完成度和内容质量检查 |
| “参考答案即官方答案” | 明确答案来源等级 |

旧文件需要保留路径时，设置：

```yaml
status: deprecated
replaced_by: 新文件名.md
```

## 十三、检查单

- [ ] 有原始题目或明确说明没有题面
- [ ] 建立题目要求映射
- [ ] 关键技术逐项复核
- [ ] 架构决策包含候选方案与权衡
- [ ] 指标建立统一表
- [ ] 模拟数据完成标注
- [ ] P0/P1/P2 清单明确
- [ ] 完成限时重写
- [ ] 更新记忆卡和评价报告
- [ ] 旧报告标记废弃或归档
