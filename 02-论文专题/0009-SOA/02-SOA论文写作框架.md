# SOA 面向服务架构论文写作框架

> 本框架按业务能力、服务契约和集成治理组织，不再强制五段、固定字数或把 SOA 等同于 SOAP/ESB。

## 一、适用题型

- 论面向服务架构及其应用；
- 说明服务识别、服务契约、服务组合和服务治理；
- 说明 ESB、API、消息和企业集成；
- 比较 SOA、单体、微服务和事件驱动；
- 结合项目说明遗留系统集成、流程协同和一致性。

## 二、审题映射

| 题目要求 | 必须回答 |
|----------|----------|
| SOA 概念 | 服务化原则、业务能力、契约、松耦合和治理 |
| 服务识别 | 业务流程、领域边界、数据所有权和复用价值 |
| 服务契约 | 语义、版本、兼容、错误、权限、SLO 和退役 |
| 集成方式 | 同步 API、消息、事件、批量、编排和协同 |
| 项目实践 | 遗留封装、语义统一、失败恢复和效果指标 |

## 三、推荐结构

```text
摘要
→ 项目孤岛、流程和本人职责
→ SOA 原则与服务识别
→ 服务契约、集成方式和治理
→ 项目实践：接口、语义和跨系统流程
→ 效果、不足和服务演进
```

## 四、SOA 核心原则

| 原则 | 含义 | 检查点 |
|------|------|--------|
| 标准契约 | 接口、数据、策略和质量有明确约定 | 版本、错误和兼容是否定义 |
| 松耦合 | 消费者不依赖服务内部实现 | 是否直接访问内部数据库 |
| 服务抽象 | 隐藏实现，暴露稳定业务能力 | 契约是否夹带私有结构 |
| 服务复用 | 支持多个合理业务场景 | 是否为复用而过度泛化 |
| 服务自治 | 控制自身逻辑、数据和运行责任 | 所有权是否清楚 |
| 可发现 | 能检索能力、契约和负责人 | 服务目录是否维护 |
| 可组合 | 能形成跨服务业务流程 | 失败和补偿如何处理 |

SOA 是架构原则和治理方法，不要求必须使用 SOAP，也不要求必须部署 ESB。

## 五、服务识别与粒度

```text
梳理端到端业务流程和价值流
→ 识别稳定业务能力
→ 划分领域边界与数据所有权
→ 明确事务和一致性要求
→ 设计粗粒度业务契约
→ 校验复用、变更、容量和团队责任
```

服务太细会增加调用、事务和治理成本；太粗则复用和独立演进困难。粒度由业务能力和约束决定，不由固定数量决定。

## 六、服务契约

至少包含：

- 业务语义与数据模型；
- 操作、事件或资源定义；
- 版本和向后兼容策略；
- 错误码、超时和重试边界；
- 身份、授权和审计；
- SLO、容量和限流；
- 负责人、依赖和退役窗口。

使用消费者驱动契约测试或等价方法验证升级兼容性。

## 七、集成方式选择

| 方式 | 适用场景 | 优点 | 风险 |
|------|----------|------|------|
| 同步 API | 需要即时结果的查询和命令 | 交互直接、错误即时返回 | 时间耦合和级联故障 |
| 异步消息 | 通知、削峰和最终一致 | 时间解耦、提高韧性 | 幂等、顺序、重试和积压 |
| 事件发布订阅 | 多消费者响应业务事实 | 扩展消费者不修改生产者 | 事件所有权和 Schema 演进 |
| 批量文件/ETL | 大批数据交换和监管报送 | 吞吐高、便于留档 | 延迟、补传和格式治理 |
| 流程编排 | 需要中心流程和状态可见 | 统一控制和补偿 | 编排器耦合和瓶颈 |
| 事件协同 | 服务自治响应业务事件 | 去中心化和局部自治 | 全局流程理解与排错困难 |

## 八、组件边界

| 组件 | 主要职责 | 不应承载 |
|------|----------|----------|
| ESB/集成平台 | 协议转换、适配、路由和遗留集成 | 无边界核心业务逻辑 |
| API 网关 | 外部路由、认证、限流和观测 | 长业务流程和领域规则 |
| 消息平台 | 可靠传输、缓冲和发布订阅 | 事件业务语义和消费者逻辑 |
| 服务目录 | 契约、版本、负责人和生命周期 | 运行时转发 |
| 流程引擎 | 长流程状态和补偿编排 | 所有服务内部业务逻辑 |

ESB 是否单点取决于部署和容灾；更常见风险是转换、规则和流程持续集中，形成组织与发布瓶颈。

## 九、跨系统一致性

```text
明确权威服务和事务边界
→ 区分强一致与最终一致步骤
→ 使用 Outbox/事务消息可靠发布
→ 消费者幂等
→ 设计补偿和状态机
→ 提供查询状态、对账和人工兜底
```

可以根据业务选择 Saga、TCC 或其他方案，但不能只列名词。需要说明失败路径、超时、重复和恢复。

## 十、项目实践框架

### 10.1 点对点接口爆炸

```text
问题：多个系统两两连接，接口数量快速增长
→ 根因：缺少业务服务边界和标准契约
→ 方案：服务目录、标准契约和遗留适配器
→ 风险：服务过度泛化和集中治理瓶颈
→ 验证：重复接口、接入周期和变更影响
```

### 10.2 业务语义冲突

```text
问题：客户、订单和金额定义不同，对账失败
→ 根因：只统一格式，未统一业务语义
→ 方案：规范模型、主数据、数据契约和责任人审批
→ 验证：对账差异和语义冲突数量
```

### 10.3 跨系统流程失败

```text
问题：订单、库存和运输部分成功
→ 根因：长同步事务不可行，缺少幂等和补偿
→ 方案：Saga/状态机、Outbox、幂等、超时和人工处理
→ 验证：异常恢复时间、一致率和人工工单量
```

### 10.4 契约演进

```text
问题：服务升级导致多个消费者同时失败
→ 方案：向后兼容、版本化、契约测试和退役窗口
→ 验证：破坏性变更和升级失败率
```

## 十一、治理与可观测性

- 服务目录记录能力、契约、负责人和依赖；
- API 与事件统一关联 ID；
- 同步调用配置超时、重试预算、熔断和隔离；
- 消息具备死信、重放、审计和积压告警；
- 定期淘汰重复、低复用或职责混乱的服务；
- 权限、容量、成本和生命周期统一治理。

## 十二、模拟指标口径

| 指标 | 改造前 | 改造后 |
|------|--------|--------|
| 点对点接口 | 180 个 | 70 个标准服务与适配接口 |
| 重复接口 | 基线 | 减少 60% |
| 新流程交付周期 | 8 周 | 2 周 |
| 对账差异 | 0.5% | 0.02% |
| 异常恢复时间 | 4 小时 | 20 分钟 |
| 核心服务可用性 | 99.5% | 99.95% |

均为训练模拟数据，应与记忆卡和范文一致。

## 十三、摘要与总结

### 摘要

```text
项目孤岛和流程问题
→ SOA 服务与契约设计
→ 集成、治理和一致性重点
→ 主要效果
→ 本文回应的题目要求
```

### 总结

```text
回扣服务复用和业务协同
→ 给出接口、交付和恢复指标
→ 说明集中治理和遗留改造成本
→ 给出契约、事件和治理演进
```

## 十四、检查单

- [ ] SOA 未被简化为 SOAP 或 ESB
- [ ] 服务边界和数据所有权清楚
- [ ] 契约包含版本、兼容和生命周期
- [ ] 同步、消息、事件和批量选择有依据
- [ ] ESB、API 网关和消息平台职责未混淆
- [ ] 跨系统一致性包含可靠发布、幂等和补偿
- [ ] SOA、微服务和事件驱动关系未绝对化
- [ ] 模拟指标与记忆卡和范文一致
- [ ] 能在规定时间内用纯文字完成
