# SOA 范文训练评价 v2

> 评估对象：`03-SOA论文范文-改写版.md`
>
> 评价性质：内部训练复盘，非官方评分。原 `71/75` 已取消。

## 一、总体判断

当前等级：**usable（可用）**。

优点：

- 能从系统孤岛、接口重复和跨系统流程引出 SOA；
- 覆盖服务契约、复用、集成、治理和流程协同；
- 具有遗留系统封装、数据语义和一致性问题素材；
- 可迁移到企业集成、服务化和事件驱动类题目。

主要风险：

- 容易把 SOA 等同于 SOAP、Web Service 或 ESB；
- 把 ESB 写成必然单点或把微服务/Service Mesh 写成简单替代；
- 服务粒度、数据所有权和契约演进说明不足；
- 集中编排与事件协同的适用边界不清；
- 分布式事务方案缺少幂等、补偿和人工兜底；
- 项目指标属于模拟数据但原文标注不足。

## 二、技术审查

| 主题 | 状态 | 修订建议 |
|------|------|----------|
| SOA 定义 | 待加强 | 强调服务原则、业务能力和治理，不等同具体协议 |
| 服务识别 | 待加强 | 从流程、领域边界、数据所有权和复用价值识别 |
| 服务契约 | P0 | 增加版本、兼容、错误、SLO 和退役策略 |
| ESB | 待修订 | 说明协议转换与集成价值，也说明集中逻辑膨胀风险 |
| API/消息 | 可用 | 根据即时结果、解耦、顺序和一致性选择 |
| 流程编排 | 可用 | 补充状态、超时、补偿和恢复 |
| 事件协同 | 待加强 | 增加事件所有权、Schema 演进和全链路观测 |
| 微服务关系 | 待修订 | SOA、微服务和事件驱动可组合，不是线性替代 |
| 模拟数据 | 待统一 | 与记忆卡和框架使用同一口径 |

## 三、关键修订

### 3.1 SOA 与技术组件

SOA 是服务化架构原则和治理方法。SOAP、REST、消息、ESB、API 网关和服务目录都可能用于实现 SOA，但没有某个组件就不等于没有 SOA。

### 3.2 ESB 边界

ESB 是否形成单点取决于集群和容灾设计。更常见的架构风险是：转换、编排和业务规则不断集中到总线上，导致发布、扩展和组织协作瓶颈。

### 3.3 服务契约

服务契约至少需要说明：

- 业务语义和数据模型；
- 版本与兼容策略；
- 身份、权限和审计；
- 错误码、超时和重试；
- SLO 和容量限制；
- 负责人和退役流程。

## 四、模拟指标建议

| 指标 | 改造前 | 改造后 |
|------|--------|--------|
| 点对点接口 | 180 个 | 70 个标准服务与适配接口 |
| 重复接口 | 基线 | 减少 60% |
| 新流程交付周期 | 8 周 | 2 周 |
| 对账差异 | 0.5% | 0.02% |
| 异常恢复时间 | 4 小时 | 20 分钟 |
| 核心服务可用性 | 99.5% | 99.95% |

## 五、优先修订清单

- [ ] 标记项目和指标为模拟数据
- [ ] 将 SOA 从技术清单改为服务原则和治理
- [ ] 增加服务识别、数据所有权和契约生命周期
- [ ] 修正 ESB、微服务和 Service Mesh 的替代性表述
- [ ] 明确同步、异步、批量和事件方式的选择依据
- [ ] 补充幂等、补偿、重放和人工处理
- [ ] 加入 API、消息和流程的统一可观测性
- [ ] 核对记忆卡、框架和范文全部指标

## 六、提升为 stable 的条件

```text
服务边界和业务语义清楚
契约版本与治理完整
集成方式选择有依据
跨系统失败和恢复方案成立
SOA与微服务关系不绝对化
限时迁移写作无重大遗漏
```
