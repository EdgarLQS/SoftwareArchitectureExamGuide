## 二、写作方法论：三种论文准备层次

### 层次一：知识点（背什么）

每个专题的 `01-核心知识点.md` 提供了考试需要掌握的技术概念。这是**原材料**，确保你写得对。

### 层次二：写作框架（怎么写）

每个专题的 `02-论文写作框架.md` 提供了论文的标准结构：摘要模板、正文论点组织、量化指标、避坑指南。这是**骨架**，确保你写得完整。

### 层次三：故事线（为什么需要）

以 `0003-测试` 专题的 `05-一个系统的测试成长史：从功能正确到质量左移.md` 为代表，用**产品成长史**的方式串联所有知识点，回答"为什么需要这个技术"。这是**灵魂**，让你写得生动。

## 三、故事线文档

### 故事线一：测试专题的成长史

这是第一个故事线文档，用产品成长史串联所有测试知识点。

### 核心记忆线

```
能不能用 → 好不好用 → 扛不扛得住 → 能不能一直稳 → 改了会不会坏 → 测得完吗 → 能不能提前保证质量
```

### 七个阶段

| 阶段 | 故事触发事件 | 引入的技术 | 一句话记忆 |
|------|------------|-----------|-----------|
| **幼年期** | 上线后用户投诉金额算错、库存为 0 还能下单 | 功能测试、单元测试、黑盒/白盒 | 证明系统"做对了事" |
| **成长期** | 用户增长，页面加载 5 秒 | 性能测试、SLA、P99、TPS | 证明系统"做得够快" |
| **爆发期** | 大促瞬时 50 倍流量，系统雪崩 | 负载测试、压力测试、并发测试 | 证明"预期流量下能达标"，找到"系统极限" |
| **成熟期** | 运行 30 天后 OOM 崩溃 | 稳定性测试、容量测试 | 证明系统"长时间运行不劣化" |
| **复杂期** | 微服务膨胀到 15 个，改一处坏三处 | 回归测试、缺陷管理 | 证明"修改没有破坏已有能力" |
| **效率期** | 每次回归测 2 天，人测不过来 | 自动化测试体系 | 让重复验证"低成本、可持续" |
| **工程化期** | 测试太晚发现问题，上线前一天性能退化 | CI/CD、测试金字塔、质量左移 | 把质量从"上线前检查"变成"研发过程内建" |

### 故事线二：从单体到云原生（微服务+云原生合并）

覆盖**微服务**（`0004-微服务/`）和**云原生**（`0005-云原生/`）两个专题的合并故事线。

### 核心记忆线

```
单体太重，所以要拆；
服务太多，所以要治；
环境太乱，所以容器化；
容器太多，所以要编排；
发布太频繁，所以要流水线；
云上规模变大，所以要 CloudOps。
```

### 八个阶段

| 阶段 | 核心问题 | 引出内容 | 归属 |
|------|---------|---------|------|
| **单体期** | 部署慢、扩容粗、故障影响面大 | 负载均衡、读写分离、缓存 | 云原生 |
| **边界期** | 乱拆变成分布式单体 | DDD、限界上下文、业务能力拆分 | 微服务 |
| **微服务期** | 服务之间怎么通信 | REST/gRPC/MQ、API 网关 | 微服务 |
| **治理期** | 地址、配置、故障、链路失控 | 注册发现、配置中心、熔断、链路追踪 | 微服务 |
| **一致性期** | 拆库后数据正确性要重新设计 | 幂等、分布式锁、TCC、EDA | 微服务 |
| **容器期** | "我机器上能跑"、环境不一致 | Docker、12-Factor、无状态 | 云原生 |
| **编排期** | 容器多了人工管不过来 | K8s、HPA、声明式配置 | 云原生 |
| **云原生期** | 交付、运维、成本、安全要体系化 | CI/CD、GitOps、FinOps、Serverless | 云原生 |

### 故事线三：从数据孤岛到数据底座（多元异构数据集成）

覆盖**多元异构数据集成**（`0002-多元异构数据集成/`）专题的故事线。

### 核心记忆线

```
识异构，选路线；
元数据，对字段；
主数据，统语义；
质量六维，保可信；
湖仓演进，抗漂移；
分片反压，扛规模；
契约血缘，做治理。
```

### 七个阶段

| 阶段 | 核心问题 | 引出内容 | 记忆钩子 |
|------|---------|---------|---------|
| **孤岛期** | 数据分散在 5 套异构系统，老板要看全球库存汇总 | 异构四层次、ETL/CDC/联邦/平台组合选型 | **不先识别异构，就无法正确选型** |
| **格式期** | 80+ 供应商三种报文格式，Flink 流水线 NPE 崩溃 | 元数据驱动、MDH 五层、Schema Registry | **转换逻辑不进代码，进元数据表** |
| **语义期** | 财务报表差 150 万——三套系统"销售额"定义不同 | MDM、Golden Record、LLM 语义对齐 | **格式统一靠映射，意思统一靠标准** |
| **质量期** | 库存负数、邮箱"asdf@"、订单重复 3 条 | 数据质量六维度、死信队列、DQC 监控 | **垃圾进垃圾出——脏数据不进湖** |
| **湖仓期** | 供应商静默改字段名，流水线停摆 4 小时 | 湖仓一体、Iceberg Schema Evolution、Schema Drift 自愈 | **上游一定会变，系统必须能自愈** |
| **规模期** | 黑五 TPS 80K，Kafka Partition 全满、小文件爆炸 | Lambda 架构、数据分片、反压、多模型数据管理 | **规模问题不是一个问题，是吞吐、存储和模型一起变大** |
| **治理期** | CTO 四问管道/血缘/合规，无人能答 | Data Contracts、Data Mesh、安全合规、数据血缘 | **平台建好了，治理跟上才算完** |

### 故事线四：从批处理到湖仓一体（大数据架构）

覆盖**大数据架构**（`0010-大数据架构/`）专题的故事线。

### 核心记忆线

```
批太慢，建实时；
快不准，走 Lambda；
吞吐高，治背压；
分布偏，解倾斜；
关联慢，做异步；
一致难，补湖仓；
成本高，精细算。
```

### 七个阶段

| 阶段 | 核心问题 | 引出内容 | 记忆钩子 |
|------|---------|---------|---------|
| **批处理期** | Hive 跑 6 小时，库存超卖 3000 单 | 批 vs 流对比、Lambda 架构必要性 | **离线批处理只能算昨天** |
| **实时期** | 30 万 TPS 涌入，热路径 2 秒出结果但冷路径对账差 0.05% | Lambda 三层、Flink CDC、Watermark、OLAP 选型 | **快和准不能兼得，所以冷热双路径** |
| **背压期** | Checkpoint 超时 30 分钟，反压从 Sink 传到 Source | Credit-Based、Unaligned CK、State 后端 | **反压不治，全链阻塞** |
| **倾斜期** | 某热门商品 Key 独占 CPU 95% | 两阶段加盐聚合、热点 Key 检测 | **数据倾斜不是算法问题，是分布问题** |
| **关联期** | 5000 万用户画像实时 JOIN，延迟 150ms | Async I/O + Redis、Broadcast State | **实时 JOIN 等不起，必须异步化** |
| **一致性期** | 两套代码维护成本高、凌晨 3 点对账复杂 | Exactly-Once 四段、Iceberg 试点 | **快和准最终要对账，双链太重就走向统一** |
| **成本期** | 数据量翻 5 倍、存储成本翻 8 倍 | RocksDB 调优、Zstd 压缩、K8s 弹性、全链路压测 | **规模越大，每一分算力都要精打细算** |

### 为什么故事线有效

1. **因果链清晰**：每个阶段都是因为"吃了亏"才引入新技术，不是凭空罗列
2. **记忆钩子强**：每章结尾一句话总结核心，考场快速调取
3. **论文可直接用**：每章的"论文句式"可以直接改写进论文正文
4. **全局视角**：不是孤立的知识点，而是一条时间线，知道"现在在哪里，接下来是什么"

## 五、论文写作通用公式

### 摘要（300-400 字）

```
项目背景（150 字）→ 核心论点（150 字）
```

### 正文结构（2700+ 字）

```
引言与背景（500 字）→ 核心技术方案（800 字）→ 实施细节（600 字）→ 效果与总结（400 字）
```

### 每个论点的三段式

```
理论说明（是什么）→ 实际应用（怎么做的）→ 效果说明（结果如何）
```

### 量化指标三件套

| 指标类型 | 示例 |
|---------|------|
| **技术指标** | TPS 从 3000 提升至 30000、P99 延迟从 2000ms 降至 150ms |
| **业务指标** | 订单转化率从 2.3% 提升至 3.8%、用户流失率降低 10% |
| **成本指标** | 服务器数量从 100 台降至 40 台、月度云资源成本降低 60% |

## 六、如何使用本仓库准备论文

### Step 1：确定要准备的专题

根据考点频率，优先准备 P0 级专题：**软件维护、SOA、数据集成、云原生、微服务**。

### Step 2：阅读顺序

```
01-核心知识点.md → 05-故事线.md（如有）→ 02-论文写作框架.md → 03-论文范文.md
```

1. 先看 `01-核心知识点` 了解技术全貌
2. 如果有 `05-故事线`，用它建立"为什么需要"的因果记忆
3. 再看 `02-写作框架` 掌握论文结构
4. 最后看 `03-范文` 学习具体表达

### Step 3：准备自己的项目素材

每个专题的写作框架都提供了摘要模板和量化指标。你需要：

- **准备 1-2 个真实项目**：名称、规模、个人角色、遇到的问题
- **准备量化数据**：优化前后的具体数值
- **准备技术细节**：用了什么工具、做了什么决策、遇到什么困难、怎么解决的

### Step 4：限时练习

考试要求 120 分钟内完成 3000+ 字。建议每周至少做一次限时写作练习。

## 七、故事线文档的扩展方向

目前已有**测试专题**、**云原生+微服务合并专题**、**多元异构数据集成专题**和**大数据架构专题**四个故事线文档。后续可以为其他专题创建类似的故事线：

| 专题 | 可能的故事线标题 | 主线 | 状态 |
|------|----------------|------|------|
| **微服务** | 《从单体到云原生：微服务与平台化架构演进故事线》 | 单体太重→拆→治→容器化→编排→CloudOps | ✅ 已完成（与云原生合并） |
| **云原生** | 《从单体到云原生：微服务与平台化架构演进故事线》 | 单体太重→拆→治→容器化→编排→CloudOps | ✅ 已完成（与微服务合并） |
| **多元异构数据集成** | 《从数据孤岛到数据底座：多元异构数据集成的觉醒与治理》 | 识异构→对字段→统语义→保可信→抗漂移→扛规模→做治理 | ✅ 已完成 |
| **大数据架构** | 《从批处理到湖仓一体：大数据架构的演进故事线》 | 批太慢→快不准→治背压→解倾斜→做异步→补湖仓→精细算 | ✅ 已完成 |
| **软件维护** | 《上线只是开始：系统的生命周期管理》 | Bug 修复 → 功能增强 → 性能优化 → 架构重构 → 技术债务清理 | 待创建 |

故事线的核心价值：**把孤立的技术概念变成一条"吃了亏→引入新技术→问题解决"的因果链**，让记忆和写作都更自然。
