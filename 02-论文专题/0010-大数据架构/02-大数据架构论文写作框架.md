# 大数据架构论文写作框架

> 本框架按数据时效、准确性、重算能力和成本组织，不再强制五段、固定字数或把某一种架构描述为普遍最优。

## 一、适用题型

- 论大数据架构及其应用；
- 说明批处理、流处理、Lambda、Kappa 或湖仓一体；
- 说明 CDC、事件时间、Watermark 和 Exactly-Once；
- 说明背压、数据倾斜、实时关联和存储治理；
- 结合项目说明架构选型、实施难点和效果。

## 二、审题映射

| 题目要求 | 必须回答 |
|----------|----------|
| 架构模式 | 核心链路、适用场景、优势和代价 |
| 流处理 | 事件时间、状态、窗口、Watermark 和迟到数据 |
| 一致性 | Source、状态、Sink、幂等、事务和外部副作用 |
| 问题治理 | 背压、倾斜、关联、小文件、Schema 和补数 |
| 项目实践 | 业务问题、架构决策、容量证据和指标 |

## 三、推荐结构

```text
摘要
→ 项目数据量、实时性问题和本人职责
→ 批流、Lambda/Kappa/湖仓的选型
→ 数据采集、处理、存储和服务架构
→ 项目实践：背压、倾斜、一致性或关联
→ 效果、治理成本和演进
```

## 四、架构模式比较

| 架构 | 核心思路 | 优势 | 主要代价 | 适用判断 |
|------|----------|------|----------|----------|
| 批处理 | 周期处理有界数据 | 吞吐高、逻辑清晰、便于重算 | 延迟高 | T+1、历史分析和全量校验 |
| 流处理 | 持续处理无界事件 | 低延迟、事件驱动 | 状态、乱序和一致性复杂 | 监控、风控和实时服务 |
| Lambda | 批路径与实时路径并存 | 可用全量路径校正实时结果 | 双链代码和运维成本 | 实时与全量重算都重要 |
| Kappa | 统一流处理，通过事件日志重放 | 一套处理模型 | 依赖完整日志和状态演进 | 流计算成熟、事件可重放 |
| 湖仓一体 | 对象存储与开放表格式，多引擎访问 | 统一数据基础、ACID 和 Schema 演进 | 元数据、并发写和兼容治理 | 需要批流共享和多引擎处理 |

不要写成“Lambda 一定准确、Kappa 一定不准确”或“湖仓自动消除所有双链问题”。准确性取决于数据源、处理逻辑、状态和写入协议。

## 五、数据链路

```text
业务数据库、日志和外部事件
→ CDC 或采集代理
→ Kafka/Pulsar 等持久化事件日志
→ Flink 等流处理引擎
→ 实时 OLAP、缓存、搜索或告警
→ 湖仓表或数据湖保存可重算数据
→ 离线校验、补数和分析服务
```

### 5.1 CDC

- 初始快照与增量日志无缝衔接；
- 保存位点并处理重放；
- 处理主键、删除、事务和 DDL；
- 下游处理重复、乱序和 Schema 演进；
- 账号遵循最小权限并保护敏感数据。

## 六、事件时间与 Watermark

| 概念 | 含义 |
|------|------|
| 事件时间 | 业务事件实际发生时间 |
| 处理时间 | 事件到达计算节点的时间 |
| Watermark | 系统对事件时间进度的估计 |
| 允许迟到 | 窗口完成后仍接受更新的范围 |
| 侧输出/补偿 | 处理超过允许迟到范围的数据 |

允许迟到越长，结果可能更完整，但状态、延迟和资源成本越高。论文应结合业务说明选择依据。

## 七、端到端一致性

Checkpoint 只保证计算状态能够一致恢复，不自动等于端到端 Exactly-Once。

```text
可重放或事务化 Source
+ 一致状态快照
+ 事务提交或幂等 Sink
+ 稳定业务主键与去重
+ 外部副作用协调或补偿
```

| 环节 | 典型机制 |
|------|----------|
| Source | Kafka Offset 与 Checkpoint 协调、CDC 位点 |
| State | Checkpoint、Savepoint 和状态后端 |
| Sink | 两阶段提交、事务写、幂等 Upsert 或去重 |
| 外部调用 | 幂等键、Outbox、补偿任务 |
| 验证 | 对账、质量规则、血缘和重算 |

Exactly-Once 不等于业务数据绝对零误差，还需要数据质量和对账。

## 八、问题治理

### 8.1 背压

```text
现象：消费 Lag 增长、Checkpoint 超时
→ 定位反压算子
→ 区分 CPU、网络、状态、序列化和外部 Sink
→ 优化慢算子、批量写或 Async I/O
→ 再决定是否增加并行度和资源
→ 验证 Lag、吞吐和 Checkpoint
```

盲目增加 Source 并行度可能让下游更快过载。

### 8.2 数据倾斜

```text
现象：少数 Subtask CPU 95%，其他空闲
→ 识别热点 Key 与分区策略
→ 热点加盐和局部聚合
→ 二次全局聚合
→ 验证负载分布和结果正确性
```

加盐增加状态和二次聚合成本，只对确认热点使用。

### 8.3 实时关联

- 小维表可使用 Broadcast State；
- 大维表可使用 Async I/O；
- 配置超时、并发上限、缓存和降级；
- 维表更新需要版本和一致性策略；
- 外部系统不可用时避免无限重试拖垮主链。

### 8.4 小文件和存储

- 控制写入并行度和文件滚动；
- 定期 Compaction；
- 使用分区裁剪和列式格式；
- 建立冷热分层和压缩策略；
- 评估对象存储请求、元数据和状态恢复成本。

### 8.5 Schema 与数据治理

- Schema Registry 和表格式管理版本与兼容；
- 业务语义变化需要数据契约和负责人审批；
- 记录血缘、质量、数据新鲜度和补数流程；
- 通过重算和对账修复历史数据。

## 九、项目实践框架

### 9.1 离线延迟

```text
问题：报表延迟 4—8 小时，库存和风控无法实时响应
→ 候选：提高批次频率、Lambda、Kappa 和统一流式链路
→ 决策：根据重算、准确性和团队能力选择
→ 实施：CDC、事件日志、流处理和实时服务
→ 验证：数据可见延迟和查询 P99
```

### 9.2 Checkpoint 超时

```text
问题：Checkpoint 30 分钟或超时
→ 证据：反压链、状态大小和 Sink 延迟
→ 方案：优化慢算子、状态后端、增量快照和 Sink
→ 风险：资源成本和恢复时间
→ 验证：Checkpoint、Lag 和故障恢复
```

### 9.3 热点 Key

```text
问题：热门商品 Key 独占资源
→ 方案：热点检测、加盐、局部聚合和再聚合
→ 风险：状态增大和结果延迟
→ 验证：Subtask 负载和正确性
```

### 9.4 端到端一致性

```text
问题：故障恢复后重复写或漏写
→ 方案：Source 位点、状态快照、事务/幂等 Sink、业务主键和对账
→ 验证：故障注入、重复率、差异率和补数时间
```

## 十、模拟指标口径

| 指标 | 改造前 | 改造后 |
|------|--------|--------|
| 数据可见延迟 | 4—8 小时 | 少于 2 秒 |
| 实时查询 P99 | 无实时服务 | 少于 100ms |
| 峰值处理能力 | 3 万 TPS | 30 万 TPS |
| 对账差异 | 0.5% | 少于 0.01% |
| Checkpoint 时间 | 30 分钟或超时 | 少于 2 分钟 |
| 热点算子 CPU | 95% | 60%—70% |
| 存储成本 | 基线 | 降低 35% |

均为训练模拟数据，应与记忆卡、范文和故事线一致。

## 十一、摘要与总结

### 摘要

```text
项目数据量和时效问题
→ 架构选型与核心链路
→ 一致性和问题治理重点
→ 主要效果
→ 本文回应的题目要求
```

### 总结

```text
回扣实时性、准确性和重算目标
→ 给出延迟、吞吐和差异指标
→ 说明状态、双链和成本不足
→ 给出湖仓、治理和容量演进
```

## 十二、检查单

- [ ] 架构选型与实时性、准确性和重算要求匹配
- [ ] Lambda、Kappa 和湖仓比较未绝对化
- [ ] 事件时间、Watermark 和迟到数据准确
- [ ] Checkpoint 未被直接等同端到端 Exactly-Once
- [ ] 背压先定位根因，再优化或扩容
- [ ] 数据倾斜说明热点识别和二次聚合代价
- [ ] 包含 Schema、质量、血缘、对账和补数
- [ ] 模拟指标与记忆卡和范文一致
- [ ] 能在规定时间内用纯文字完成
