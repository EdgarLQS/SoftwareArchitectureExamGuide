# 云原生范文训练评价 v2

> 评估对象：`03-云原生论文范文-改写版.md`
>
> 评价性质：内部训练复盘，非官方评分。原 `71/75` 已取消。

## 一、总体判断

当前等级：**usable（可用）**。

优点：

- 能从部署、扩容和故障恢复问题引出云原生改造；
- 覆盖容器、编排、持续交付、可观测和弹性；
- 具备应用无状态化、灰度和治理的基本素材；
- 可迁移到容器化、Kubernetes、DevOps 和平台工程类题目。

主要风险：

- 把“容器、微服务、DevOps、持续交付”写成唯一固定四大支柱；
- 应用扩容未充分考虑数据库、缓存和外部依赖的容量上限；
- 探针、PDB、资源配置和自动扩容的边界不够准确；
- “服务器减少即成本同比下降”缺少账单和托管服务分析；
- 99.99% 可用性等指标缺少故障预算和验证证据；
- 项目数据属于模拟场景，原文标注不足。

## 二、技术审查

| 主题 | 状态 | 修订建议 |
|------|------|----------|
| 云原生定义 | 待修订 | 改为能力集合，不宣称唯一“四大支柱” |
| 容器化 | 可用 | 增加镜像供应链、不可变制品和状态外置 |
| Kubernetes | 可用 | 区分 Startup、Readiness 和 Liveness 探针 |
| HPA | 待加强 | 结合业务指标、冷启动和下游饱和度 |
| 数据层容量 | P0 | 增加连接池预算、数据库代理和保护阈值 |
| 持续交付 | 可用 | 增加制品晋级、契约兼容、灰度和回滚 |
| 可观测性 | 待加强 | 从工具清单升级为 SLI/SLO 和业务指标关联 |
| 成本 | 待修订 | 使用总拥有成本、资源利用和账单验证 |
| 模拟数据 | 待统一 | 与记忆卡和框架保持同一基线 |

## 三、关键修订

### 3.1 扩容预算

```text
最大 Pod 数 × 每 Pod 最大连接数
≤ 数据库允许的连接预算
```

应用扩容可能放大数据库、缓存、消息和外部 API 压力。HPA 不应只看 CPU，需要结合请求率、队列长度、延迟和下游饱和度。

### 3.2 健康检查

- Startup：应用是否已经完成启动；
- Readiness：实例是否可以接收流量；
- Liveness：实例是否需要重启；
- 探针配置错误可能造成重启风暴和流量抖动。

### 3.3 高可用

高可用不仅是多副本，还需要：

- 多故障域调度；
- PDB 与维护策略；
- 超时、熔断和隔离；
- 数据层备份、恢复和容灾；
- 发布期间容量预留；
- 演练和 SLO 误差预算。

## 四、模拟指标建议

| 指标 | 改造前 | 改造后 |
|------|--------|--------|
| 发布频率 | 每周 1 次 | 每天 20+ 次 |
| 部署时间 | 30 分钟 | 少于 2 分钟 |
| 扩容响应 | 数小时 | 60 秒 |
| 实例恢复 | 人工处理 | 45 秒内自动替换 |
| 可用性 | 99.5% | 99.99% |
| 资源利用率 | 20% | 65% |
| 数据库连接使用率 | 100% | 45% |

成本变化单独记录，不从服务器数量直接推导。

## 五、优先修订清单

- [ ] 标记项目和指标为模拟数据
- [ ] 将固定“四大支柱”改为云原生能力模型
- [ ] 补充应用扩容与数据库连接预算
- [ ] 修正三类探针和 PDB 的使用边界
- [ ] 使用 SLI/SLO 验证可用性和性能
- [ ] 补充镜像供应链、Secret 和权限治理
- [ ] 用账单和总拥有成本验证成本效果
- [ ] 核对记忆卡、框架和范文全部指标

## 六、提升为 stable 的条件

```text
云原生能力与题目要求匹配
弹性设计包含下游容量约束
高可用覆盖应用和数据层
发布与回滚流程完整
指标有可验证依据
限时迁移写作无重大遗漏
```
