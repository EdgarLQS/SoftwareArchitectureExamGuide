> 软考架构师论文专题 | 适用考试：系统架构设计师（2026 年 5 月）
>
> 阅读方法：这是一条产品从小到大的架构风格选型线。每个阶段都是一个"吃了亏→引入新风格→问题解决"的因果故事。故事帮你记住**为什么需要这种风格**，具体知识点可跳转 `01-软件架构风格核心知识点.md`、`02-软件架构风格论文写作框架.md`。

## 核心记忆线

```
分层解决职责秩序，仓库承载统一数据；
读写分离缓解 I/O 竞争，管道-过滤器治理异构接入；
缓存补偿一致性延迟，降级熔断守住可用性；
事件驱动削峰解耦，规则引擎承接频繁变化；
最后用 ATAM 说明混合风格的敏感点和权衡点。
```

一条线串起 Garlan & Shaw 五大分类中的所有子风格。每个阶段的结尾都有一句"论文记忆钩子"，帮助你在考场上快速调取知识。

### 背诵版

```
分层立秩序，仓库管数据；
读写抗压力，管道治异构；
缓存补延迟，降级保可用；
事件解耦合，规则管变化；
ATAM 做权衡。
```

### 论文口径版（可直接用于摘要/正文）

> 项目初期采用层次结构风格快速交付，随着数据规模和供应商接入量增长，依次引入仓库风格的读写分离变体解决 I/O 竞争、管道-过滤器风格治理异构报文接入、事件驱动风格实现异步削峰，以及虚拟机风格的规则引擎应对频繁变化的业务规则。最终通过 ATAM 方法系统化评估各质量属性的敏感点与权衡点，形成仓库风格 + 管道-过滤器 + 事件驱动 + 虚拟机风格的混合架构体系。

## 贯穿设定

- **项目**：全球跨国物流追踪平台
- **角色**：你作为系统架构师
- **团队**：产品经理、开发负责人、测试负责人、运维负责人
- **业务演进**：50 家供应商 / 日均百万级轨迹数据 → 200+ 家 / 日均 5000 万级轨迹数据
- **风格映射红线**（每个阶段都需回看这张表）：

| 技术实现 | 对应的 Garlan & Shaw 架构风格 |
|---------|-----------------------------|
| 分层 Web 应用 | 调用/返回 → 层次结构风格 |
| MySQL 主从读写分离 | 数据中心 → 仓库风格（变体） |
| ACL 数据清洗链路 | 数据流 → 管道-过滤器风格 |
| Kafka 异步投递 | 独立构件 → 事件驱动风格 |
| 规则引擎 / 状态码映射 | 虚拟机 → 解释器/规则系统 |

> **全文底线**：架构风格不是技术栈，而是构件、连接件和约束的组织方式。每章都先说风格，再说技术；先说质量属性矛盾，再说实现方案。

## 第一阶段 · 幼年期：先用分层把系统立起来

### 故事场景

创业团队花了三个月做出了物流追踪平台 V1.0。

系统采用经典的三层架构：表示层（Spring MVC Controller）→ 业务逻辑层（Service）→ 数据访问层（DAO + MySQL）。50 家物流供应商接入，日均百万级轨迹数据。

上线第一个月，一切顺利。

老板在周会上表扬："系统很稳，用户反馈也不错。"

但变化来得很快。

半年后，供应商从 50 家增长到 200+ 家，日均轨迹数据从百万级飙升到 5000 万级。问题接踵而至：

- 快递员刚扫完包裹的条形码，用户立刻在手机上查——"无数据"。
- 数据库 CPU 持续 95%，连接池频繁爆满，日志里全是"Too many connections"。
- 客服每天收到 200+ 起用户投诉："轨迹更新太慢了""查不到最新物流"。
- 表示层想加一个"最近查询"缓存功能，但层次结构约束（禁止跨层调用）让实现变得异常别扭。

开发负责人抱怨："我们的代码结构没问题啊，三层分得很清楚。"

运维负责人摇头："结构清楚不代表能扛住 5000 万条数据。"

### 问题本质

**层次结构风格解决了关注点分离（职责分离），但没有解决数据 I/O 竞争。**

层次结构风格的构件是"层"，连接件是"层间接口"，核心约束是"只能调用直接下层，禁止跨层调用"。这个约束在早期保证了系统的秩序——表示层不直接碰数据库，业务层统一处理逻辑。

但当所有读写操作争抢同一个中央仓库（MySQL 单实例）时，层次结构不仅帮不上忙，其跨层禁止约束反而成为灵活性的限制。

层次结构风格的质量属性特征是：**安全性最优（边界集中管控），但性能最差（需逐层穿越）**。当数据规模上来后，"有序"变成了"有序地慢"。

### 引出的风格与战术

这个阶段我们接触到了 **调用/返回风格（Call/Return）** 下的三个子风格：

**层次结构风格（Layered）**：

| 特征 | 描述 |
|------|------|
| 构件 | 层（Layer）：表示层、业务层、数据访问层 |
| 连接件 | 层间接口：方法调用、DTO/VO 传递 |
| 约束 | 只能调用直接下层，禁止跨层 |
| 适用场景 | Web 应用、企业信息系统 |
| 优点 | 关注点分离、每层可独立替换、安全性高 |
| 缺点 | 逐层穿越导致性能开销、跨层功能实现困难 |

**主程序-子程序风格（Main Program & Subroutine）**（对照理解）：

| 特征 | 描述 |
|------|------|
| 构件 | 主程序、子程序（函数/过程） |
| 连接件 | 显式方法调用、参数传递 |
| 控制流 | 同步调用，调用者等待返回值 |
| 缺点 | 紧耦合、扩展困难、单点故障影响全局 |

层次结构本质上是对主程序-子程序风格的改进——将子程序组织成有秩序的层，但仍未解决底层数据访问的瓶颈。

**质量属性 × 风格映射（本节重点记忆）**：

| 质量属性 | 层次结构表现 | 原因 |
|---------|------------|------|
| 安全性 | 最优 | 可在层边界集中管控 |
| 可测试性 | 中等 | 层内可独立测试，但层间依赖复杂 |
| 性能 | 最差 | 请求需逐层穿越 |
| 可修改性 | 中等 | 层内修改影响范围可控，但跨层修改困难 |

### 关键指标

| 指标 | 数值 | 说明 |
|------|------|------|
| P99 延迟 | 300ms → 8s+ | 数据规模增长后的劣化 |
| 主库 CPU 利用率 | 95% | 读写竞争导致 |
| 连接池利用率 | 98%（频繁溢出） | "Too many connections" |
| 系统可用性 | 99.5% | 每月宕机数小时 |
| 用户投诉 | 200+ 起/天 | 轨迹查询不到 |

### 架构师视角

在这个阶段，我认识到：

1. **层次结构风格是起点，不是终点。** 它解决了系统早期的职责秩序问题，但面对数据规模增长时，必须引入其他风格来补强。
2. **风格选择的第一步是识别瓶颈。** 当前的瓶颈不是代码结构混乱（层次已经很好了），而是所有读写操作竞争同一个数据实例。这需要从数据中心化的角度思考解决方案。
3. **质量属性之间存在天然矛盾。** 层次结构在安全性上表现最优，但在性能上表现最差。当性能成为首要矛盾时，必须引入新的风格。

### 论文句式

> "项目初期采用层次结构风格（Layered Style）快速交付，系统组织为表示层、业务逻辑层和数据访问层。该风格保证了关注点分离和系统秩序，但随着供应商从 50 家增长到 200+ 家、日均轨迹数据从百万级增长到 5000 万级，层次结构风格的性能缺陷暴露——所有读写操作竞争同一个 MySQL 实例，P99 延迟从 300ms 劣化到 8 秒以上，主库 CPU 持续 95%。层次结构风格在安全性上表现最优，但在性能上表现最差，当性能成为首要矛盾时，必须引入新的架构风格。"

### 论文记忆钩子

> **分层解决秩序，不解决规模。**

## 第二阶段 · 压力期：一个数据库扛不住读写竞争

### 故事场景

架构评审会上，你画了一张图：

```
所有请求 ──→ 同一个 MySQL 实例
              ├── 写入：INSERT/UPDATE 轨迹数据
              ├── 查询：用户实时查物流
              ├── 报表：运营导出 Excel
              └── 分析：BI 跑数据看板
```

"读写全打在一个实例上，就像一条高速公路只有一个车道。"你说，"需要把读写分开。"

方案确定：引入 MySQL 主从复制。1 个主库（16C32G SSD，专注写入）+ 3 个从库（各 16C32G，分别服务实时查询、报表导出、BI 分析）。

实施后效果立竿见影：

- 主库 CPU 从 95% 降到 45%。
- QPS 从 500 提升到 3000。
- 连接池利用率恢复正常。

团队刚松了口气，新的问题来了。

快递员小李在仓库扫完一个包裹的条形码，写入主库成功。用户小王在手机上刷新——"无轨迹信息"。

小李："我明明扫了！"
小王："就是查不到！"

排查发现：主库写入成功，但 Binlog 异步同步到从库需要 500ms-2s。用户在这 2 秒的时间窗口内查询从库，自然看不到数据。

运维负责人看着监控："Seconds_Behind_Master 在 500ms 到 2s 之间波动，高峰期更高。"

### 问题本质

**仓库风格的本质是组件通过中央数据存储间接交互。** 读写分离是仓库风格的变体——将仓库拆为主库（Master）和从库（Slave），通过异步同步机制（Binlog）保持数据一致。

读写分离解决了 I/O 竞争（磁盘级、内存级、连接级三层隔离），但异步同步带来了不可避免的主从延迟。这本质上是 **CAP 定理中一致性（C）与可用性（A）的权衡**。

在物流追踪场景中，"系统不崩溃"远比"数据绝对实时"重要。我们选择了 AP（可用性 + 分区容错性），接受最终一致性。但主从延迟带来的"扫码后查不到"问题，必须通过额外的战术来补偿。

> **风格澄清**：读写分离是仓库风格的变体，不是独立的新风格。其构件是数据存储（Master/Slave），连接件是数据访问接口，约束是组件间不直接通信。

### 引出的风格与战术

**仓库风格（Repository Style）**：

| 特征 | 描述 |
|------|------|
| 构件 | 数据存储（Data Store）：主库、从库 |
| 连接件 | 数据访问接口：SQL 查询、ORM 映射 |
| 约束 | 组件间不直接通信，全部通过仓库间接交互 |
| 适用场景 | 数据库系统、物流追踪系统、企业信息系统 |

**读写分离的 I/O 隔离三层机制**：

| 隔离层 | 原理 | 解决的问题 |
|--------|------|-----------|
| 磁盘级 | 主库专注顺序写（Sequential Write），从库专注随机读（Random Read） | 消除 B+ 树索引维护与查询扫描的磁盘头竞争 |
| 内存级 | 从库 Buffer Pool 长期驻留高频查询页 | 提升缓存命中率，从磁盘级降至内存级响应 |
| 连接级 | 写连接池与读连接池物理隔离 | 防止复杂 SQL 阻塞实时写入 |

**CAP 定理在仓库风格中的体现**：

| 方案 | 一致性 | 可用性 | 本项目选择 |
|------|--------|--------|-----------|
| 强一致性（同步复制） | 最高 | 最低（写入需等待所有从库确认） | 不选 |
| 最终一致性（异步复制） | 中等 | 最高（写入立即返回） | **选择 AP** |

**牺牲的质量属性**：选择读写分离后，**牺牲了一致性（实时性），换取了可用性和性能**。这是仓库风格在物流追踪场景下的合理权衡——用户延迟几秒看到数据，远比系统完全不可用的影响小。

### 关键指标

| 指标 | 优化前 | 优化后 | 说明 |
|------|--------|--------|------|
| 主库 CPU 利用率 | 95% | 45% | 下降 50 个百分点 |
| QPS | 500 | 3,000 | 6 倍提升 |
| 主从同步延迟 | N/A | 500ms-2s | 异步同步的必然代价 |
| 查询 P99 | 8s | 2s | 仍不理想，需进一步补偿 |
| 连接池利用率 | 98%（溢出） | 60%（稳定） | 下降 38 个百分点 |

### 架构师视角

在这个阶段，我做了以下决策：

1. **选择仓库风格的读写分离变体而非分库分表。** 分库分表能全方位扩展，但对于 15 人团队和当前业务阶段来说复杂度过高。读写分离在"解决问题"和"引入复杂度"之间取得了最优平衡。
2. **明确 CAP 选择为 AP。** 在架构决策文档中记录："物流追踪场景中，用户延迟几秒看到轨迹数据的影响远小于系统完全不可用。因此选择异步复制的最终一致性方案。"
3. **I/O 隔离必须三层都做。** 仅做主从分离而不做磁盘级/内存级/连接级的隔离，效果大打折扣。SSD 给主库、HDD 给从库是性价比最高的磁盘级隔离方案。
4. **主从延迟是必须面对的副作用。** 异步同步的物理限制无法消除，只能通过缓存补偿来遮掩。这是下一阶段要解决的问题。

### 论文句式

> "针对读写 I/O 竞争瓶颈，我引入了仓库风格（Repository Style）的读写分离变体。将单一 MySQL 实例拆分为 1 个主库（16C32G SSD，专注写入）和 3 个从库（各 16C32G，分别服务实时查询、报表导出和 BI 分析），通过 Binlog 异步同步保持数据一致。主库 CPU 从 95% 降至 45%，QPS 从 500 提升至 3000。在 CAP 定理中选择了 AP（可用性优先），接受最终一致性，因为'系统不崩溃'比'数据绝对实时'对物流业务更重要。但异步同步带来了 500ms-2s 的主从延迟，需要通过缓存补偿来解决。"

### 论文记忆钩子

> **仓库集中数据，也集中压力。**

## 第三阶段 · 接入期：200 家供应商格式各不相同

### 故事场景

读写分离稳定运行两周后，业务部门引入了第 150 家物流供应商——某国国家邮政。

开发小王花了两天时间对接：

- 对方用的是 XML 格式，而系统之前只处理 JSON。
- 状态码体系完全不同：对方的"3"表示"运输中"，而 DHL 的"3"表示"已签收"。
- 时区是当地时间，不是 UTC。
- 字符集是 ISO-8859-1，不是 UTF-8。

小王把这些适配逻辑直接写进了业务层的 Service 里。代码变成了这样：

```java
if (supplier.equals("DHL")) {
    // JSON 解析，状态码 1=IN_TRANSIT
} else if (supplier.equals("FEDEX")) {
    // JSON 解析，状态码 2=IN_TRANSIT
} else if (supplier.equals("ChinaPost")) {
    // XML 解析，状态码 3=IN_TRANSIT
} else if (supplier.equals("USPS")) {
    // EDI 解析...
}
// ... 200+ 个 else if
```

一个月后，问题爆发了。

- 一次错误的 JSON 解析（某供应商在报文里加了个 emoji）导致整个 Service 层 NPE，系统宕机 20 分钟。
- 新供应商接入平均需要 2 天——改代码、回归测试、重新部署。
- 业务层的代码里混杂了 3000+ 行数据解析逻辑，核心业务逻辑被淹没。

开发负责人在复盘会上说："异构数据的解析逻辑不应该和业务逻辑混在一起。"

你说："数据应该先清洗，再入仓库。异构数据不应该污染业务层。"

### 问题本质

**当不同格式的数据直接进入业务层，业务层就被污染了。**

层次结构风格中，表示层→业务层→数据层的链路是清晰的。但"数据从哪来、长什么样"这个问题，层次结构没有回答。200+ 家供应商的异构报文（JSON、XML、EDI、CSV）直接进入业务层，相当于把外部系统的复杂性直接注入了内部核心模型。

**管道-过滤器风格**通过独立的过滤器（Filter）串联成数据处理管道（Pipe），每个过滤器只关注一种转换职责，过滤器之间通过标准数据接口传递归一化后的数据。这样，异构数据在进入仓库之前就被清洗、归一化、校验完毕。

ACL 防腐层（Anti-Corruption Layer）是管道-过滤器风格在本项目中的**落地载体**——它不是一个独立的架构风格，而是管道-过滤器风格在异构系统集成场景下的具体实现方式。

> **风格澄清**：管道-过滤器属于**数据流风格**，其构件是独立过滤器，连接件是数据管道/缓冲区。ACL 防腐层是设计模式层面的实现方式，不是 Garlan & Shaw 标准风格。

### 引出的风格与战术

**管道-过滤器风格（Pipe & Filter）**：

| 特征 | 描述 |
|------|------|
| 构件 | 过滤器（Filter）：独立的数据变换单元 |
| 连接件 | 管道（Pipe）：数据缓冲区/通道 |
| 控制流 | 数据驱动——有数据即触发处理 |
| 适用场景 | 实时数据清洗、日志处理管线、异构报文归一化 |
| 优点 | 高内聚低耦合、过滤器可复用、支持并行 |
| 缺点 | 数据转换开销、共享上下文困难、错误处理复杂 |

**管道-过滤器 vs 批处理序列**（常考对比）：

| 维度 | 批处理序列 | 管道-过滤器 |
|------|-----------|------------|
| 执行方式 | 阶段串行，前阶段完成才进入下一阶段 | 流式并行，过滤器同时运行 |
| 延迟 | 高（等待整个批次完成） | 低（数据逐过滤器流动） |
| 并行性 | 阶段间不可并行 | 过滤器天然并行 |
| 复用性 | 低（阶段定制化） | 高（过滤器通用） |

**ACL 防腐层三层过滤器设计**（管道-过滤器在本项目中的落地）：

| 过滤器层级 | 职责 | 设计模式 | 输入 → 输出 |
|-----------|------|---------|------------|
| Ingest（接入层） | 多协议接入、格式识别、报文接收 | Strategy 策略模式 | 异构报文 → 标准 Raw DTO |
| Mapping（语义转换层） | 数据归一化、状态映射、时区统一 | Adapter 适配器模式 | Raw DTO → 标准领域模型 |
| Validation（校验与异步化） | 数据校验、去重、投递 MQ | Factory Method 工厂模式 | 标准 DO → Kafka Topic / 仓库 |

**质量属性映射**：管道-过滤器风格在**性能上最优**（过滤器可并行执行），在**可测试性上最优**（每个过滤器可独立单元测试）。

**牺牲的质量属性**：管道-过滤器风格在可靠性上表现最差——管道中任一过滤器断裂会导致整条链路崩溃。因此需要配合事件驱动风格来做异步缓冲（这是后续阶段的主题）。

### 关键指标

| 指标 | 优化前 | 优化后 | 说明 |
|------|--------|--------|------|
| 新供应商接入时间 | 2 天（改代码+测试+发版） | 4 小时（新增过滤器+配置） | 效率提升 12 倍 |
| 解析逻辑耦合度 | 20+ 层 if-else 嵌套 | 每个过滤器独立 | 消除隐式依赖 |
| 业务层代码行数 | 包含 3000+ 行解析逻辑 | 仅接收已归一化数据 | 业务层不再被污染 |
| 因解析错误导致的宕机 | 频繁 | 0 | 错误隔离在过滤器内 |

### 架构师视角

在这个阶段，我做了以下决策：

1. **引入管道-过滤器风格作为数据接入层的架构风格。** 将异构报文解析、格式归一化、数据校验拆分为三个独立的过滤器，过滤器之间通过标准数据管道传递归一化后的数据。
2. **以 ACL 防腐层作为管道-过滤器的落地载体。** Ingest 层用策略模式选择解析器，Mapping 层用适配器模式统一格式，Validation 层用工厂方法校验和投递。每个过滤器可独立开发、测试、替换。
3. **管道-过滤器解决的是可修改性和可测试性问题。** 新供应商接入只需新增一个适配器过滤器，不需要改已有代码。每个过滤器可独立单元测试，不再需要全量回归。
4. **管道-过滤器在可靠性上的短板需要后续补强。** 管道中任一过滤器断裂会影响整条链路，因此需要在过滤器之间加入事件缓冲（Kafka），这是后续阶段引入事件驱动风格的伏笔。

### 论文句式

> "针对 200+ 物流供应商异构报文（JSON、XML、EDI）导致业务层被污染的问题，我引入管道-过滤器风格（Pipe & Filter Style）构建数据接入层。以 ACL 防腐层作为落地载体，设计了 Ingest（策略模式选择解析器）、Mapping（适配器模式统一格式）、Validation（校验与异步化）三段过滤器。每个过滤器独立处理一种转换职责，通过标准数据管道传递归一化后的数据。新供应商接入时间从 2 天缩短至 4 小时，因解析错误导致的系统宕机从频繁降至 0。管道-过滤器风格在性能和可测试性上表现最优，但在可靠性上表现最差，需要配合事件缓冲做补强。"

### 论文记忆钩子

> **数据先清洗，再入仓库。**

## 第四阶段 · 补偿期：读写分离带来了数据延迟

### 故事场景

"扫码后 1 秒内必须可查。"产品经理在需求评审会上提出了硬性要求。

但从库延迟 500ms-2s，这个要求无法满足。快递员刚扫完码，用户立刻查，看到的是空白。

你说："主从延迟消除不了，但可以用速度来掩盖它。"

方案：引入 Redis 缓存层，采用 **Cache-Aside 模式**。

- 写入主库的同时，同步写入 Redis。
- 查询优先走 Redis，命中则直接返回（亚毫秒级）；未命中再回源从库，并回填缓存。

效果立竿见影：

- P99 延迟从 2 秒降到 400ms。
- 缓存命中率 95%+。
- 用户投诉从 200+/天降到 30/天。

### 问题本质

**主从延迟无法消除（异步同步的物理限制），但可以通过缓存补偿来"遮掩"。**

Cache-Aside 是仓库风格的**性能补偿战术**——用内存写入的极速性（亚毫秒级）填补 Binlog 同步的时间窗口（500ms-2s）。

> **风格澄清**：缓存（Redis）和 Cache-Aside 模式**不是** Garlan & Shaw 架构风格，而是一种质量属性战术（Performance Tactic）。它们依附于仓库风格，是对仓库风格在性能维度上的补强。

仓库风格（读写分离）牺牲了一致性换取可用性，缓存补偿战术进一步缩小了"不一致的时间窗口"，让用户体验接近实时。

### 引出的风格与战术

**Cache-Aside 模式时序**：

```
写操作路径：
  应用层 → 写入主库 → 主库返回成功
  应用层 → 同步写入 Redis（SET key = data, TTL=3600s）
  主库 → Binlog 异步同步到从库（500ms-2s）

读操作路径：
  应用层 → 查 Redis（GET key）
  ├── 命中 → 直接返回（亚毫秒级）
  └── 未命中 → 查从库 → 回填 Redis → 返回
```

**缓存补偿方案对比**：

| 方案 | 实现方式 | 延迟 | 复杂度 | 推荐度 |
|------|---------|------|--------|--------|
| Cache-Aside（旁路缓存） | 应用层先查缓存，未命中查 DB，写入时更新缓存 | 毫秒级 | 低 | **推荐** |
| Write-Through（写穿） | 写入缓存时同步写入 DB | 低 | 中 | 可选 |
| Write-Behind（写回） | 先写缓存，异步批量写 DB | 高 | 高 | 不推荐 |

**配套战术**：

| 战术 | 作用 | 实现 |
|------|------|------|
| 版本号控制 | 防止旧数据覆盖新数据 | 写入时携带时间戳版本号 |
| TTL 策略 | 控制缓存生命周期 | 热点数据 5min，普通数据 30min |
| TTL 随机偏移 | 防缓存雪崩 | 基础 TTL ± 30% 随机偏移 |

### 关键指标

| 指标 | 优化前 | 优化后 | 说明 |
|------|--------|--------|------|
| 查询 P99 延迟 | 2s | 400ms | 5 倍改善 |
| 缓存命中率 | 0%（无缓存） | 95%+ | 缓存补偿效果 |
| 用户投诉 | 200+/天 | 30/天 | 下降 85% |
| 快递员扫码后可查率 | 60% | 98% | 业务体验大幅提升 |

### 架构师视角

1. **Cache-Aside 是仓库风格的性能补偿战术，不是独立风格。** 在论文中必须说清"缓存是战术，仓库是风格"的层级关系。
2. **读写双写路径保证一致性。** 写入主库和写入 Redis 必须在同一个事务边界内（或通过本地消息表保证最终一致性），否则会出现缓存和数据库不一致。
3. **TTL 随机偏移是必选项。** 如果所有 Key 同时过期，缓存雪崩会瞬间打爆从库。随机偏移是成本最低、效果最好的防护手段。
4. **缓存带来新的依赖。** 系统从"只依赖 MySQL"变成"依赖 MySQL + Redis"。缓存是性能加速器，但也引入了新的故障点——必须有降级方案。

### 论文句式

> "针对读写分离带来的 500ms-2s 主从延迟问题，我引入 Cache-Aside 缓存补偿战术作为仓库风格的性能补强。写入主库时同步写入 Redis，查询优先走缓存，未命中回源从库并回填。配合版本号控制和 TTL 随机偏移策略，查询 P99 延迟从 2 秒降至 400ms，缓存命中率 95%+，用户投诉从 200+/天降至 30/天。Cache-Aside 本身不是架构风格，而是仓库风格的性能补偿战术，用内存写入的极速性填补了 Binlog 异步同步的时间窗口。"

### 论文记忆钩子

> **一致性换可用性，要用缓存补偿。**

## 第五阶段 · 危机期：缓存不是永远可靠

### 故事场景

凌晨 2:47，运维负责人被电话惊醒。

Redis 集群因为内存碎片化 OOM 崩溃了。

所有查询请求瞬间打到从库。从库 CPU 从 40% 飙升到 100%，响应超时。

系统从"95% 的请求在 400ms 内返回"变成"大量请求返回 504"。

运维紧急重启 Redis。但重启后的 15 分钟里，缓存是空的，所有查询都是冷启动，从库持续承受全部压力。

运维负责人在复盘会上问了一个尖锐的问题："如果缓存是系统性能的关键，那缓存挂了怎么办？"

你说："缓存是加速器，不是拐杖。加速器坏了，车还得能开。"

### 问题本质

**引入缓存后，系统的降级能力必须独立于缓存。**

降级、熔断、限流属于**质量属性战术（Availability Tactics）**，不是 Garlan & Shaw 架构风格。它们是仓库风格在性能优化后必须补足的可用性战术——**同一仓库风格在性能优化后，还必须补足可用性战术。**

> **风格澄清**：本章不涉及新架构风格。它是对第二阶段（仓库风格读写分离）和第四阶段（缓存补偿战术）的**可靠性补强**。在论文中，这一部分应放在"仓库风格的实施细节"章节，而非作为独立风格论述。

### 引出的风格与战术

**三级降级架构**：

| 降级层级 | 组件 | 触发条件 | 策略动作 |
|---------|------|---------|---------|
| L1 本地缓存 | Caffeine | Redis 完全不可用时 | 返回本地缓存的最热数据（~1000 条） |
| L2 断路器+限流 | Sentinel | Redis 部分可用或从库延迟 > 5s | 仅 10% 核心查询允许回源从库 |
| L3 主库兜底 | 令牌桶限流 | 从库无数据且为核心业务 | 受控回源主库，上限 100 QPS |

**断路器状态机**：

```
CLOSED（正常）── 失败率超阈值 ──→ OPEN（熔断）
                                    │
                              等待超时后
                                    ↓
                            HALF-OPEN（半开）
                               /        \
                          成功           失败
                            ↓              ↓
                        CLOSED          OPEN
```

**Sentinel 限流规则**：

| 规则类型 | 配置 | 作用 |
|---------|------|------|
| 慢调用比例 | RT > 500ms 的调用占比 > 50% | 触发熔断 |
| QPS 限流 | 从库查询 QPS 上限 3000 | 防止打爆 |
| 线程隔离 | 从库查询线程池 50 线程 | 隔离故障 |

### 关键指标

| 指标 | 数值 | 说明 |
|------|------|------|
| 降级时系统可用性 | 仍保持 99.99% | 三级降级生效 |
| L1 本地缓存覆盖 | ~1000 条最热数据 | Caffeine，TTL 5min |
| L2 限流回源比例 | 仅 10% 查询 | 90% 返回"数据更新中" |
| L3 主库回源上限 | 100 QPS | 令牌桶限流保护 |

### 架构师视角

1. **降级不是风格，是战术。** 在论文中，三级降级应作为仓库风格的实施细节来论述，展示你对质量属性战术的掌握。
2. **断路器的核心是快速失败。** 与其让请求在从库排队等超时（用户等 30 秒后得到一个 504），不如 100ms 内返回"数据更新中"。快速失败本身就是一种用户体验保护。
3. **优雅降级的业务设计比技术实现更重要。** 返回"您的物流数据正在更新中，请稍后刷新"，远比返回 500 错误让用户困惑要好。
4. **每次引入新组件，都要问"它挂了怎么办"。** Redis 挂了→有三级降级。那 Caffeine 挂了呢？进程内的本地缓存几乎不可能单独挂，不需要额外降级。

### 论文句式

> "为防止缓存故障导致系统雪崩，我设计了三级降级架构：L1 本地缓存（Caffeine）返回最热数据约 1000 条；L2 断路器+限流，仅允许 10% 核心查询回源从库；L3 主库兜底，通过令牌桶限流上限 100 QPS。降级生效时系统可用性仍保持 99.99%。降级、熔断、限流属于质量属性战术而非架构风格，是仓库风格在性能优化后必须补足的可用性保障。"

### 论文记忆钩子

> **加速器坏了，也要有刹车。**

## 第六阶段 · 异步期：海量轨迹数据同步写不动

### 故事场景

双十一。

日数据量从日常的 500 万飙升到 5000 万。

ACL 防腐层把异构报文解析成标准格式后，同步写入主库。写入链路变成了新的瓶颈：

- 高峰期报文积压在应用层内存中，GC 频繁触发。
- 部分供应商的 Webhook 因超时而重试，造成数据重复写入。
- 主库写入队列堆积，从库查询延迟从 500ms 飙升到 10s+。

运维在作战室大喊："应用服务器内存快满了！"

开发负责人紧急扩容，但新服务器上线也需要重新部署 ACL 代码，来不及。

你说："写操作不应该阻塞读操作。数据接入和数据落库应该解耦。"

方案：引入 Kafka 事件总线。ACL 解析完成后，不再同步写主库，而是发布 `TrackingEventIngested` 事件到 Kafka。后台消费服务异步消费、批量写入主库。

效果：

- 写入吞吐量从 500 QPS 飙升到 6000+ QPS。
- 高峰期报文积压被 Kafka 缓冲，应用层不再 OOM。
- 供应商 Webhook 收到 Kafka ACK 后立即返回，不再超时重试。

### 问题本质

**同步调用链（Call/Return）在海量写入场景下成为瓶颈。**

在调用/返回风格中，调用方发出请求后必须等待被调用方返回结果。当写入量激增时，等待链条上的每一个环节都成为阻塞点。

**事件驱动风格**通过**隐式调用（Implicit Invocation）**实现发布方与订阅方的完全解耦：发布方发出事件，不关心谁处理、什么时候处理。订阅方注册感兴趣的事件类型，事件发生时系统自动调用处理器。

> **隐式调用 vs 显式调用**：显式调用中，调用方必须知道被调用方是谁（`userService.createOrder()`）；隐式调用中，发布方只管发事件（`eventBus.publish("OrderCreated")`），不关心谁订阅。

**牺牲的质量属性**：事件驱动风格在可修改性和可靠性上最优（新增订阅方无需修改发布方、支持异步重试），但在**安全性上表现最差**（事件广播难以加密隔离）。需要通过事件总线 ACL、消息加密等战术来补强。

### 引出的风格与战术

**事件驱动风格（Event-Driven / Implicit Invocation）**：

| 特征 | 描述 |
|------|------|
| 构件 | 事件源（Publisher）、事件处理器（Subscriber） |
| 连接件 | 事件总线（Event Bus）：Kafka Topic |
| 控制流 | 隐式调用——发布方不知晓订阅方 |
| 适用场景 | 消息队列、GUI 事件、微服务事件、削峰填谷 |
| 优点 | 完全解耦、异步非阻塞、新增订阅方无需改发布方 |
| 缺点 | 调试困难、时序不可控、安全性较差 |

**事件驱动 vs 进程通信**（独立构件风格内部对比）：

| 维度 | 事件驱动（隐式调用） | 进程通信（显式调用） |
|------|---------------------|---------------------|
| 耦合方式 | 事件解耦，发布方不知订阅方 | 显式引用，调用方知道被调用方 |
| 时序性 | 异步，非阻塞 | 通常同步，阻塞等待 |
| 扩展性 | 高（新增订阅无需改发布方） | 低（新增调用需修改调用方） |
| 错误隔离 | 好（一个处理器崩溃不影响其他） | 差（调用链中任一节点崩溃影响全局） |

**Kafka 事件总线设计**：

| 设计点 | 方案 | 理由 |
|--------|------|------|
| Topic 划分 | `tracking.ingested` / `tracking.normalized` / `tracking.stored` | 按处理阶段分 Topic，便于独立扩缩容 |
| Partition 策略 | 按 tracking_no 哈希分配 | 同一运单号的事件进入同一 Partition，保证顺序 |
| ACK 机制 | acks=all（所有副本确认） | 保证不丢消息 |
| 本地消息表 | DB 事务内写入 + 消息记录，后台线程补偿投递 | 保证可靠投递（DB 和 MQ 的最终一致性） |

### 关键指标

| 指标 | 优化前 | 优化后 | 说明 |
|------|--------|--------|------|
| 写入吞吐量 | 500 QPS | 6,000+ QPS | 12 倍提升 |
| 高峰期报文积压 | 应用层 OOM | Kafka 缓冲，零丢失 | 削峰填谷效果 |
| 供应商超时重试 | 频繁 | 0 | Kafka ACK 即确认 |
| 主库写入延迟 | 队列堆积 | 批量异步写入，稳定 | 消费端批量写入优化 |

### 架构师视角

1. **事件驱动风格的核心价值是解耦。** 发布方不关心订阅方，订阅方也不依赖发布方。这种双向解耦在海量写入场景下是唯一的可扩展方案。
2. **隐式调用带来调试困难。** 事件链路不像同步调用那样可以通过堆栈追踪。因此必须引入分布式链路追踪（SkyWalking），否则问题排查如同盲人摸象。
3. **Partition 按 tracking_no 哈希是保证顺序的关键。** 如果同一运单号的事件分散到不同 Partition，消费者可能先收到"已签收"再收到"运输中"，导致数据状态混乱。
4. **事件驱动牺牲了安全性换可修改性。** 在论文中必须体现这个权衡意识——新增供应商适配器（可修改性提升）的代价是事件链路的管控复杂度增加（安全性下降）。

### 论文句式

> "针对双十一海量写入场景下同步调用链成为瓶颈的问题，我引入事件驱动风格（Event-Driven Style）实现异步削峰。ACL 防腐层解析完成后不再同步写入主库，而是将 TrackingEventIngested 事件发布到 Kafka 事件总线，后台消费服务异步批量写入。Kafka Partition 按 tracking_no 哈希分配保证同一运单事件的顺序性。写入吞吐量从 500 QPS 提升至 6000+ QPS，高峰期应用层零 OOM。事件驱动风格在可修改性和可靠性上表现最优，但在安全性上表现最差，需要通过事件总线 ACL 和消息加密来补强。"

### 论文记忆钩子

> **发布者不认识订阅者，系统才松耦合。**

## 第七阶段 · 规则期：供应商规则不能总靠发版

### 故事场景

系统稳定运行三个月后，团队发现了一个新问题。

ACL 防腐层里的状态码映射规则越来越庞大：

```java
// DHL 状态码映射
if (status == 1) return "IN_TRANSIT";
if (status == 2) return "OUT_FOR_DELIVERY";
if (status == 3) return "DELIVERED";
// ... DHL 有 15 个状态码

// FedEx 状态码映射
if (status == "IT") return "IN_TRANSIT";
if (status == "OD") return "OUT_FOR_DELIVERY";
if (status == "DL") return "DELIVERED";
// ... FedEx 有 20 个状态码

// 某国邮政状态码映射
if (status == 3) return "IN_TRANSIT";  // 注意：3 在这里是运输中，在 DHL 是已签收
// ...
```

200+ 家供应商，每家 10-25 个状态码，总共 3000+ 条映射规则，全部硬编码在代码里。

每次新供应商接入或老供应商修改状态码体系：
- 改代码
- 编译
- 回归测试
- 部署发版

开发负责人抱怨："改一个状态码映射就要发一次版，我们成了配置管理员。"

产品经理也不满："供应商说他们的状态码下周要调整，但我们发版周期是两周一次，根本来不及。"

你在架构评审会上说："规则不应该写在代码里。规则应该被解释执行。"

### 问题本质

**硬编码的业务规则违反开闭原则（对扩展开放，对修改关闭）。**

虚拟机风格（Virtual Machine）通过**解释器**或**规则引擎**，将"业务规则"从"代码逻辑"中分离出来。规则存储在外部配置（数据库、规则文件、规则管理平台）中，由解释引擎在运行时动态加载和执行。

这使得非技术人员（如运营人员）也能通过配置界面维护规则，不需要改代码、不需要发版。

> **风格澄清**：解释器风格和基于规则的系统都属于**虚拟机风格**。其核心特征是提供一个自定义的执行语义环境，由引擎解释执行用户定义的规则或指令。

### 引出的风格与战术

**解释器风格（Interpreter）**：

| 特征 | 描述 |
|------|------|
| 构件 | 指令集、解释引擎、执行上下文、存储区 |
| 连接件 | 指令的执行顺序、跳转、循环 |
| 适用场景 | SQL 引擎、脚本语言解释器、工作流引擎 |
| 优点 | 用户可编程、灵活性极高、核心引擎可复用 |
| 缺点 | 执行效率低（相比编译执行）、引擎开发复杂度高 |

**基于规则的系统（Rule-Based System）**：

| 特征 | 描述 |
|------|------|
| 构件 | 规则集合（IF-THEN）、事实库、推理引擎 |
| 推理方式 | 正向推理（数据驱动）或反向推理（目标驱动） |
| 适用场景 | 专家系统、风控规则引擎、定价策略引擎 |
| 优点 | 业务规则与代码分离、易于非技术人员维护 |
| 缺点 | 规则冲突检测困难、规则数量增长后性能下降 |

**规则引擎在本项目中的应用**：

| 设计点 | 方案 |
|--------|------|
| 规则存储 | MySQL 规则表（supplier_code, external_status, internal_status） |
| 推理方式 | 正向推理——收到外部报文后，根据 supplier_code + external_status 查询规则表 |
| 热更新 | 规则变更后，配置中心推送新规则到各节点，无需重启 |
| 默认规则 | 未知状态码映射为 UNKNOWN，不阻断流程 |

**质量属性映射**：虚拟机风格在**灵活性（可修改性）上最优**，业务规则可独立于代码变更。但**执行效率最低**（解释执行相比直接代码执行有额外开销）。

**牺牲的质量属性**：选择规则引擎后，牺牲了执行效率（每次规则匹配需要查表/加载），换取了极致的可修改性。本项目中规则引擎执行延迟 < 5ms，在可接受范围内。

### 关键指标

| 指标 | 优化前 | 优化后 | 说明 |
|------|--------|--------|------|
| 新供应商接入时间 | 2 天（改代码+测试+发版） | 2 小时（配置规则即可） | 效率提升 12 倍 |
| 规则变更发版频率 | 每月 4 次 | 0（热更新） | 规则不再需要发版 |
| 规则数量 | 硬编码，难以统计 | 3000+ 条，独立管理 | 可视化规则列表 |
| 规则引擎执行延迟 | N/A | < 5ms | 可接受范围 |

### 架构师视角

1. **虚拟机风格的核心价值是业务与代码的分离。** 当业务规则的变化频率远高于代码逻辑的变化频率时，必须将规则从代码中拿出来。
2. **规则引擎不是万能的。** 它解决了灵活性的问题，但引入了执行效率的开销和规则冲突的风险。必须在规则入库前做冲突检测。
3. **规则热更新需要配套的安全机制。** 规则变更后，必须验证新规则的完整性和兼容性，避免一条错误规则导致整条数据链路异常。
4. **解释器风格和规则引擎的区别在于抽象层次。** 解释器风格更底层（自定义指令集+解释执行），规则引擎更面向业务（IF-THEN 规则+推理执行）。本项目选择规则引擎，因为规则的本质是"条件→结果"的映射，不需要自定义指令集。

### 论文句式

> "针对 200+ 供应商状态码映射规则硬编码在代码中、每次变更需要发版的问题，我引入虚拟机风格（Virtual Machine Style）中的基于规则的系统。将 3000+ 条映射规则从代码中分离到 MySQL 规则表中，由推理引擎在运行时正向推理执行。配合配置中心实现规则热更新，供应商接入时间从 2 天缩短至 2 小时，规则变更发版频率从每月 4 次降至 0。虚拟机风格在灵活性上表现最优，但执行效率最低，本项目中规则引擎执行延迟 < 5ms，在可接受范围内。"

### 论文记忆钩子

> **变化快的规则，从代码里拿出来。**

## 第八阶段 · 成熟期：真实系统都是混合风格

### 故事场景

系统运行一年后，你站在白板前画了一张架构图：

```
┌─────────────────────────────────────────┐
│  层次结构风格（整体架构框架）              │
│  ┌───────────────────────────────────┐  │
│  │  表示层：Web API Gateway           │  │
│  ├───────────────────────────────────┤  │
│  │  业务层：                          │  │
│  │  ├── 管道-过滤器（ACL 数据清洗）     │  │
│  │  ├── 事件驱动（Kafka 异步削峰）     │  │
│  │  └── 规则引擎（供应商状态映射）     │  │
│  ├───────────────────────────────────┤  │
│  │  仓库风格（读写分离 + 缓存补偿）     │  │
│  │  ├── Master（写）                   │  │
│  │  ├── Slave1/2/3（读）              │  │
│  │  └── Redis Cluster（缓存）          │  │
│  └───────────────────────────────────┘  │
└─────────────────────────────────────────┘
```

开发负责人看着图说："我们现在用的风格也太多了。"

新来的 CTO 问了一个尖锐的问题："为什么这里用事件驱动不用管道-过滤器？为什么这里用仓库不用黑板？每个选择的依据是什么？"

团队沉默了。

你说："我们凭经验做了正确的选择，但没有系统地解释为什么。"

你引入了 ATAM（Architecture Tradeoff Analysis Method）。

### 问题本质

**真实系统的架构风格从来不是单一的。**

混合风格的设计必须回答两个核心问题：
1. 不同风格如何协同工作并保持数据一致？
2. 为什么在这个场景选风格 A 而不是风格 B？

ATAM 提供了系统化的评估框架，帮助我们识别每个架构决策的**敏感点**（影响特定质量属性的决策）和**权衡点**（同时影响多个质量属性的决策），让架构选择有据可依。

同时，**不是所有风格都适合本项目。** 理解一个风格"为什么不选"和"为什么选"同样重要。

### 引出的风格与战术

**ATAM 方法（Architecture Tradeoff Analysis Method）**：

| 阶段 | 步骤 | 产出 |
|------|------|------|
| Phase 1：准备 | 步骤 1-3：展示 ATAM、业务驱动、架构描述 | 业务目标文档、架构视图 |
| Phase 2：探索 | 步骤 4-6：确定架构方法、构建质量属性效用树、分析架构方法 | 效用树、初步风险列表 |
| Phase 3：深入 | 步骤 7-9：选择场景、分析架构方法、场景影响描述 | 场景分析报告 |
| Phase 4：报告 | 步骤 10-12：深入分析、生成报告 | 风险点/非风险点/敏感点/权衡点清单 |

**敏感点 vs 权衡点**：

| 概念 | 定义 | 本例 |
|------|------|------|
| 敏感点 | 影响特定质量属性的架构决策 | 读写分离→影响性能 |
| 权衡点 | 同时影响多个质量属性的决策 | 事件驱动→提升可修改性，降低安全性 |

**本项目 ATAM 分析结果**：

| 架构决策 | 敏感点 | 权衡点 | 影响的质量属性 |
|---------|--------|--------|--------------|
| 仓库风格读写分离 | 性能显著提升 | 牺牲一致性 | 性能↑，一致性↓ |
| 管道-过滤器 ACL | 可测试性显著提升 | 可靠性下降（管道断裂风险） | 可测试性↑，可靠性↓ |
| 事件驱动 Kafka | 可修改性显著提升 | 安全性下降 | 可修改性↑，安全性↓ |
| 规则引擎 | 灵活性显著提升 | 执行效率下降 | 可修改性↑，性能↓ |
| 层次结构整体框架 | 安全性显著提升 | 性能下降 | 安全性↑，性能↓ |

**质量属性 × 风格映射（系统化论述）**：

| 质量属性 | 最优风格 | 最差风格 | 本项目选择 | 理由 |
|---------|---------|---------|-----------|------|
| 性能 | 管道-过滤器 | 层次结构 | 仓库+缓存 | 读写竞争是首要瓶颈 |
| 可靠性 | 事件驱动/黑板 | 管道-过滤器 | 事件驱动+降级 | 管道断裂风险必须补强 |
| 安全性 | 层次结构 | 事件驱动 | 层次结构为框架 | 物流数据需要边界管控 |
| 可修改性 | 事件驱动 | 主程序-子程序 | 事件驱动+管道-过滤器 | 供应商规则多变 |
| 可测试性 | 管道-过滤器 | 黑板 | 管道-过滤器 ACL | 每个过滤器独立测试 |
| 可复用性 | 管道-过滤器 | 主程序-子程序 | 管道-过滤器 | 过滤器可跨项目复用 |

**混合风格协同机制**：

| 风格组合 | 协同方式 | 数据一致性保障 |
|---------|---------|--------------|
| 仓库 + 管道-过滤器 | ACL 管道处理数据，归一化后写入仓库 | 管道输出 = 仓库输入，标准接口契约保证 |
| 仓库 + 事件驱动 | 数据写入仓库后发布事件，触发下游 | 本地消息表模式保证 DB 和 MQ 最终一致 |
| 层次 + 事件驱动 | 层间用事件总线通信，层内同步调用 | 事件总线作为层间中间件，统一路由 |

**黑板风格为什么没选**：

黑板风格（Blackboard Style）适合多个知识源围绕共享工作区进行增量式、探索性推理的场景，如语音识别、专家诊断。其核心特征是：多个知识源**协作猜测**同一个问题的答案，逐步向收敛方向推进。

物流追踪平台的核心矛盾是**海量数据接入、查询性能和异构报文归一化**——这是一个确定性的数据处理流程，不需要增量推理、不需要协作猜测。因此选择仓库 + 管道 + 事件的混合风格，而不是黑板风格。

> **风格澄清**：黑板风格属于**数据中心化风格**，与仓库风格同属一大类但适用场景完全不同。仓库风格 = 组件通过中央存储间接交互（确定性数据管理）；黑板风格 = 多知识源协作增量推理（不确定性问题解决）。

### 关键指标

| 指标 | 数值 | 说明 |
|------|------|------|
| 识别敏感点 | 6 个 | ATAM 分析产出 |
| 识别权衡点 | 4 个 | ATAM 分析产出 |
| 架构决策文档化率 | 100% | 每个决策都有依据 |
| 系统可用性 | 99.99% | SLA 级别 |
| P99 延迟 | 400ms | 最终指标 |

### 架构师视角

在这个阶段，我完成了以下工作：

1. **引入 ATAM 系统化评估架构决策。** 构建质量属性效用树，从业务需求出发推导出关键质量场景，对每个架构决策分析其敏感点和权衡点。ATAM 不是"为了评估而评估"，而是为了让架构选择有据可依。
2. **明确混合风格的协同机制。** 仓库 + 管道：ACL 管道归一化后写入仓库；仓库 + 事件：本地消息表保证一致性；层次 + 事件：事件总线作为层间中间件。不同风格在一起工作时，必须有明确的数据一致保障。
3. **排除不适合的风格。** 黑板风格适合语音识别、专家诊断等增量推理场景，而物流平台的核心矛盾是数据接入和查询性能，因此不选黑板。理解"为什么不选"和理解"为什么选"同等重要。
4. **架构师的核心能力是权衡。** 没有完美的风格，只有适合当前业务阶段的选择。层次结构提供秩序，仓库解决数据管理，管道治理异构接入，事件驱动实现解耦，规则引擎应对变化，ATAM 帮助解释为什么这样组合。

### 论文句式

> "随着系统引入多种架构风格，我通过 ATAM 方法系统化评估了各质量属性的敏感点与权衡点。构建了包含性能、可靠性、安全性、可修改性、可测试性、可复用性六个维度的质量属性效用树，识别出 6 个敏感点和 4 个权衡点。同时明确了混合风格的协同机制：仓库 + 管道-过滤器通过标准接口契约保证数据一致，仓库 + 事件驱动通过本地消息表保证最终一致。对于黑板风格，因物流平台核心矛盾是海量数据接入与查询性能而非增量推理，故选择不采用。真实系统的架构风格从来不是单一的，架构师的核心能力是在质量属性之间做权衡。"

### 论文记忆钩子

> **风格不是越多越好，而是权衡要说清。**

| 8 成熟期 | 真实系统都是混合风格 | 混合风格 + ATAM 评估 | 多风格协同复杂度↑ | 风格不是越多越好，而是权衡要说清 |

## 附录二：核心记忆线（背诵版）

```
分层立秩序，仓库管数据；
读写抗压力，管道治异构；
缓存补延迟，降级保可用；
事件解耦合，规则管变化；
ATAM 做权衡。
```

```
阶段 1 → 层次结构风格    → 分层解决秩序，不解决规模
阶段 2 → 仓库风格         → 仓库集中数据，也集中压力
阶段 3 → 管道-过滤器风格   → 数据先清洗，再入仓库
阶段 4 → 仓库风格 + 战术   → 一致性换可用性，要用缓存补偿
阶段 5 → 可用性战术补强    → 加速器坏了，也要有刹车
阶段 6 → 事件驱动风格      → 发布者不认识订阅者，系统才松耦合
阶段 7 → 虚拟机风格        → 变化快的规则，从代码里拿出来
阶段 8 → 混合风格 + ATAM  → 风格不是越多越好，而是权衡要说清
```
