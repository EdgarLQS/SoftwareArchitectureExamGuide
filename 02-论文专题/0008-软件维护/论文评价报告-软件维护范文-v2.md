# 软件维护范文训练评价 v2

> 评估对象：`03-软件维护论文范文-改写版.md`
>
> 评价性质：内部训练复盘，非官方评分。原 `71/75` 已取消。

## 一、总体判断

当前等级：**usable（可用）**。

优点：

- 能区分纠错、适应、完善和预防性维护；
- 覆盖故障恢复、技术债、重构、测试和变更管理；
- 实践问题与维护主题相关；
- 具备可迁移到遗留系统、软件演进和可维护性题目的素材。

主要风险：

- 把维护类型占比和生命周期成本比例写成通用固定事实；
- 使用固定圈复杂度、覆盖率和技术债单位作为绝对质量线；
- MTBF、可用性、MTTR 和故障频率之间缺少一致性校验；
- “适配 2 周→30 分钟”等提升与实际工作范围不匹配；
- CCB 和 20% 技术债容量被写成所有团队通用做法；
- 项目和效果指标属于模拟数据但标注不足。

## 二、技术审查

| 主题 | 状态 | 修订建议 |
|------|------|----------|
| 四类维护 | 稳定 | 保持定义，比例引用必须给出来源 |
| 故障管理 | 可用 | 区分发现、止损、恢复和永久修复 |
| 变更管理 | 可用 | 按风险分级，不让所有变更进入重审批 |
| 技术债 | 待加强 | 记录原因、利息、风险、负责人和偿还方案 |
| 重构 | 待加强 | 先建立特征测试和度量，再渐进修改 |
| 测试覆盖 | 待修订 | 覆盖率只是信号，增加关键路径和变异测试 |
| 复杂度阈值 | 待修订 | 按语言和模块校准，不统一设为 10 |
| 指标一致性 | P0 | 统一 MTTR、可用性、故障和变更指标 |
| 模拟数据 | 待统一 | 与记忆卡和框架使用同一口径 |

## 三、关键修订

### 3.1 维护分类

四类维护用于说明变更目的，不直接决定唯一流程。同一次变更可能同时具有纠错和预防性目的，论文应说明主要目标、风险和验收方式。

### 3.2 技术债

固定预留 20% 研发容量可以作为团队策略，但需要业务和风险依据。更通用的做法是维护债务清单，按故障、安全、变更成本和业务机会排序。

### 3.3 可靠性指标

- MTTA：发现故障所需时间；
- MTTR：恢复服务所需时间；
- 变更失败率：发布引起故障或回滚的比例；
- 可用性：服务在统计窗口内满足要求的比例；
- MTBF 在软件服务中的使用需要明确故障定义和统计口径。

这些指标必须共享同一时间窗口和故障定义。

## 四、模拟指标建议

| 指标 | 改造前 | 改造后 |
|------|--------|--------|
| MTTR | 4 小时 | 30 分钟 |
| 变更缺陷 | 12 起/月 | 少于 2 起/月 |
| 变更成功率 | 82% | 98% |
| 关键路径覆盖 | 45% | 82% |
| 高复杂度模块平均复杂度 | 12 | 6 |
| 高风险适配交付周期 | 2 周 | 2 天 |
| 可用性 | 99.0% | 99.9% |

## 五、优先修订清单

- [ ] 标记项目和指标为模拟数据
- [ ] 删除无来源的维护占比和成本比例
- [ ] 统一可靠性、变更和故障指标
- [ ] 将固定质量阈值改为模块化校准
- [ ] 增加特征测试、灰度和回滚
- [ ] 说明技术债优先级和投入依据
- [ ] 缩小不合理的“分钟级适配”效果
- [ ] 核对记忆卡、框架和范文全部指标

## 六、提升为 stable 的条件

```text
四类维护定义和应用场景清楚
变更流程按风险分级
技术债和重构有证据与验收
可靠性指标口径一致
模拟数据合理
限时迁移写作无重大遗漏
```
