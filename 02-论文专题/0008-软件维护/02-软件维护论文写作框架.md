# 软件维护论文写作框架

> 本框架按题目要求和维护风险组织，不再强制五段、固定字数或统一质量阈值。

## 一、适用题型

- 论软件维护及其应用；
- 说明纠错、适应、完善和预防性维护；
- 说明可维护性、技术债、重构和软件演进；
- 说明变更管理、故障恢复和持续改进；
- 结合项目说明维护体系、难点和效果。

## 二、审题映射

| 题目要求 | 必须回答 |
|----------|----------|
| 维护分类 | 目的、触发条件、活动和验收方式 |
| 维护流程 | 发现、评估、修改、验证、发布和复盘 |
| 可维护性 | 模块化、测试、观测、文档、配置和依赖治理 |
| 技术债与重构 | 风险、收益、优先级、保护性测试和渐进迁移 |
| 项目实践 | 故障、变更、债务、指标和副作用 |

## 三、推荐结构

```text
摘要
→ 项目背景、维护痛点和本人职责
→ 四类维护及其使用边界
→ 可维护性、变更和技术债治理体系
→ 项目实践：故障、变更和重构
→ 效果、不足和持续演进
```

## 四、四类维护

| 类型 | 目的 | 示例 | 管理重点 |
|------|------|------|----------|
| 纠错性维护 | 修复已发现缺陷 | 支付状态错误、内存泄漏 | 止损、根因和防复发 |
| 适应性维护 | 适应外部环境变化 | 数据库升级、政策和接口变化 | 兼容、迁移和回滚 |
| 完善性维护 | 改进功能、性能或体验 | 查询优化、新业务能力 | 价值、范围和回归测试 |
| 预防性维护 | 降低未来风险和成本 | 重构、依赖升级、债务清理 | 风险排序和效果度量 |

同一次变更可能同时具有多种目的。各类比例和维护成本占比因行业、生命周期和统计口径不同，引用时必须有来源，不能写成通用固定事实。

## 五、维护闭环

### 5.1 纠错流程

```text
告警或用户反馈
→ 影响评估与止损
→ 收集证据和定位根因
→ 修复与回归验证
→ 灰度发布和回滚准备
→ 复盘并形成永久改进
```

区分：

- MTTA：发现故障时间；
- MTTR：恢复服务时间；
- 永久修复时间：完成根因修复所需时间；
- 复发率：同类问题再次出现的比例。

### 5.2 变更管理

- 按风险、影响范围和可回滚性分级；
- 高风险变更进行架构、数据和安全影响分析；
- 使用 Code Review、契约测试、回归和静态分析；
- 使用功能开关、金丝雀或蓝绿发布；
- 变更后观察业务和技术指标；
- CCB 是否需要取决于组织和风险，不让所有变更进入重审批。

## 六、可维护性设计

| 方向 | 主要措施 |
|------|----------|
| 模块化 | 高内聚、低耦合、边界和依赖方向 |
| 可测试性 | 依赖可替换、契约清楚、分层自动化测试 |
| 可观测性 | 日志、指标、追踪、业务事件和关联 ID |
| 配置化 | 外部配置、版本、审计、灰度和回滚 |
| 文档化 | ADR、接口契约、运行手册和故障知识库 |
| 依赖治理 | 版本清单、漏洞、升级节奏和兼容策略 |
| 数据演进 | Schema 版本、迁移、双写校验和回滚 |

圈复杂度、覆盖率等阈值应按语言、模块和风险校准，不把 10 或 80% 写成所有系统统一质量线。

## 七、技术债与重构

技术债记录：

- 形成原因；
- 对故障、安全、变更和成本的影响；
- 持续利息；
- 偿还方案和风险；
- 不偿还的后果；
- 负责人和计划周期。

固定预留 20% 容量可以是团队策略，但不是通用最佳实践。应按风险和价值显式安排。

### 7.1 重构步骤

```text
建立运行和测试基线
→ 使用特征测试保护遗留行为
→ 识别边界和高风险依赖
→ 小步重构
→ 持续集成和灰度
→ 对比指标并回滚或继续
```

重构不能只追求代码整洁，还要验证业务正确性、性能、可靠性和交付效率。

## 八、项目实践框架

### 8.1 故障定位

```text
问题：故障依赖人工查分散日志，MTTR 4 小时
→ 根因：缺少关联 ID、Tracing 和运行手册
→ 方案：统一日志、链路、告警分级和 Runbook
→ 风险：告警噪声和存储成本
→ 验证：MTTA、MTTR 和复发率
```

### 8.2 变更副作用

```text
问题：支付超时逻辑变更引起订单状态错误
→ 根因：隐式依赖和回归覆盖不足
→ 方案：影响分析、契约测试、功能开关和灰度回滚
→ 验证：变更失败率、逃逸缺陷和恢复时间
```

### 8.3 过度拆分

```text
问题：简单查询跨多个服务，排错和发布困难
→ 根因：按概念机械拆分，忽略变更内聚和数据责任
→ 方案：根据领域边界、事务和变更频率重组
→ 验证：调用链、发布耦合、P99 和故障影响
```

是否合并为固定数量的子域不是通用结论。

### 8.4 依赖升级

```text
问题：旧依赖存在高危漏洞但升级风险大
→ 方案：依赖清单、兼容测试、分阶段升级和回滚
→ 验证：高危漏洞修复时间和升级失败率
```

## 九、质量度量

| 维度 | 指标 | 注意事项 |
|------|------|----------|
| 故障 | MTTA、MTTR、复发率 | 区分止损和永久修复 |
| 变更 | 失败率、回滚率、逃逸缺陷 | 与变更风险和规模一起看 |
| 交付 | Lead Time、部署频率 | 频率高不等于质量高 |
| 代码健康 | 复杂度、重复、依赖和漏洞 | 按模块校准 |
| 测试 | 关键路径、覆盖率和变异测试 | 覆盖率高不保证断言有效 |
| 技术债 | 风险、利息和偿还周期 | 不使用通用“天/KLOC”标准 |
| 运营 | Runbook、演练和恢复通过率 | 文档必须与实际同步 |

## 十、模拟指标口径

| 指标 | 改造前 | 改造后 |
|------|--------|--------|
| MTTR | 4 小时 | 30 分钟 |
| 变更缺陷 | 12 起/月 | 少于 2 起/月 |
| 变更成功率 | 82% | 98% |
| 关键路径覆盖 | 45% | 82% |
| 高复杂度模块平均复杂度 | 12 | 6 |
| 高风险适配交付周期 | 2 周 | 2 天 |
| 可用性 | 99.0% | 99.9% |

均为训练模拟数据。可用性、故障频率和 MTTR 必须使用一致统计窗口。

## 十一、摘要与总结

### 摘要

```text
项目与维护痛点
→ 维护分类和治理体系
→ 重点故障、变更和重构实践
→ 主要效果
→ 本文回应的题目要求
```

### 总结

```text
回扣维护目标和可维护性
→ 给出故障、变更和交付指标
→ 说明流程成本和预防投入不足
→ 给出针对性的演进计划
```

## 十二、检查单

- [ ] 四类维护定义和应用场景准确
- [ ] 没有无来源的固定维护比例和成本比例
- [ ] 故障、变更、技术债、测试和文档形成体系
- [ ] 变更流程按风险分级
- [ ] 重构有保护性测试、灰度和回滚
- [ ] 指标口径和统计窗口一致
- [ ] 固定阈值未被当作绝对质量线
- [ ] 模拟指标与记忆卡和范文一致
- [ ] 能在规定时间内用纯文字完成
